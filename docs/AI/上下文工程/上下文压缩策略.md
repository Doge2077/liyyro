# 上下文压缩策略

## 1. 概述

Agent 的每一次模型请求都需要一份当前上下文。它由系统规则、工具定义、用户目标、模型动作、工具结果、任务状态和最近一次输入共同组成。任务继续推进时，新的消息和工具结果不断追加，原始轨迹会逐渐变长。

上下文压缩（context compaction）是在任务仍然需要继续时，把较早的轨迹替换为信息密度更高的检查点（checkpoint）。检查点保存后续决策所需的事实、约束、决策、失败记录、文件位置和来源，最近一段消息继续逐字保留；无法稳定放入模型输入的原始材料则写入外部产物，使用路径或标识符回查。

压缩处理的是“发给模型的视图”，不等于删除任务的全部历史。生产系统通常同时保留三份内容：事件日志用于恢复和审计，原始产物用于追溯，压缩后的消息视图用于下一轮模型请求。这样可以在控制输入长度的同时保留可复查性。

同一个任务可以采用多种处理方式：短结果直接保留，重复结果做局部摘要，低价值工具输出只保留结论，探索型工作交给独立 Agent，历史达到压力阈值后再生成整体检查点。压缩策略需要提高信息密度，让下一次决策仍然能够回答四个问题：已经知道什么、依据来自哪里、做过哪些尝试、接下来需要完成什么。

## 2. 上下文压缩必要性

上下文变长会同时影响可发送性、费用、时延和决策质量。长任务中一次文件读取、网页检索或日志分析都可能返回数万词元；如果每轮都把完整结果留在消息列表中，模型窗口会很快被中间材料占满。

### 2.1 客观条件约束

模型的上下文窗口 `W` 同时容纳输入和输出。Agent 还需要为本轮回答、工具参数、重试和压缩摘要预留输出空间，因此真正可用于历史消息的预算小于模型标称窗口。可以用下面的形式表达主动压缩阈值：

```text
T = min(floor(W × r), W - O - B)
```

其中 `r` 是使用比例，`O` 是本轮输出预留，`B` 是安全余量，`T` 是触发主动压缩的输入预算。不同模型和服务商的计费方式不同，实际实现还需要考虑图片、工具定义、推理词元和协议包装产生的额外消耗。

| 约束 | 变长来源 | 超出后的表现 | 压缩的作用 |
| --- | --- | --- | --- |
| 上下文窗口 | 历史消息、工具结果、图片、工具定义 | 请求被拒绝或只能截断输入 | 释放可用输入空间 |
| 输入费用 | 每一轮重新发送的历史词元 | 多轮任务费用线性甚至更快增长 | 减少重复发送的历史 |
| 首词时延 | 长前缀的预填充计算 | 请求开始等待时间变长 | 缩短需要重新计算的部分 |
| 有效输出预算 | 输入占用输出窗口 | 模型回答变短，工具参数可能不完整 | 为当前动作保留空间 |
| 失败恢复 | 过长请求、网络重试、模型切换 | 任务停在中间状态 | 留出可恢复的检查点 |

例如，产品调研任务连续调用搜索工具。每次返回的网页正文约有 20,000 个词元，五轮后原始结果已经超过 100,000 个词元。把每个网页都完整带入下一轮，既会消耗大量输入费用，也会让后续请求没有空间生成新的工具调用。压缩可以把每份结果保存为原始文件、来源和短摘要，把模型输入中的内容降到与当前问题相关的事实集合。

压缩阈值不应只看历史消息长度。系统还需要把本轮用户输入、预计工具输出、模型最大输出和重试次数纳入预算。对于拥有多个模型路由的系统，阈值应按实际路由模型计算，不能用一个固定数字覆盖所有上下文窗口。

### 2.2 注意力机制

上下文压缩需要先理解注意力的计算对象。对一个注意力头，输入隐藏状态记为矩阵 `X`，模型先计算：

```text
Q = XW_Q
K = XW_K
V = XW_V

A = softmax((QKᵀ / √d_k) + M)
Y = AV
```

`Q`（Query）表示当前位置正在寻找什么，`K`（Key）表示每个历史词元可以被什么问题匹配，`V`（Value）表示匹配后取回的内容。`M` 是因果掩码：当前位置 `i` 只能看到 `j ≤ i` 的词元，未来位置的分数设为负无穷。对第 `i` 个位置而言，某个历史词元 `j` 得到的权重为：

```text
αᵢⱼ = exp(qᵢ · kⱼ / √d_k) / Σₗ≤ᵢ exp(qᵢ · kₗ / √d_k)
```

输出 `yᵢ` 是所有可见 `vⱼ` 的加权和。模型会在多层、多头中重复这个过程，逐步把分散在上下文里的信息组合到当前表示中。这个机制提供了强大的按内容检索能力，也带来几个与长上下文直接相关的数学限制。

**第一，计算量随可见位置成平方增长。** 一次全量预填充需要生成 `n × n` 的注意力分数矩阵，标准实现的计算量近似为 `O(n²d)`，其中 `n` 是输入词元数，`d` 是每个头的维度；显式保存分数矩阵时，注意力中间结果的空间也接近 `O(n²)`。FlashAttention 等实现可以减少中间矩阵的存储量，但每个新位置仍需要读取它之前的大量 `K`、`V`。因此，输入从 32K 增长到 128K 时，预填充工作量不会只增加四倍，注意力部分的两两交互会增加到约十六倍量级。

**第二，softmax 让有限权重在候选项之间分配。** 如果多个历史词元与当前查询的分数接近，`αᵢⱼ` 会接近均匀分布；当可见位置从 `m` 增加到 `4m`，同等分数下单个事实得到的权重大致从 `1/m` 降到 `1/(4m)`。真实模型会用多头、不同层和更尖锐的分数集中权重，长上下文也不必然导致均匀分配，但重复日志、网页菜单、格式标记和多份相同结论会增加竞争项，让关键事实需要更强的匹配信号才能脱颖而出。

**第三，注意力输出是加权混合。** `Y = AV` 产生的是多个 `V` 向量的组合。某个事实如果只出现一次，且没有明确的字段名、来源或任务关系，它的表示可能与周围内容混合；重复出现的结论更容易获得稳定信号，互相矛盾的结果则会让不同层的表示承担额外辨别工作。压缩摘要需要把事实、状态、来源和关系写成结构化字段，帮助后续查询产生更清晰的 `Q-K` 匹配。

**第四，位置编码带来距离和外推约束。** 以 RoPE 为例，位置 `i` 的查询和位置 `j` 的键经过旋转后，点积会携带相对位置 `i-j` 的相位信息。模型在训练窗口内学到的相位范围有限，输入接近或超过训练长度时，远距离位置的区分可能变得困难；不同模型的长上下文扩展方法会改善这种现象，仍然需要在实际长度上验证。消息顺序、重复插入和压缩边界会改变位置序列，因此压缩后的内容需要保持清晰的时间顺序与阶段边界。

**第五，注意力只处理词元，不直接处理事实。** 一个路径、日期或 JSON 字段可能被拆成多个词元；模型需要先从这些词元恢复实体，再把实体与任务目标关联。把长网页原文塞进上下文，增加的是词元和匹配机会，事实之间的关系仍然需要模型从文本中重建。压缩保留“结论—来源—状态”的紧凑表达，可以减少从词元恢复结构的工作。

因此，注意力机制的数学限制可以归纳为三类成本：两两交互带来的计算增长，softmax 权重竞争造成的信号稀释，位置和表示混合造成的远距离检索难度。压缩策略需要降低候选词元数量，提升关键事实的结构化程度，并保留足够的位置与关系信息。

这会产生几类常见现象：

| 现象 | 具体表现 | 压缩时需要保留的内容 |
| --- | --- | --- |
| 关键事实被稀释 | 模型重新搜索已经确认过的资料 | 事实、数值、时间和来源 |
| 关系被拆散 | 工具结果仍在，但看不出它回答了哪个问题 | 调用标识、问题、结果之间的对应关系 |
| 决策理由消失 | 模型重复讨论已经否决的方案 | 决策、理由、适用条件 |
| 失败路径被遗忘 | 模型再次调用已经失败的接口 | 失败原因、重试次数、替代方案 |
| 任务状态过时 | 模型误以为文件、权限或环境仍处于旧状态 | 当前阶段、已完成项、待办和限制 |

因此，简单的滑动窗口并不适合长任务。它可以缩短输入，却可能把“为什么不再尝试某条路径”一起移除，导致 Agent 重复执行相同工具调用。压缩应当围绕任务语义组织内容，至少保留事实与关系：事实说明发生了什么，关系说明该事实服务于哪个目标、来自哪次操作。

压缩摘要也需要区分信息类型。架构决策、用户约束、文件路径、提交哈希、URL、端口号和工具调用 ID 属于精确标识，适合逐字保留；网页背景、重复日志和已经验证的中间推导可以概括；尚未确认的猜测需要明确标记，不能与事实混写。

### 2.3 压缩与 KV Cache互补

KV Cache 和上下文压缩处理的是两个层次的问题。模型在一次推理过程中会缓存已经计算出的键和值，避免生成每个新词元时从头计算前缀；服务商也可能跨请求复用相同的提示前缀，这通常称为 Prompt Cache。两者都依赖前缀稳定，但作用范围不同。

上下文压缩会替换历史中的一段内容，因此从替换位置开始的缓存通常需要重新计算。把压缩放在系统规则和工具定义之后，可以保留更早的稳定前缀；把动态状态追加到末尾，可以减少前缀变化对缓存的影响。

| 操作 | 对历史的影响 | 对前缀缓存的影响 | 适用位置 |
| --- | --- | --- | --- |
| 追加新的用户消息或工具结果 | 只增加末尾内容 | 已有前缀可以继续复用 | 每轮正常推进 |
| 修改系统提示词 | 改变最早的输入 | 后续缓存大范围失效 | 版本切换或规则变更 |
| 删除中间工具结果 | 从删除点开始改变序列 | 删除点之后需要重新计算，缓存编辑接口可减少重算 | 上下文压力上升 |
| 用摘要替换旧历史 | 生成新的检查点 | 替换点之后重新建立缓存 | 长任务阶段切换 |
| 子 Agent 隔离探索 | 主 Agent 只接收结论 | 主 Agent 前缀保持不变 | 大量检索、代码浏览 |

这说明压缩不应在每一轮都执行。过于频繁的摘要会增加额外模型请求，并反复重建缓存；完全不压缩又会让输入、费用和注意力压力持续上升。常见做法是先处理单条大结果，再在接近阈值时批量处理旧历史，同时保留稳定的系统前缀和工具目录。

## 3. 压缩策略

阅读这些实现时，需要把三个对象分开：消息视图决定本轮发给模型的内容，事件日志记录压缩前后的操作，提供方检查点保存只能在原路由中回放的状态。公开文档描述用户能观察到的行为，源码揭示范围选择、预算计算和失败恢复的细节，社区文章适合提供线索，不能替代代码和规范。下文按本地仓库快照与公开文档交叉核对；函数名、常量和目录会随版本变化，文章中的路径用于解释实现关系。

### 3.1 常用的分层压缩策略

生产系统通常按信息粒度和处理成本组织多层策略。低成本操作先减少明显冗余，只有仍然超出预算时才启动需要额外模型请求的整体摘要。

| 层级 | 处理对象 | 典型操作 | 是否需要额外模型请求 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 单条超大工具结果 | 截断展示，原文写入文件 | 否 | 模型看到预览和产物路径 |
| 2 | 单条结果中的重复信息 | 提取结论、参数、来源和错误 | 可选 | 结果变短，调用关系保留 |
| 3 | 低价值旧消息 | 删除或折叠整条消息、代码块和重复日志 | 否 | 释放空间，保留边界标记 |
| 4 | 探索型中间过程 | 委托给子 Agent，只回传结论 | 需要子 Agent | 主上下文不承载大段中间材料 |
| 5 | 已完成的历史阶段 | 生成结构化会话摘要并保留最近尾部 | 是 | 形成可恢复检查点 |
| 6 | 压缩请求自身过长 | 从最早的消息组开始缩短后重试 | 通常需要 | 让压缩请求有机会完成 |

#### 分层策略如何协同

分层压缩的关键是为每一条内容同时计算三个属性：当前体积、再次使用的可能性、重新获取的成本。搜索结果通常体积大、再次使用的可能性中等、重新获取成本可能很高；重复的目录输出体积大、事实密度低、重新获取成本很低；用户给出的约束体积小、影响范围大、重新获取成本极高。三类内容应当进入不同的处理层。

可以把选择过程写成下面的决策顺序：

1. 先检查结果是否超过单条输出上限。超过时保存完整产物，消息只留下预览、统计信息和产物路径。
2. 再检查结果是否已经有可靠摘要。已有摘要可以复用，避免每轮重复调用摘要模型；摘要必须带来源和适用范围。
3. 再检查消息是否属于同一次 API round。选择压缩范围时保持用户消息、assistant 工具调用和对应的 `tool_result` 完整配对。
4. 再根据任务阶段决定摘要重点。搜索阶段偏向保留候选来源和未确认事实，分析阶段偏向保留证据链和决策理由，执行阶段偏向保留文件变更、测试结果和失败限制。
5. 最后才选择整体摘要。整体摘要需要生成新的边界事件，并记录它覆盖了哪些原始消息和产物。

压缩范围通常有两个边界：前边界保护稳定前缀和系统规则，后边界保护最近一段可直接用于下一步的消息。中间区域可以被折叠或摘要。后边界不能只按消息条数计算，因为一条网页结果可能占用几万词元；成熟实现会按 token 预算选择近期尾部，并向前移动到工具调用配对完整的位置。

每次压缩应产生一个可观测记录：

```json
{
  "trigger": "token_threshold",
  "selected_range": {"start": "event_018", "end": "event_067"},
  "retained_tail_tokens": 12000,
  "input_tokens_before": 118400,
  "input_tokens_after": 42300,
  "summary_request_tokens": 9400,
  "artifacts": ["artifacts/search/result_07.json"],
  "status": "completed"
}
```

这类记录能把“压缩成功”拆成可检查的事实：范围是否正确、释放了多少空间、摘要请求花费多少、原始材料是否仍可访问。只记录压缩后的文本，无法定位错误来自摘要内容还是范围选择。

分层处理需要明确输入和输出边界。工具结果修剪器只改变模型看到的内容，原始输出仍保存在外部文件；会话摘要只负责建立新的上下文入口，任务状态、权限和文件快照继续由独立存储维护；子 Agent 的中间轨迹留在自己的会话里，主 Agent 接收带来源的结果。

一个可恢复的检查点可以包含以下字段：

```json
{
  "objective": "完成产品研讨会资料、PRD 和评审安排",
  "completed": [
    "确认三个竞品的核心能力",
    "保存来源页面和原始检索结果"
  ],
  "decisions": [
    "PRD 先覆盖会议记录、摘要和待办提取"
  ],
  "constraints": [
    "每条外部事实必须带来源",
    "未公开的价格和识别准确率仍需验证"
  ],
  "pending": [
    "补充用户访谈问题",
    "安排评审会议"
  ],
  "artifacts": [
    "artifacts/search/competitor-a.json"
  ]
}
```

其中 `objective`、`completed`、`decisions`、`constraints` 和 `pending` 面向下一轮决策，`artifacts` 负责把摘要与原始材料连接起来。摘要应当说明事实的来源和状态，不能只留下“已经处理”这类无法复核的结论。

### 3.2 Claude Code压缩策略

#### Cluade Code压缩概述

Claude Code 的源码把压缩分成三条主路径，并在其外提供上下文折叠、snip 和超限兜底等可选或异常路径。源码位置主要在 `src/services/compact/` 与 `src/services/contextCollapse/`。

| 序 | 层 | 文件 | 粒度 | 触发 |
|----|----|------|------|------|
| 1 | **microcompact 微压缩** | `microCompact.ts` | 清除旧的单条 `tool_result` 内容 | 主线程请求前的轻量处理 |
| 2 | **Session Memory Compact** | `sessionMemoryCompact.ts` | 使用已提取的会话记忆替换旧历史 | feature flag 开启且自动压缩触发 |
| 3 | **传统 API 摘要** | `compact.ts` | 摘要旧历史、保留近期消息并重注附件 | 手动 `/compact` 或 Session Memory 不可用 |
| 4 | **context-collapse 折叠** | `contextCollapse/` | 将可重新读取的代码块替换为引用 | feature `CONTEXT_COLLAPSE` 且达到阈值 |
| 5 | **snip 剪除** | `snipCompact.ts` | 按 UUID 删除模型指定的历史消息 | 模型主动调用或 `/force-snip` |
| 6 | **reactive compact 被动兜底** | `reactiveCompact.ts`、`compact.ts` | 缩短最早 API round 后重新摘要 | 服务商返回 `prompt-too-long` |

前三层构成主压缩链：先清除可以重新读取的工具结果，再尝试无模型调用的会话记忆，最后才请求摘要模型。context-collapse 和 snip 属于额外的消息级处理，reactive compact 负责请求已经超限后的恢复。

Claude Code 的阈值计算可以拆成三步。`getEffectiveContextWindowSize()` 先从模型配置取得窗口，再扣除摘要输出预留；摘要输出最多按 20,000 tokens 预留。`getAutocompactBufferTokens()` 根据有效窗口选择安全余量：常规窗口使用 13,000 tokens，超过 400K 的窗口使用 30,000，超过 800K 的窗口使用 50,000。最后，`getAutoCompactThreshold()` 用有效窗口减去这段余量，得到主动压缩阈值；测试环境可以通过 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 覆盖比例。

代码还会估算单轮可能新增的内容。`TOOL_RESULT_GROWTH_ESTIMATE` 设为 15,000 tokens，叠加模型输出上限后用于请求前预测。警告和错误状态各保留 20,000 tokens 缓冲，手动压缩的阻塞限制保留 3,000 tokens。这样可以在模型真正返回超限错误前开始处理，给摘要请求和下一轮工具调用留出空间。

#### 压缩触发时机

Claude Code 在主线程每次请求前计算当前 token 使用量，并为模型输出和单轮工具结果预留余量。`autoCompact.ts` 根据有效上下文窗口、输出预留和缓冲区计算阈值；上下文窗口较大的模型会使用更大的安全缓冲。达到阈值时先尝试自动压缩，关闭自动压缩时仍可使用手动 `/compact`。

触发点可以分为四类：

1. **请求前的轻量处理**：`microcompactMessages()` 识别可处理的工具结果。支持缓存编辑的模型会发送 `cache_edits`，在服务端移除旧工具结果；缓存已经失效时，时间触发路径会直接把旧结果替换为 `[Old tool result content cleared]`。
2. **阈值触发的整体压缩**：`shouldAutoCompact()` 判断 token 使用量是否达到阈值，再调用 `compactConversation()`。压缩失败会累计失败次数，连续失败达到三次后停止重复尝试，避免在不可恢复的超长请求上持续消耗 API。
3. **用户主动触发**：`/compact` 和 `/force-snip` 允许用户在任务阶段切换前提前整理上下文。
4. **服务商拒绝后的被动处理**：`reactiveCompact.ts` 识别 `prompt-too-long`，在一次请求链中只执行一次兜底压缩，避免请求失败和压缩失败互相循环。

当 `tengu_session_memory` 与 `tengu_sm_compact` 同时启用时，自动压缩优先读取已经提取的 Session Memory，不再额外调用摘要模型。`calculateMessagesToKeepIndex()` 会在最近历史中保留至少 10,000 tokens 和 5 条含文本消息，并把上限控制在 40,000 tokens；边界随后由 `adjustIndexToPreserveAPIInvariants()` 向前移动，直到 `tool_use`、`tool_result` 以及同一条流式 assistant 消息中的 thinking block 保持完整。这个路径的收益来自复用现有记忆，代价是摘要质量依赖记忆提取阶段。

自动压缩不会对所有消息源递归执行。`session_memory`、`compact` 等摘要子 Agent 会被排除，避免摘要过程再次触发摘要；启用上下文折叠时，折叠专用 Agent 也会跳过自动压缩。这个判断避免多个内部会话共享状态时互相等待或重复修改主线程历史。

#### 各层压缩执行细节

**snip 剪除。** `snipCompact.ts` 以消息 UUID 为单位删除模型已经不需要的历史。它适合去掉大段探索过程、重复的读取结果和用户明确要求忽略的内容。由于动作由模型或用户指定，系统需要记录删除了哪些 UUID，便于界面展示和审计。

**microcompact 微压缩。** `microCompact.ts` 只处理可压缩工具的 `tool_result`，包括文件读取、搜索、Shell、网页读取和编辑等结果。缓存编辑路径先登记工具调用 ID，再根据保留数量选择旧结果，通过 API 的缓存编辑字段删除内容，本地消息列表仍保留原始结构；时间触发路径检测到长时间没有新一轮助手消息时，会直接清空较旧结果的内容，只保留最近结果和占位文本。两条路径都不会把工具调用本身删除，因此模型仍能理解动作与结果之间的关联。

**context-collapse 折叠。** `contextCollapse/operations.ts` 处理代码块等适合引用的长内容，把已经展示过的内容变成可重新读取的占位引用。原始文件仍可通过文件工具访问，主上下文只保留定位信息和必要的修改状态。该层适合重复读取同一文件或大段代码的编码任务。

**autocompact 自动摘要。** `compact.ts` 先运行 `pre_compact` 钩子，再调用摘要模型，生成摘要消息、保留的近期消息和必要附件，最后执行 `post_compact` 清理。摘要阶段会尽量共享主请求的稳定前缀缓存；技能正文、文件状态和计划附件在压缩后按需重新注入，避免把所有已加载内容再次复制到新历史。摘要失败会保留可诊断错误，连续失败由 `autoCompact.ts` 的断路计数停止重复调用。

`compactConversation()` 的内部顺序决定了恢复质量：

1. 统计压缩前 token，并执行 `pre_compact` hooks；界面状态进入 `compacting`。
2. 组装摘要请求，把待压缩历史、摘要指令和必要的稳定上下文发送给摘要模型。
3. 如果摘要请求自身返回 `prompt-too-long`，调用 `truncateHeadForPTLRetry()` 按 API round 删除最早消息，最多执行 `MAX_PTL_RETRIES = 3` 次，再重新请求摘要。
4. 摘要完成后清理文件读取状态和已加载的嵌套记忆，异步生成文件、计划和技能附件。
5. 按 `boundaryMarker → summaryMessages → messagesToKeep → attachments → hookResults` 的顺序构造新的消息列表，并重置旧的摘要消息 ID。

这条顺序保留了三个恢复入口：摘要提供任务背景，`messagesToKeep` 提供最近动作，附件提供文件状态和计划内容。只生成一段摘要会让模型失去最近的工具结果，只保留最近消息又会让早期决策消失。

压缩完成后，Claude Code 会重新建立一部分启动上下文：系统提示词和输出风格继续生效，项目根目录的 `CLAUDE.md`、无路径限制的规则、自动记忆、计划和新的 Git 状态会重新注入；路径规则和嵌套 `CLAUDE.md` 在模型重新访问相关文件时按需加载。最近修改过的文件最多恢复五个，单个文件超过 5,000 tokens 时只保留路径引用；已调用的 Skill 每个最多恢复 5,000 tokens，总量最多 25,000 tokens。后台命令和后台子 Agent 继续运行，匹配 `compact` 来源的 SessionStart hook 也会重新执行。这个重建过程让摘要只承担任务历史，当前项目规则和文件状态由各自的来源提供。

**reactive compact 被动兜底。** 当服务商返回 `prompt-too-long` 时，系统按 API round 分组，从最早的消息组开始删除，最多重试三次。若删除后首条消息变成孤立的 `assistant` 或 `tool_result`，实现会插入边界标记并重新建立消息配对，保证下一次请求仍符合协议。该过程有损，适合解决请求已经无法发送的异常状态，不应替代正常阈值触发。

如果错误响应没有提供可解析的 token 缺口，`truncateHeadForPTLRetry()` 会按消息组的约五分之一删除历史；如果响应带有缺口，则累计最早消息组的估算 token，直到覆盖缺口。删除后首条消息若是 `assistant`，实现会插入一个带 `isMeta` 的用户标记，使消息序列重新满足 API 的首条角色约束。这个兜底路径保留最近消息，牺牲较早历史来恢复可发送性。

#### 缓存与成本优化

Claude Code 的缓存策略围绕“稳定前缀、变化后缀”组织：系统提示词和工具定义尽量保持不变，工具结果以追加消息进入轨迹，压缩只替换较晚的历史。支持缓存编辑时，删除旧 `tool_result` 可以减少需要重算的内容；缓存已经失效时，直接清空工具结果比再次生成摘要更省一次模型调用。

整体摘要本身需要一次额外模型请求，因此只有在摘要能释放足够空间时才值得执行。`compact.ts` 会保存文件读取状态和技能使用记录，压缩后创建附件恢复模型所需的工作状态。系统还会把压缩前后的 token 数量、触发原因和失败次数写入事件，便于比较压缩节省量与任务成功率。

### 3.3 Codex 压缩策略

#### Codex 压缩概述

Codex 将 compaction 视为一次新的上下文窗口检查点。入口 `codex-rs/core/src/session/turn.rs` 的 `run_auto_compact()` 先生成新的世界状态，再根据功能开关和模型提供方能力选择实现：TokenBudget 重置、远程压缩 V2 或本地压缩。

| 实现 | 主要文件 | 压缩动作 | 适用情况 |
| --- | --- | --- | --- |
| TokenBudget | `compact_token_budget.rs` | 直接调用 `start_new_context_window()` | 只需要新窗口，服务端或本地摘要都不需要时 |
| 远程压缩 V2 | `compact_remote_v2.rs` | 把历史交给支持该能力的 Responses 服务，安装返回的压缩项 | 提供方能生成并保存原生 compaction |
| 本地压缩 | `compact.rs` | 用摘要提示调用当前模型，再替换本地历史 | 本地模型或提供方不支持远程压缩时 |

三条路径共享压缩生命周期：执行 `pre-compact` 钩子，记录 `ContextCompaction` 事件，安装新上下文，执行 `post-compact` 钩子，并把触发原因和实现方式写入分析数据。它们的差异集中在“摘要由谁生成”和“历史由谁保存”。

Codex 的实现可以看成“历史层 + 世界状态层 + 窗口计数器”三部分。历史层保存用户输入、模型响应和工具输出；世界状态层保存当前目录、项目指令、权限、工具和连接器状态；窗口计数器记录自动压缩发生的次数和窗口标识。压缩时只替换历史层，重新生成世界状态层，窗口计数器继续递增。这个分层让新窗口拥有当前环境信息，避免摘要承担所有恢复职责。

#### 压缩触发时机

Codex 会在请求前、工具循环中和轮次结束后检查上下文状态。触发原因包括接近模型窗口上限、当前轮需要为新请求腾出空间、服务端返回上下文超限，以及用户手动执行压缩。`run_auto_compact()` 接收 `CompactionPhase`，因此同一套实现可以区分 `PreTurn`、`MidTurn`、`PostTurn` 和独立手动压缩。

TokenBudget 功能打开时，系统直接创建一个新的上下文窗口。远程压缩能力为 `V2` 时，Codex 会优先等待或使用后台候选压缩结果；提供方能力为 `Unsupported` 时，流程转到本地摘要。切换模型或提供方后，重新计算上下文预算，不能沿用旧路由的阈值。

`run_auto_compact()` 在选择实现前先调用 `build_world_state_for_step(..., new_window: true)`，为新窗口准备状态基线。远程 V2 路径还会判断是否存在后台候选压缩结果：候选结果已经足够且当前阶段不要求立即压缩时可以跳过前台请求；上下文确实达到限制时才切换到前台安装。TokenBudget、远程和本地三条路径都遵守相同的取消信号和钩子生命周期，因此用户中断时不会留下半个新窗口。

#### 本地压缩流程

本地实现 `compact.rs` 会把当前历史复制到摘要请求中，并追加压缩指令。摘要完成后，Codex 将旧历史改为摘要项和必要的用户目标，再调用 `build_compaction_replacement_history()` 重新组装前缀、世界状态和压缩后的历史。压缩结果会记录窗口编号、压缩模型哈希、响应 ID 和摘要文本，便于恢复和分析。

本地摘要请求会复用当前模型客户端会话，以保持路由和流式请求的连续状态。摘要生成前，系统把已经执行的工具调用附加到压缩提示中，避免摘要模型把已完成动作误判为待执行动作。摘要输出只接受完整文本；流中断、预算耗尽和取消都会直接结束压缩，并保留原历史供后续恢复。

压缩请求自身也可能超出窗口。实现会从历史开头移除一个项目后重试，同时保留较新的消息；如果只剩一个项目仍然超限，就报告无法压缩。摘要请求使用独立的 `ContextCompactionItem` 标记，正常回答不会把压缩指令当成用户任务的一部分。

本地压缩完成后，Codex 会把摘要放在新的历史尾部，再插入重新生成的初始上下文。`replace_compacted_history()` 同时写入替换历史、下一步的 `StepContext`、世界状态基线和压缩元数据，然后重新计算 token 使用量。恢复后的第一轮请求看到的是一份新的前缀和一个检查点，原始工具调用仍可以从持久化 rollout 中追溯。

#### 世界状态快照机制

Codex 把任务环境中的持久信息从对话历史中抽离出来，以 `WorldStateSnapshot` 保存和重建。世界状态包含项目说明文件、工作目录和环境信息、权限设置、当前模型、工具目录、协作模式以及插件或连接器贡献的上下文片段。压缩历史后，系统重新生成这些片段，再把摘要接到它们之后。

这种设计让“过去发生过什么”和“现在处于什么环境”分开维护。历史摘要可以省略已经完成的读取过程，世界状态仍然提供当前项目规则和可用工具；重新打开会话或进入新窗口时，也能根据快照恢复相同的工作边界。若权限或工作目录发生变化，下一次世界状态渲染会记录增量更新，模型不会继续使用旧状态。

世界状态每个 section 都有自己的 snapshot 和差异渲染函数。首次构造新窗口时注入完整片段，后续步骤根据上一次 snapshot 只追加发生变化的片段；被压缩的历史不会覆盖 section 的快照。这个机制同时减少重复输入和陈旧信息：项目规则、环境变量、权限或工具目录变化时，变化会出现在新的状态片段中；没有变化的 section 继续复用已有上下文。

### 3.4 OpenCode 压缩策略

#### OpenCode 压缩概述

OpenCode 将工具输出处理和会话压缩拆成两个服务。`packages/core/src/tool-output.ts` 的 `ToolOutput.truncate()` 在工具结果进入消息历史前限制大小；`packages/core/src/session/compaction.ts` 的 `SessionCompaction.compact()` 负责在会话接近窗口限制时生成检查点。

第一线（持续）: `ToolOutput.truncate()` 每次工具结果实时截断，完整内容写入 `tool-output/`，消息中保留预览和文件路径。

第二线（兜底）: `SessionCompaction.compact()` 在达到阈值、提供方拒绝请求或用户执行 `/compact` 时整体处理历史。

OpenCode 的实现把“结果大小控制”和“会话语义压缩”放在两个独立服务中。`ToolOutput` 只接收规范化工具结果并返回新的结果对象，`SessionCompaction` 读取会话历史、模型窗口和压缩配置。两者之间通过消息中的预览文本、`outputPath` 和 `metadata.truncated` 连接，工具服务无需知道摘要模板，摘要服务也无需重新执行工具。

#### 压缩触发时机

工具输出服务默认限制 2,000 行和 50 KiB。结果超限时保存原文，并在模型可见内容中添加 `[showing ...; full output saved to ...]` 标记；已经截断的结果不会重复处理。这个操作不需要模型请求，因此适合在每次工具调用后执行。

截断流程先把所有文本块合并计算行数和 UTF-8 字节数，再按行保留前部内容。文件型内容块继续保留，文本块达到预算时插入 marker，最终结果带 `truncated: true` 和 `outputPath`。原文文件按 `tool_<id>` 命名，默认保存七天，并由后台清理任务每小时检查一次。这样模型看到的是可读的前部样本，Agent 仍然可以使用路径读取完整输出。

会话压缩由 `SessionCompaction` 根据模型窗口、配置的 `buffer` 和 `keep` 预算判断。自动压缩关闭时，`manual` 触发仍可执行；模型窗口未知时不会主动按阈值压缩，但收到提供方超限错误后仍会选择一个估算窗口生成恢复请求。超限恢复使用 `SHRINK_STEPS = [0.7, 0.5, 0.35]` 逐步降低目标输入规模，避免每次重试只减少极少内容。

OpenCode 会先用当前会话模型解析压缩 Agent；如果配置了专用的 `compaction` Agent，摘要请求可以走另一条模型路由。工具结果的 `payload-too-large` 错误先尝试把图片和其他媒体改成文本表示，随后才进入按比例缩减历史的路径。模型窗口未知时，自动触发保持关闭，手动压缩和提供方拒绝后的恢复仍然可用。

默认配置中 `keep` 为 15,000 tokens，`buffer` 用于在模型窗口底部预留空间。`due()` 会跳过刚刚完成的压缩，等待下一次请求根据新检查点重新计量；对于已经加密的原生检查点，系统等待服务商返回可测量的 prompt usage 后再决定下一次触发。会话有历史但模型窗口未知时，系统保留手动和错误恢复路径，避免凭猜测自动压缩。

#### 压缩执行细节

普通模型路径会把消息拆成较早的历史和最近 `keep` 词元，向压缩模型追加结构化摘要指令。摘要模板要求模型输出目标、要求、决策、工作状态、下一步、相关文件和重要上下文。压缩完成后，旧历史被一个检查点替换，最近消息以 `recent` 字段保留，下一轮请求从检查点继续。

摘要路径会先识别上一次检查点，再把它和新历史合并成一份更新后的摘要，避免多个摘要消息并列增长。摘要提示要求保留用户目标和约束、已完成与进行中的工作、下一步、相关文件以及恢复所需的重要上下文；模型没有按模板输出时，系统会追加一次 nudge 提示重新请求，仍然没有结构化内容才报告失败。

如果当前模型提供原生 compaction 能力，OpenCode 会调用 `llm.compact()`，由提供方生成 `providerContext`，本地只记录最近用户消息和提供方检查点。普通摘要和原生压缩共享触发、预算和失败处理，但原生检查点只能在产生它的提供方上下文中回放。

工具输出截断与整体压缩之间有明确分工：前者减少单条结果的体积，后者处理多轮历史的结构和任务状态。工具输出保存路径进入检查点后，模型仍可通过文件工具重新读取完整内容，不需要把原始输出重新塞回每轮请求。

原生 compaction 路径的前提更严格：当前模型必须声明原生能力，提供方配置必须能稳定解析，路由重写不能把请求切换到另一个提供方。OpenCode 会把检查点编码为 `providerContext`，只回放到生成它的提供方上下文；不满足条件时转到普通摘要或报告不支持错误。

#### 缓存友好设计

OpenCode 的历史布局尽量保持系统提示词、工具定义和提供方信息稳定，把检查点与最近消息放在动态区域。整体压缩会改变历史中的一个边界，因此缓存需要从该位置重新建立；工具结果先截断可以减少边界移动的频率。

普通摘要将最近消息序列化到检查点，原生 compaction 则保存提供方上下文。两种形式都需要保留任务目标、用户限制和最近动作，否则缓存节省下来的输入会被恢复错误抵消。压缩配置中的 `keep` 应根据任务类型调整：代码编辑任务需要保留最近的文件变更与测试结果，检索任务需要保留最近的来源和未解决问题。

缓存友好的布局还要求工具输出截断尽量早发生。若先把 50 KiB 的日志写入历史，再立即整体压缩，摘要请求会重复读取这段日志；在工具结果进入会话前截断，后续检查点只需保存预览和路径。整体压缩发生时，稳定的系统指令和工具定义位于前部，摘要检查点与 `recent` 位于后部，压缩边界之后的缓存可以重新建立。

### 3.5 DeepSeek Harness压缩策略

#### DeepSeek Harness压缩概述

DeepSeek Harness 将压缩能力拆成一组可组合包，Agent 主循环只负责使用这些包提供的能力：

| 包 | 作用 | 关键接口 |
| --- | --- | --- |
| `@deepseek-ai/dsh-compaction` | 定义压缩事务、摘要和事件的共享约定 | `ctx.compaction` |
| `@deepseek-ai/dsh-compaction-basic` | 按 token 压力压缩旧历史并恢复超限请求 | `BasicCompactionEngine` |
| `@deepseek-ai/dsh-compaction-tool-result-pruner` | 在摘要前修剪超大工具结果 | `ctx.toolResultPruner` |
| `@deepseek-ai/dsh-command-compact` | 提供手动 `/compact` | `ctx.commands` |
| `@deepseek-ai/dsh-compaction-image-offload` | 把超预算图片替换为可追溯占位文本 | 请求错误监听器 |

这种拆分把“什么时候需要空间”“怎样选择历史范围”“怎样生成摘要”“怎样处理特殊内容”分别抽象出来。Agent 主循环只消费压缩服务提供的结果，不需要知道摘要模板和工具结果修剪的具体实现。

DeepSeek Harness 的持久模型也分成两层：session event log 采用追加写入，记录 `compaction/start`、`compaction/summary`、replacement 和 `compaction/end`；当前 surface 通过 replacement 隐藏已经压缩的节点，模型下一轮只看到新的检查点和保留尾部。这样既能回放完整事件，又能让输入视图保持短小。

DeepSeek Harness 的核心抽象是“压缩能力接缝”。`@deepseek-ai/dsh-compaction` 规定范围选择、工具配对、摘要结果和事件的共同数据结构；基础包通过 `ctx.llm`、`ctx.session` 和 `ctx.tokenMeter` 使用这些能力。摘要器可以是默认的 LLM 摘要器，也可以由其他插件提供，主循环不需要更改消息处理代码。

#### 压缩触发时机

自动模式由 `agent/pre-step` listener 检查最近一次路由请求的 token 使用量。配置包含 `thresholdRatio`、`headroomTokens`、`retainRatio` 或 `retainTokens`，默认阈值近似为：

```text
threshold = floor(min(W × thresholdRatio, W - O - headroomTokens))
```

达到阈值后，系统先调用可选的工具结果修剪器；修剪后已经回到预算范围时，直接结束本轮，不发起摘要请求。仍然超出预算时，选择最早且不破坏工具调用—结果配对的历史范围，生成整体摘要。压力判断使用最新一次持久路由请求的 provider/model 和输出预留，模型切换后会重新解析对应策略；按模型覆盖项可以分别设置摘要模型、阈值、保留量和重试次数。

提供方确认 `CONTEXT_WINDOW_EXCEEDED` 后，错误恢复路径会绕过普通阈值，尝试一次更大的历史缩减，再重试原请求。用户输入 `/compact` 时可以在未达到阈值的情况下手动执行；压缩与 Agent 轮次串行，正在执行工具时手动命令会等待当前轮次结束。

默认策略以 `thresholdRatio = 0.8`、`headroomTokens = 65,536`、`retainRatio = 0.16` 计算压力。`retainRatio` 会作用于扣除输出预留后的窗口，系统也允许按模型配置绝对的 `retainTokens`。两种保留方式不能同时设置，保留预算必须小于实际触发阈值；摘要 `maxTokens`、普通压缩重试次数和超限恢复重试次数也属于模型策略的一部分。

#### 压缩执行细节

`selectCompactableRange()` 从系统消息之后的第一条历史开始选择范围，保留最近一段逐字消息，并向前移动边界直到工具调用与工具结果处于平衡状态。这样可以避免摘要后的消息列表出现孤立的 `tool_result` 或缺少对应动作的结果。

范围选择会先验证 token meter 的 surface 与 Session 当前 surface 完全一致，再从尾部累计保留预算。边界落在未闭合的工具调用组内时，算法继续向前移动，直到 `toolPairingBalancedBefore()` 返回平衡。系统消息位于 surface 的第 0 个节点时永远留在压缩范围之外；后续追加的普通 `system/message` 可以随历史一起折叠。没有足够历史可压缩，或保留尾部已经覆盖全部历史时，函数返回 `null`，系统跳过摘要。

摘要请求会回放当前系统消息、工具声明和待压缩历史，然后把压缩指令作为最后一条用户消息追加。该布局让摘要请求复用最近一次路由请求的稳定前缀；摘要返回后只提取文本，图片和工具调用输出会被拒绝，避免把不可回放内容写入检查点。摘要内容以 `<compacted-summary>` 标签包裹，并和 `compaction/start`、`compaction/summary`、`compaction/end` 事件一起持久化。

默认摘要提示要求模型输出固定检查点结构：原始目标与意图、关键技术概念、文件与代码、错误与修复、待处理工作、当前工作、下一步和关键上下文。摘要调用携带当前工具历史和 `purpose: compaction`，模型输出中的推理和工具调用不会进入最终检查点，只提取文本块。摘要前导告诉下一轮模型把检查点当作已经建立的背景，继续处理后续消息。

压缩事务在摘要前记录范围和活动锁，摘要完成后再次确认历史没有变化，再提交检查点。摘要失败会写入错误事件并结束事务；范围在等待期间发生变化时不会把旧摘要写回新历史。配置解析也在插件加载时完成，未知字段、冲突的保留配置或无效 token 数会直接报告错误。

事务的持久化顺序是 `compaction/start → compaction/summary → replacement → compaction/end`。`start` 记录压缩 ID、轮次归属和可选命令 ID，形成活动锁；`summary` 保存摘要原文、摘要模型、token 使用和源范围；replacement 把摘要消息放回会话 surface；`end` 记录成功或错误。摘要失败、取消或关闭失败都会留下可诊断事件，下一次调用会先检查未闭合的事务，避免并发覆盖历史。

#### 插件化设计优势区间

插件化结构适合以下场景：

1. 同一个 Agent 框架需要服务不同上下文窗口和不同模型路由，可以用 `modelPolicies` 为提供方和模型设置独立阈值、保留量与摘要模型。
2. 工具结果、图片、会话摘要和手动命令需要分别替换，系统可以按部署需要挂载对应包。
3. 需要比较“只修剪工具结果”“修剪后再摘要”“直接整体摘要”三条路径时，每个组件都可以单独启用并记录 token 变化。
4. 需要替换摘要器时，只实现 `summarize()` 接口即可，压力计算、范围选择、稳定性检查和事件事务仍由基础包负责。

插件化并不会自动解决摘要质量问题。它只把触发和执行边界写清楚；摘要模板仍需要根据任务类型保留事实、来源、失败原因和待办，token 预算也需要结合真实模型请求测量。

**四个实现的共同骨架。** Claude Code、Codex、OpenCode 和 DeepSeek Harness 的代码组织不同，压缩过程都可以拆成下面六个阶段：

| 阶段 | Claude Code | Codex | OpenCode | DeepSeek Harness |
| --- | --- | --- | --- | --- |
| 计算压力 | `autoCompact.ts` 估算 token 和单轮增长 | turn 与 context window 状态 | `due()` 和模型窗口 ceiling | `tokenMeter` 定价当前 surface |
| 选择范围 | 工具结果、代码块、API round | 历史项与最近窗口 | older / recent 消息拆分 | `selectCompactableRange()` 保持工具配对 |
| 生成检查点 | `compactConversation()` | 本地摘要或远程 compaction | 摘要模板或 `llm.compact()` | `summarizeWithLlm()` 或插件摘要器 |
| 恢复状态 | 文件、技能、计划附件 | `WorldStateSnapshot` | `recent` 或 `providerContext` | 事件日志与 replacement surface |
| 失败处理 | PTL 重试、reactive compact、失败计数 | 历史前移重试、取消传播 | shrink steps、nudge、提供方错误 | 稳定性检查、事务关闭、超限重试 |
| 缓存处理 | cache edits 和稳定前缀共享 | 新窗口重建前缀 | 工具结果提前截断 | 摘要指令追加到稳定前缀之后 |

这张表也说明了设计取舍：结果截断减少单次请求成本，局部删除减少历史噪声，整体摘要恢复跨阶段任务状态，新窗口或远程检查点减少本地摘要负担。系统应根据模型能力、任务时长、原始材料大小和提供方协议选择组合，不应把一个实现的行为推断到其他实现。

## 4. 压缩策略最佳实践

压缩前先定义任务状态和原始产物的存储位置。上下文消息只承担当前决策，事件日志承担恢复与审计，文件或对象存储承担大结果和原文。三者职责清晰后，压缩可以只替换消息视图，不会破坏历史记录。

| 实践 | 执行规则 | 验收方式 |
| --- | --- | --- |
| 低成本操作优先 | 先截断超大工具结果，再处理重复消息，最后生成整体摘要 | 统计每层释放的 token 与额外请求数 |
| 保留精确事实 | 文件路径、URL、哈希、ID、时间、数值、失败错误码逐字保存 | 从检查点恢复后再次调用工具，标识符仍可用 |
| 保留任务关系 | 摘要同时写明目标、动作、结果、来源和下一步 | 新模型能解释结果服务于哪个目标 |
| 原始材料外置 | 全文、日志、图片和网页写入带版本的产物路径 | 根据路径可以重新读取和核查原文 |
| 状态独立维护 | 阶段、待办、权限、工作目录、预算不依赖聊天历史推断 | 压缩或重启后状态字段仍一致 |
| 工具调用成对处理 | 压缩范围不能拆开 assistant tool call 与 tool result | 消息协议检查通过，模型不会重复或误配调用 |
| 稳定前缀优先 | 系统规则、工具定义和固定示例保持稳定，动态信息追加到末尾 | 监控 Prompt Cache 命中与首词时延 |
| 失败可恢复 | 保存压缩前后 token、触发原因、摘要版本和重试次数 | 模拟超限、取消和摘要失败后能继续任务 |
| 压缩结果可审计 | 记录摘要覆盖的消息范围和原始产物引用 | 可以回答“这条结论来自哪次操作” |

摘要模板建议固定字段，避免每次压缩都改变结构。下面的字段适用于编码、检索和产品文档任务：

```text
目标：用户要完成什么，范围是否发生变化
已确认事实：带时间、数值、来源和状态
关键决策：采用或放弃了哪些方案，原因是什么
已执行动作：工具、文件、接口和结果
失败与限制：错误、权限、网络、尚未验证的假设
当前状态：阶段、已完成项、进行中项目、待办
原始产物：文件路径、URL、对象 ID、版本或哈希
下一步：恢复后应执行的第一项动作
```

压缩触发量可以用三组数据共同评估：输入 token 减少量、压缩额外请求成本、任务恢复后的成功率。只看压缩比例会掩盖摘要错误；只看缓存命中又可能忽略模型重复调用。至少需要记录压缩前后 token、摘要耗时、缓存命中、失败重试、重复工具调用和用户重新说明次数。

任务类型会影响保留策略。代码修改任务重点保留文件路径、变更内容、测试命令和失败日志；检索任务重点保留来源、发布日期、事实和冲突结论；规划任务重点保留约束、决策、依赖和待确认事项。对于包含大量探索材料的任务，优先使用子 Agent 隔离中间过程，主 Agent 只接收结构化结果，可以减少压缩发生的频率。

不要把压缩摘要当作新的永久知识。跨任务经验需要经过独立评估后写入项目文档、知识库或记忆系统；当前任务的检查点只服务于当前会话恢复。压缩完成后，继续让模型读取原始产物并核查关键事实，能够及时发现摘要中遗漏的限定条件。
