# RSI 设计

## 1. 从一次「改完了但没变好」说起

一个团队给 Agent 加了一条新规则：「遇到测试失败时，先检查是不是环境问题再重试」。规则来自一次真实的排查经历，写得也很具体。

上线两周后，这类任务的通过率没有变化。进一步看：规则确实被加载了，但在多数失败案例里，模型读到它之后仍然直接重试；少数遵守了它的案例，也没有因此变好——因为那些失败确实不是环境问题。

这次更新失败的原因不在规则本身，而在三个环节都没做完：没有可靠的信号判断「这次失败是什么类型」，没有区分「规则没被加载」与「加载了没遵守」，也没有用未参与提炼的任务验证「是否真的改善」。

持续进化（Recursive Self-Improvement，下称 RSI）要解决的就是这三件事：从哪得到信号、更新到什么载体、怎么验证。

## 2. 学习信号的三层

判断一次运行为什么成功或失败，要依次回答三个问题。

**事情是否办成了。** 结果验证读测试结果、数据库状态、接口返回。Coding Agent 可以跑测试、类型检查、基准；替用户办退款的 Agent 可以查订单状态与实际退款金额。这类信号来自环境的真实状态，比模型对自己行为的描述可靠，应优先建立。

**是否以允许的方式办成。** 过程验证检查业务规则、权限、动作序列。删掉失败的测试也能让测试通过；口头承诺「七天内退款」也可能得到暂时满意的反馈。这一层区分「结果达成」与「结果以允许的路径达成」。

**是否让用户舒服。** 质量验证评表达、耐心、是否抓住重点。这些维度不影响事情办成与否，但影响体验。可用量表加模型评分，要求逐项给分并引用轨迹证据。

三层的可靠性与成本都递增。第一层可以用代码判定，第二层需要策略库，第三层只能靠评分模型。工程上的顺序应当是从下往上建，因为上层依赖下层的结论。

### 验证器必须输出什么

只给一个总分的验证器无法指导更新。它说不清「该改知识、改提示词、改程序，还是改参数」。一个可用的验证结论至少包含四项：

| 项 | 内容 | 缺了会怎样 |
| --- | --- | --- |
| 结论 | 成功、部分成功、失败 | 只有二分，部分成功案例被误判 |
| 逐维度判断 | 每个检查项各自的结论 | 无法定位该改哪一层 |
| 证据位置 | 第几轮、哪次工具调用 | 无法复核，也无法做失败归因 |
| 失败类型 | 分类标签 | 无法聚合同类失败，只能逐条看 |

还要允许一件事：证据不足时拒绝评分。与其把低置信度结论当作事实固化下来，不如把该案例排除在学习集之外。

## 3. 四种更新载体

学习信号说明「应当改变」，没说明「改在哪里」。四种载体的适用面不同。

<iframe src="/diagrams/rsi-carriers.html" title="四种更新载体的适用范围" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/380;border:0;display:block;margin:24px 0;"></iframe>

**知识文档**承载事实、经验规律、例外与来源。更新快、可追溯、可按需检索。失效模式是依赖检索命中——写进去了但没被取回，等于没写。

**提示词与 Skill**承载能用自然语言说清的判断原则，含例外与优先级。可解释、作用范围可控。失效模式是膨胀与互相冲突——规则越多越难同时满足。

**程序与框架**承载可解析、可验证的硬约束：权限、路径、格式、必须成对的操作。可测试、执行稳定、成本低。失效模式是开发维护成本高，且僵化——把需要判断的事写成代码，模型失去变通空间。

**模型参数**承载高维感知、生成风格、隐式策略。泛化强、推理开销低。失效模式是更新与回归成本最高，且容易灾难性遗忘。

选错载体的两种典型表现：把硬约束写成原则（拦不住），把判断原则写成代码（僵化）。

同一能力常常要拆到多个载体。以第 1 节那个例子为例：判断「这次失败是不是环境问题」需要领域知识（进知识文档），需要判断原则（进 Skill 的例外条款），而「测试失败后必须先查环境再重试」如果可以被代码强制，就写进工具的执行顺序，别放提示词。

## 4. 五个搜索尺度

除了「改哪个载体」，还有一条正交的轴：优化的对象是产物本身，还是产生产物的方法。

<iframe src="/diagrams/rsi-scales.html" title="五个搜索尺度与外层成本" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/340;border:0;display:block;margin:24px 0;"></iframe>

从内到外：单条规则或记忆 → 结构化上下文 → 工作流 → 框架代码 → 优化器代码。

越往外，单次验证越贵，可归因性越差，但改进的杠杆越大。

最内层只改内容：给提示加一条规则、给文档补一个例外。作用面小、容易归因与回滚，应当是默认选择。

第二层改的是「上下文怎么被构造」：检索规则、过滤条件、格式化方式。改一条检索规则是在改内容管理机制。

第三层改工作流：节点组合、控制流、并行度。

第四层改框架代码：存储、检索、呈现的代码。这一类搜索的候选是「框架版本」，验证靠整体分数与轨迹。

第五层改的是优化器本身：探索策略、候选选择、停止时机。这一层的反馈成本最高，因为它的好坏要经过很长的生成与评估链条才显现。

有一条实用的判断：**如果内层改得动，就不要往外走**。外层搜索的收益通常被它的验证成本吃掉。

外层搜索有一个绕不开的问题：每个候选策略都要重新跑 Agent 和评估器。一个可能的缓解是把已完成的发现过程保存下来，作为可回放的模拟器：根节点是初始状态，子节点保存从某个历史状态继续尝试后的结果与分数。候选策略与在线时用同一套接口逐步选择节点或开新分支，离线阶段只揭示已记录的结果，不必重跑。

这类回放成立需要两个条件：在线与离线使用相同的决策接口；只向策略揭示当前已展开的子树（不能偷看未来）。它能比较分支、顺序、并行批次与停止时机，但不能证明在旧树上得分更高的策略能迁移到新任务。

## 5. 双循环

四种载体与五个尺度只有进入同一个循环才成为持续进化。稳妥的结构是两个循环。

<iframe src="/diagrams/rsi-double-loop.html" title="在线执行与离线进化的双循环" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/340;border:0;display:block;margin:24px 0;"></iframe>

**在线循环**只完成任务并记录证据，不直接改写正式版本。这一条是硬约束：一次偶发成功、一次网络故障、一次恶意输入，都不应该立刻改变长期能力。

**离线循环**聚合轨迹、诊断根因、生成提案、过发布检查、发布新版本。

两个循环通过版本化的经验库与评估集连接。评估集在这里承担发布检查的职责——没有它，离线循环无法判断一个提案是否值得上线。

把记录与整理分开还有一层好处：离线可以用更大的批量与更便宜的模型，因为它不在关键路径上。

## 6. 提案的收益判定

一个提案值不值得上线，可以写成一个简单的判定：

$$
g = \Delta_{\mathrm{r}} - c_{\mathrm{u}} - c_{\mathrm{g}}
$$

其中 $\Delta_{\mathrm{r}}$ 是保留集上的增益，$c_{\mathrm{u}}$ 是更新成本（一次额外的模型调用、一次人工审核），$c_{\mathrm{g}}$ 是回退风险的折算成本。

只接受 $g > 0$ 且保留集无回退的提案。

这个式子的第二项常被忽略。一个提案即使增益为正，如果它要求每次任务都多一次模型调用，长期成本可能超过收益。所以「零增益但有负成本」的提案（例如把一段提示词从系统提示移到 Skill 正文）同样有意义。

第三项最难量化。可行的替代是设一条硬规则：保留集上任何一项指标退化的提案一律拒绝，不管总增益多少。这条规则牺牲了「用一项退化换两项提升」的可能性，但它把回退风险压到了零。

## 7. 失败模式

**只追加不淘汰。** 症状：规则越来越多，互相冲突，模型在不同规则间摇摆。成因：更新只做加法。修法：每次提案必须声明它替代或废除了哪些旧内容。

**摘要代际漂移。** 症状：几轮整理后，早期的重要限定条件消失。成因：只在摘要之间互相改写，不回到原始证据。修法：定期整理必须读原始材料。

**把探索性讨论固化为规则。** 症状：某次对话里的方案比较被写成「必须这样做」。成因：抽取时没有区分「讨论过」与「验证过」。修法：提案必须带证据类型标签，只有「验证过」的才能进正式规则。

**无保留集导致过拟合。** 症状：在评测集上分数持续上升，真实使用没有改善。成因：评测集被反复用来调参。修法：划出保留集，只在发布前评测，不参与任何调优决策。

四条里，第四条最容易发生，因为它不会报错，只是在几个月后表现为「指标好但用户抱怨」。
