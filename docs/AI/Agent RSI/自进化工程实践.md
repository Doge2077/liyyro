# 自进化工程实践

## 1. 同一个失败的四条路径

某个内部接口总被误用：模型习惯直接调用 `POST /orders`，而正确做法是先调 `POST /orders/draft` 再提交。

四家 Coding Agent 面对这个问题，进化的路径完全不同。Claude Code 会在会话中观察到这个反复出现的错误，把它抽成「直觉」，达到阈值后生成一个 Skill；Codex 要等这批轨迹冷却，再经过两阶段管线并入记忆摘要；OpenCode 什么都不会发生，除非有人把这条约定写进指令文件；DeepSeek Harness 也不会发生，除非有人写一个插件在调用前做检查。

四条路径的差别不在能力，在「学习发生在哪个时刻」。

## 2. Claude Code

### 信号来源

观察事件分五类：用户消息、助手消息、工具开始、工具完成、工具错误。每类事件带一个结果标记（成功、失败、未知）。

这个粒度值得注意：它记录的是「动作与其结果」，不是「对话内容」。这让后续的归纳能落到具体行为上，而不只是文本相似度。

### 载体：直觉

中间产物叫「直觉」——一条从观察中提炼出的判断，带领域分类与置信度。领域分七类：工作流、测试、调试、代码风格、安全、版本控制、项目。

分类的作用是路由：不同领域生成不同前缀的 Skill 名，避免所有生成的 Skill 都叫「learned-skill」。

### 状态机

直觉有七种状态：待定、活跃、陈旧、被替代、退役、归档、冲突挂起。

七种状态里最有价值的是最后一种。冲突挂起表示「这条直觉与已有的某条矛盾，需要人裁决」，它阻止了系统在未裁决的情况下用新直觉覆盖旧直觉。

这个设计的实际含义是：系统承认自己可能得出矛盾结论，并把裁决权交回给人。

### 晋升条件

从直觉到 Skill 不是自动的，要满足两个条件：

第一，跨项目数。同一条直觉在多个项目里被观察到，说明它不是某个项目的特例。

第二，平均置信度。默认阈值 0.75，低于此不生成。

两条都过才生成 Skill。生成产物有三种形态：Skill、Agent、命令。选哪种取决于内容的形状——流程性强的生成 Skill，需要独立上下文的生成 Agent，短动作生成命令。

### 生命周期与回退

Skill 生成后进入生命周期管理：使用统计、陈旧判定、退役。这些状态让它能被降权而不必删除。

### 我的评价

这套设计的完整度是四家里最高的：从观察到晋升到退役，每一环都有明确的数据结构与状态。

代价也在完整度上。三个产物类型、七种状态、七个领域，加在一起是一套需要维护的模型。如果只用其中一部分（例如只做 Skill 不做 Agent），仍要承担全部状态机的复杂度。

另一处代价是反馈延迟。观察事件是即时的，但晋升要等多项目证据，这个等待可能长达数周。对「这个接口总被误用」这类问题，等不起。

## 3. Codex

### 信号来源

轨迹加使用统计。轨迹提供「发生了什么」，使用统计提供「哪些记忆被用过」。

后者是它相对独特的地方：一条记忆被取回几次、最近一次什么时候用，都进状态库。这让「30 天未使用不入选」这类规则成为可能。

### 载体：手册加摘要加技能

三层分得清楚：摘要是每轮注入的跨任务信号，手册是可检索的操作层，技能是可执行的流程。

三者的更新频率不同：摘要每次整合重写、手册按块更新、技能独立演进。

### 流程：两阶段

阶段一按轨迹抽取，产出详细记忆、摘要、标识。阶段二全局整合，把多份摘要合并成手册与摘要。

两阶段的分离理由前文说过：抽取可并行，整合必须串行。

### 批准与回退

批准的位置在「整合前看工作区差异」。系统生成差异文件，整合子代理读它定位改动；人可以在合并前审阅这个差异。

回退靠 git 基线重置。这是这套设计里最实用的一处：任何一次整理都能回到上一个已审核状态。

### 我的评价

这套设计的强项在可回滚与可审计：差异即记录，git 即版本。

弱项在延迟：6 小时空闲加 10 天窗口，意味着一条教训最快也要几小时才可能被抽取，再等到下次整合才进入摘要。对需要即时纠错的问题，这个延迟不可接受。

另一处弱项是对「删除」的处理依赖文本匹配：删除一份摘要后，要按文件名、路径、线程标识去手册里搜引用。这个搜索是启发式的，漏掉一处就会留下失效引用。

## 4. OpenCode

### 信号来源

没有运行时观察。系统不记录「模型做错了什么」，也不做归纳。

### 载体与时机

进化发生在构建期：插件与指令文件在打包时定稿，运行时不改。

`effect` 层让插件装配成为编译期的事，配置在启动时解析。所以「自修改」在这里指改代码并重新构建，不是会话中的自我调整。

### 我的评价

这个选择让系统完全可测：同样的代码与配置，行为可复现。代价是没有积累——所有经验必须由人在构建前写进去。

对开源项目这是合理默认：使用者众多、场景差异大，自动积累的经验容易变成噪声。对长期单人的高频使用，积累的损失明显。

## 5. DeepSeek Harness

### 信号来源

同样没有内置学习。但它把「能力」全部外置成插件，这带来另一种进化形态：组合。

### 载体：插件、扩展、钩子

工作流、团队、钩子、扩展都是可挂载的包。进化等于「换一套装配」，靠改提示词做不到。

### 时机

装配期。配置在启动时解析，运行时不自我修改。

### 我的评价

这套设计的价值在于它把「进化」定义成「可替换」，不依赖自我修改。一个能力不行，换一个实现；一组行为不对，改装配。

代价是进化的主体是人：系统本身不会提出「我该换个工作流」这样的判断。

这个定位与它的使用场景匹配：作为框架，它提供的是组合能力，不含自主进化。

## 6. 三条判断

### 信号可得性决定上限

能观察到什么，决定了能学什么。四家的差异首先在这一层：

| 家 | 观察对象 | 可学的内容 |
| --- | --- | --- |
| Claude Code | 动作与结果的事件 | 行为模式、成败归因 |
| Codex | 轨迹 + 使用统计 | 任务经验、记忆效用 |
| OpenCode | 无 | 无（构建期） |
| DeepSeek Harness | 无 | 无（装配期） |

前两家能学「模型做错了什么」，后两家只能学「人愿意写什么」。这个差别无法用算法弥补。

### 审批位置决定速度

审批放在哪一环，决定了进化的速度与风险。

- 生成即上线（无审批）：最快，风险最高。
- 生成后人工审（Claude Code 的冲突挂起、Codex 的差异审阅）：慢一些，可控。
- 只允许构建期改（OpenCode、DeepSeek Harness）：最慢，完全可控。

有一点容易忽略：审批位置与「谁能撤销」是两件事。一个审批宽松但可回滚的系统，可能比审批严格但不可回滚的系统更安全。

### 回滚能力决定敢不敢自动化

能不能回滚，决定了系统敢不敢把审批放宽。

Codex 的 git 基线让它可以自动整合（因为能回退）；OpenCode 的版本控制让它根本不需要运行时回滚（因为不自动改）。

反过来，一个没有回滚路径的系统，无论如何都应当把审批做严——因为错了没法改。

## 7. 外部参照

四家之外，有几个公开做法值得对照。它们不改变上面的判断，但补上了几个我们还没覆盖的机制。

**Voyager 里的三件套。** 自动课程（决定下一步学什么）、技能库（把成功程序保存为可组合代码）、迭代提示（把错误带回下一轮）。三件缺一不可：只有技能库而没有课程，不知道下一步学什么；只有反思而没有环境验证，技能库会积累错误；只有探索而没有持久化，每次任务都从头开始。

**ACE 里的条目化上下文。** 不每轮重写整份上下文，改为维护带稳定标识符的条目集合，由生成、反思、整理三个模块提出增量更新，再用确定性逻辑合并与去重。这解决了一个具体问题：反复重写会丢细节，而增量更新不会。

**MCE 的内外双循环。** 内层在给定管理方法下优化当前任务的上下文产物，外层根据多轮结果修改搜索、选择、过滤、格式化这些操作本身。这个区分与第 4 节讲的五个尺度对应。

**AFlow 与 Meta-Harness 的代码搜索。** 把工作流表示为代码图，通过执行反馈搜索节点与控制流的组合；让 Coding Agent 读待验证版本的源码、分数与轨迹，搜索决定信息如何存储、检索和呈现的代码。

**Dream-RSI 的发现树回放。** 把已完成的发现过程存成树，当作离线评估环境。在线与离线用同一套决策接口，离线只揭示已展开的子树。这让策略可以在不重跑底层 Agent 与评估器的前提下被比较。

五个做法有一个共同点：它们都把「评价」放进了循环，没放在循环之后。这与第 6 节的第三条判断一致——回滚与评价能力，决定了自动化能推到哪一步。
