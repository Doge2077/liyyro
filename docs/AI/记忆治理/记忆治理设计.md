# 记忆治理设计

## 1. 从一次跨周任务说起

上周的会话里，你确认了三个竞品的核心能力、纠正了模型对"会议纪要"字段的理解、发现某个接口在测试环境里一直超时。这周新开会话，问同一件事，模型重新问了一遍、重新搜了一遍、重新踩了同一个接口。

问题不在模型能力，而在于这三次对话之间没有任何东西被留下来。上下文工程解决的是"这一次请求怎么组装"，状态栏解决的是"当前状态怎么投影成消息"，压缩解决的是"历史变长时怎么换视图"。这三件事的视野都在一次任务之内。任务结束后，事件日志还在磁盘上，模型却看不见它。

记忆治理处理的就是这一段：把跨会话仍然有价值的东西挑出来、存下来、在需要时取回、在失效时清理。它包含四件事：

- 判断什么值得留；
- 选择用什么形式留；
- 决定下次怎样取回；
- 规定怎样变旧和下线。

## 2. 四种持久化机制的分工

谈到"记住东西"，很容易把几件不同的事混成一个"存储"问题。实际上一个 Agent 运行环境里通常同时存在四种持久化机制，它们的写入者、保存内容与失效方式都不一样。

| 机制 | 写入者 | 保存内容 | 失效方式 | 谁读它 |
| --- | --- | --- | --- | --- |
| 上下文消息 | 运行时每轮组装 | 这一轮要发给模型的内容 | 每轮重建 | 模型 |
| 事件日志 | 系统自动追加 | 发生过的一切，只增不改 | 基本不失效 | 恢复、审计、追溯 |
| 状态投影 | 运行时按规则计算 | 当前阶段的结论字段 | 每轮重算或按事件更新 | 运行时判断与模型 |
| 长期记忆 | 智能体或后台管线 | 跨任务可复用的结论 | 整理、降权、过期 | 后续任务的模型 |

这张表的作用是确定责任归属。用户说"你记错了"，系统需要知道去改哪一层：改消息没用，下一轮就重建了；改日志是篡改证据；改状态投影只能影响当前任务；只有改记忆才能影响未来。

反过来说，当用户抱怨"你怎么又忘了"，也要先判断是哪一层出了问题。如果信息只写进了日志而从未进入记忆，那是提取环节缺失；如果写进了记忆但没被取回，那是检索环节的问题；如果取回了但被模型忽略，那是提示词与信任级别的问题。三种症状看起来一样，修的地方完全不同。

这套分工还解释了为什么"把所有对话存进向量库"不是记忆治理。向量库解决的是"怎么找"，不解决"该不该写"和"什么时候该删"。前面两种机制（日志与投影）都已有成熟的工程做法，记忆这一层缺的正是判断。

## 3. 记忆类型与生命周期

分类的价值不在分类本身，而在于每一类对应不同的写入条件、不同的过期规则、不同的信任级别。

| 类型 | 内容 | 写入条件 | 过期规则 | 取回后的信任级别 |
| --- | --- | --- | --- | --- |
| 工作记忆 | 当前任务状态、近期工具结果 | 任务进行中自动积累 | 任务结束即失效 | 高，但仅限当前任务 |
| 情节记忆 | 某次任务发生了什么 | 任务结束、有可复用经验 | 按时间衰减 | 中，需要核对细节 |
| 语义记忆 | 稳定的事实与项目背景 | 有来源支撑、多次确认 | 按版本与最近验证时间 | 中，涉及代码位置需核对 |
| 偏好记忆 | 用户习惯与协作方式 | 用户明确陈述或反复纠正 | 新偏好覆盖旧偏好 | 高，可直接改变行为 |
| 反思记忆 | 失败教训与策略修正 | 失败被归因、可在类似场景复用 | 工具或环境升级后失效 | 低，只作为策略提示 |

信任级别的差异很关键。偏好类记忆可以直接改变输出格式，因为它是用户的显式意图；语义类记忆要求模型在使用前核对当前状态，因为项目事实会变；反思类记忆只能提示"上次这条路走不通"，不能当作当前环境的结论，因为工具版本可能已经变了。

Claude Code 在这一点上做得比较明确：它把记忆限定为四类——用户的角色与偏好、用户对工作方式的反馈、代码与提交历史推不出来的项目进展、外部系统的位置指引——并且专门写了一段"不要在记忆里保存什么"，明确排除能从当前项目状态推导的内容。这条排除规则在用户明确要求保存时同样生效：如果用户说"帮我记住这周的 PR 列表"，系统应当反问"这里面哪一点是出乎意料的"，只有那一部分值得留。

这个细节值得单独拎出来：**排除规则比收录规则更省成本**。把代码结构、调试结论、提交历史写进记忆，等于在代码库之外维护第二份事实，而第二份事实没有编译器和测试来保证它是对的。它会安静地过期，然后在某次任务里被当成事实引用。

## 4. 写入判据

一条候选信息要进入长期记忆，需要同时满足四条：

- **稳定**：下周还成立。临时路径、一次性报错、某次运行的耗时数字不满足。
- **可复用**：未来的相似任务会用到。只对当前任务有用的中间结论不满足。
- **有来源**：能指回产生它的那次操作。凭印象归纳的"用户似乎喜欢表格"不满足。
- **已授权**：用户允许保存，且不含敏感信息。密钥、令牌、内部地址永不满足。

四条里最难落实的是"有来源"。它要求记忆对象带一个可回溯的指针：哪次任务、哪条消息、哪个文件。这个字段在正常使用时几乎不产生价值，但出错时是唯一的救生索——当一条记忆导致错误回答，只有能回到来源才能判断是提取错了、还是当时的事实本身就变了。

Codex 的写入提示词里有一句自检，值得照搬：

> 我会不会因为写了这条记忆，而让未来的智能体做得更好？

如果答案是否定的，就不要写。它同时给了几种应当返回空的情形：一次性的随机提问、没有结论的状态更新、应当重新查询的临时指标、常识、没有任何新证据的探索性讨论。允许"什么都不写"是一个重要设计——如果每次任务结束都必须产出记忆，系统会为了填满配额而制造噪声。

Codex 另一条经验是把提取过程分成三个阶段。先在轨迹上做结构化抽取，产出一份详细记忆、一段摘要和一个标识；再由一个独立的整合步骤把多份摘要合并成手册与索引。第一阶段可以并行，第二阶段必须串行，否则同一份产物会被并发改写。这个分工在后面《记忆工程实践》里展开。

## 5. 存储结构与单条记忆的字段

记忆的存储形式有两层选择：整体结构怎么组织，单条记忆怎么表示。

整体结构上，几乎所有的成熟实现都收敛到"轻量索引 + 若干主题文件"：

```text
memory/
├── MEMORY.md          索引：每条一行，指向主题文件
├── user_role.md       主题：用户的角色与职责
├── feedback_testing.md  主题：对测试方式的要求
├── project_release.md   主题：发布流程的进展与坑
└── logs/2027/03/2027-03-14.md  按日追加的原始记录
```

索引每轮注入，主题文件按需展开。这样做的理由在下一节展开。这里先记一个约束：索引必须是索引，不能是正文。一旦有人往索引里塞内容，它就同时承担了索引和存储两个职责，行数上限会迅速被撑破。

单条记忆的表示有两种极端。一种是最小事实卡片，一条只记一件事，检索精确但丢失关联；另一种是完整段落，保留叙事但冗余严重。工程上常见的折中是"结构化卡片 + 叙事背景"：既存字段化的属性，也存一段说明这条信息是在什么场景下得到的。后者解决了一个具体问题——同一条信息在不同关系下含义不同，"张医生"可能是用户自己的牙科医生，也可能是用户父亲的医生，只靠键值对无法区分。

一条记忆至少要带这些字段：

```json
{
  "type": "preference",
  "scope": "private",
  "subject": "user:liys05/project:liyyro",
  "content": "技术文章用中文写，多方案对比用表格。",
  "source": {
    "task": "tr_20270314_02",
    "message_index": 7
  },
  "confidence": 0.92,
  "verified_at": "2027-03-14T10:20:00+08:00",
  "supersedes": null
}
```

`scope` 决定谁能看到，`source` 决定能否追溯，`confidence` 与 `verified_at` 决定排序与过期判断，`supersedes` 记录替代关系。少任何一个，后续的整理与冲突处理都会失去依据。

## 6. 整理与失效

记忆只增不减的代价很少落在存储上，更多落在检索质量下降与事实冲突。整理要处理三类问题：重复、过期、冲突。

**重复**来自同一事实被反复写入。合并时要保留全部来源，不能只留最新一条——来源数量本身就是可信度的信号。

**过期**来自环境变化。判断过期的依据通常有两条：最近一次被取回的时间，以及最近一次被验证的时间。前者反映"还有没有用"，后者反映"还对不对"。这两件事必须分开记录：一条一年没被用过但昨天刚验证过的记忆，比一条天天被用但三年没验证的记忆更可靠。

**冲突**最需要谨慎。用户先说"部署到 testing 环境"，后来说"部署到 staging 环境"，这可能是改主意，也可能是两个不同的流程。系统需要区分三种情况：

- 后一次是对前一次的更正，前一条标记为被替代；
- 两条在不同条件下都成立，需要把条件写进记忆；
- 证据不足，保留冲突状态，取回时提示模型不要单独依据其中任何一条。

### 一次冲突的完整处理

把上面三种情况落到具体流程上，可以拆成五步。用"部署命令"这个例子走一遍。

第一条记忆来自三个月前的一次任务：主体是当前项目，属性是部署方式，取值是 `npm run deploy`，来源是那次任务的第 12 条消息，置信度 0.9，验证时间是三个月前。

第二条记忆来自上周：同一主体同一属性，取值是 `bash deploy.sh`，来源是那次任务第 4 条消息，置信度高，验证时间是上周。

第一步是识别。两条的主体与属性相同、取值不同，构成互斥。如果只按文本相似度看，它们相似度很高，会被当成重复合并，结果是留下一条随机的。所以识别必须靠结构字段，不能靠文本。

第二步是判定来源强弱。第二条更新、来源更近、验证更晚，三条都指向它更可信。但"更可信"不等于"旧的就是错的"——旧的那条在当时是对的，它错在没被更新。所以处理方式是标记替代、保留原文：第一条的 `supersedes` 被第二条指向，取回时默认不返回。

第三步是检查是否存在条件差异。如果第二条的来源里提到"这个项目从下周起改用脚本"，那两条就是时序关系，不是矛盾；如果提到"生产用脚本、测试用命令"，那两条是并列，需要把条件写进各自的记忆。这一步只能读来源，不能靠推理。

第四步是更新下游。如果索引里有一行指向第一条，那行需要改写或删除，否则模型会顺着索引读到一条已失效的记忆。

第五步是记录。这次替代关系要写进事件，因为它是"为什么系统改了行为"的唯一解释。没有这条记录，三个月后再有人问"为什么不直接用 `npm run deploy`"，没人答得上来。

这五步里，第三与第四最容易漏。漏了第三步会把并列关系误判成替代，丢掉一条仍然有效的知识；漏了第四步会让索引与主题文件脱节，模型读到索引却取不到正确内容。

### 整理的四步

Claude Code 的夜间整理给出了一个具体做法，把整理拆成定向、采集、整合、修剪四步。

定向阶段先看清全貌：列目录、读索引、浏览已有主题文件。这一步的目的是避免重复创建——不做定向，整理会不断产生新的近似条目。

采集阶段按优先级找新信号，顺序是：按日的日志文件、与当前代码矛盾的旧记忆、必要时用窄关键词去 grep 转录文件。第三项有明确约束——不要穷尽读取转录文件，只在已经怀疑某件事重要时去查。原因是转录是巨大的 JSONL 文件，全读会耗尽预算。

整合阶段写或更新主题文件。三条明确要求：把相对日期换成绝对日期；删除已被证伪的旧记忆；合并新信号时优先更新已有主题文件，不要创建近似副本。

修剪阶段更新索引：删掉指向失效条目的指针，把超过约 200 字的索引行压回主题文件——一行太长说明它承载了正文内容。

这四步的顺序不能换。先采集后整合会让新内容冲击已有结构；先修剪后定向会让整理看不到全貌。

### 什么可以自动、什么要人批

有一条实用分界：**不增加语义的动作可以自动，改变结论的动作需要人批或至少需要可回滚。**

可以自动的动作：合并重复条目、缩短过长索引行、修正日期格式、更新 `verified_at`、把主题文件里的过时链接改指向。

需要人批或需要回滚的动作：删除条目、改写事实内容、把私人记忆提升为团队共享、调整作用域、批量重组目录。

分界的理由是错误代价不同。前者错了只是难看，下次整理还能修；后者错了会让系统在没人察觉的情况下改变行为，而且改动本身可能已经通过整理被"合法化"了。

Codex 在这条上给出了更彻底的做法：它的整理产物落在一个 git 基线工作区里，每次整合前先生成工作区差异，整合后重置基线。这样任何一次整理都能回滚到上一个已审核状态。这比"是否人批"更实用——人批只能防住单次错误，回滚能防住累积错误。

## 7. 作用域与共享

记忆的可见范围通常分三级：仅当前任务、仅当前用户当前项目、团队共享。

分级的必要性来自两类风险。一类是越权，用户的私人偏好不应该被同事看见；另一类是污染，某个人的个人习惯被写进团队约定后，所有贡献者都要遵守一条没人同意的规则。

Claude Code 的处理方式值得参考：它把记忆分成私人目录与团队目录，并要求在写入时显式选择 scope。判据写在提示词里——只有当一条指引明显属于项目级约定（测试策略、构建约束）、不属于个人风格时，才写入团队记忆。团队记忆在同步前还要过一遍密钥扫描，命中高危模式的内容不会离开本机。

共享带来一个新问题：冲突的裁决者变了。私人记忆的冲突由用户自己裁决，团队记忆的冲突需要项目维护者裁决。所以团队记忆的写入最好经过可审阅的变更，避免自动同步——这与代码变更走评审是同一个道理。

## 8. 衡量记忆系统

记忆系统的质量不能用"存了多少条"衡量。可用的指标分成两组。

写入侧：

| 指标 | 含义 | 采集方式 |
| --- | --- | --- |
| 精确率 | 写入的记忆中真的可复用的比例 | 抽样人工标注 |
| 来源完整率 | 带有效来源指针的比例 | 检查字段 |
| 敏感信息拦截率 | 含密钥/令牌的候选被拦下的比例 | 红队样本回放 |
| 重复率 | 同一事实被写入多次的比例 | 近似去重统计 |

取回侧：

| 指标 | 含义 | 采集方式 |
| --- | --- | --- |
| 命中率 | 需要记忆的任务里成功取回的比例 | 任务回放 |
| 无效占比 | 注入内容中未被使用的比例 | 对比注入与引用 |
| 重复说明次数 | 用户被迫重新说明同一件事的次数 | 会话标注 |
| 过期引用率 | 取回的记忆在核对时被证伪的比例 | 抽检 |

最后一组指标最能说明问题：如果一个系统上线后用户重复说明的次数没有下降，那么不管它存了多少条记忆，都没有产生价值。

### 怎么测重复说明次数

这个指标听起来主观，实际上可以机械统计。做法是在会话里标记两类事件：用户提出一项要求，以及用户在同一项目里再次提出语义相同的要求。第二次及以后都计一次重复说明。

难点在"语义相同"的判断。可行的近似是人工抽检加规则：如果用户的话里出现"我说过""上次说过""还是""又"这类词，或者同一约束在七天内被提及两次以上，就标为候选，再人工确认。

一个健康的系统上线三个月后，这个数字应当明显下降。如果它不变，通常对应三种原因之一：

- 记忆写入了但在需要时没被取回（取回链路问题）；
- 取回了但被当作参考信息，没有影响行为（注入位置或信任级别问题）；
- 根本没写（抽取判据过严或抽取未运行）。

三种原因的修法完全不同，所以这个指标下降不了时，先查是哪一种，不要直接去调抽取阈值。

### 一个反面指标

除了正向指标，还有一组反向信号值得监控：

| 信号 | 说明 |
| --- | --- |
| 记忆总量增速远高于任务量增速 | 抽取过宽，在制造噪声 |
| 索引行长度持续增长 | 有人往索引里写正文 |
| 单条记忆被反复改写 | 事实不稳定，或者写入时没有判据 |
| 团队记忆的条目数与贡献者人数脱节 | 少数人把个人偏好写成了团队约定 |
| 整理后条目数下降但检索质量未变 | 整理在删无关紧要的东西，没解决真问题 |

第四条容易被忽略。团队记忆的健康状态是"条目数随团队规模缓慢增长"，如果一个人贡献了大部分条目，那大概率是个人偏好在冒充团队约定。

## 9. 与其他机制的交界

记忆与相邻机制有几处容易混淆的地方，需要在设计时定清楚。

**记忆与压缩。** 压缩替换的是发给模型的视图，目标是在窗口限制内完成任务；记忆是跨任务的沉淀。压缩可能复用记忆（用已有的会话记忆替代一次摘要调用），但记忆本身不负责解决窗口压力。

**记忆与指令。** 指令由人写、可以评审、随仓库版本走；记忆由智能体写、会被自动整理。两者不能互相替代：把项目约定交给记忆，会让约定变成某个智能体的个人理解；把用户偏好交给指令，会让每次改偏好都要改代码库。

**记忆与日志。** 日志是事实，记忆是结论。结论可能错，所以必须能回到事实。这也是"来源"字段不可省略的原因。

**记忆与经验学习。** 把经验写成可检索的文档属于记忆；把经验写成指令、技能、程序或模型参数属于能力更新。两者的验证标准不同：记忆只要有来源就能存，能力更新必须通过回归测试才能生效。

## 10. 本章要点

记忆治理真正要处理的是判断与责任：判断什么值得留（写入判据），判断什么时候该走（过期规则），判断谁有权改（作用域），判断错了之后怎么回到事实（来源绑定）。

工程上实施这件事，需要先回答三个问题：谁负责写、写的时候依据什么、失效由谁负责。三个问题的答案决定了架构选型——独立记忆库、指令文件、还是引用快照。下一章讨论第二个问题的一半：写下来之后，怎么在需要的时候取回，以及用什么形式取回。
