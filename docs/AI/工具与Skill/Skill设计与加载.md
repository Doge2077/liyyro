# Skill 设计与加载

## 1. 一次没被加载的约定

团队在新员工文档里写明了「生成发布说明时必须跑 `scripts/changelog.py`，手写的格式会漏掉合并提交」。这条约定写进了系统的全局提示词，五千字。三个月后，提示词涨到一万两千字，大部分内容与当前任务无关，而那条发布说明的约定被埋在中段。

模型偶尔遵守，偶尔不遵守。团队以为是模型不稳定，实际上是这条约定的可见性下降了：它在一万两千字里，而且每轮都要和几十条其他约定竞争注意力。

Skill 要解决的就是这件事：把只在特定场景生效的知识从全局提示词里拿出来，按需加载。

## 2. 三者的分工

系统提示、Skill、工具各承担一件事。

**系统提示**对所有任务生效：不能违反的约束（不许提交密钥）、身份（你是谁）、输出格式（用中文）、必须遵守的流程（改完代码要跑测试）。

**Skill**按任务匹配加载：某类任务的流程、领域知识、判定原则、完成标准。

**工具**提供可执行动作：读写文件、调接口、跑命令。

判定顺序不能反。先问「这个内容需要模型执行动作吗」——需要，是工具；再问「它对所有任务都生效吗」——是，进系统提示；剩下的才是 Skill。

顺序反了会犯一种错：把工具写成 Skill。例如写一个 Skill 说「用 `scripts/deploy.py` 部署」，但不提供调用脚本的工具，模型知道该做什么却没有手段。

反向的错也存在：把流程写成工具。例如为「生成周报」写一个工具，把整个流程硬编码在工具里，参数只有日期。这样做的代价是流程改了要改代码，而且模型无法在中间做判断。

## 3. 三层披露

<iframe src="/diagrams/skill-layers.html" title="Skill 的三层披露结构" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/340;border:0;display:block;margin:24px 0;"></iframe>

**目录层**常驻：名称、一句描述、何时使用。每条 100 到 200 字节。

**正文层**命中后加载：流程、判定条件、完成标准、注意事项。通常 2 到 8 KB。

**资源层**执行时读：脚本、模板、示例。正文里只需要说「运行 `scripts/check.py`」，不必内联脚本内容。

三层的体积相差一个数量级，这个梯度决定了目录层要写得极省。

### 目录层的写法

设目录有 $n$ 条，每条描述 $d$ 字节，则常驻成本是 $n \cdot d$。二十个 Skill、每条 200 字节是 4 KB；每条 500 字节就是 10 KB，且每轮都付。

所以目录描述要回答一个问题：**什么任务下该选我**。不需要说我是怎么实现的，也不需要列出我的全部能力。

对比两种写法：

```text
弱：处理文档相关工作。
强：把 Markdown 转成正式的 Word 文档，包含目录、页眉、样式模板。
```

弱写法在「把这份文档转成 Word」这个任务里不会命中，因为它没说 Word。强写法命中，因为它把动作与产物都写出来了。

### 正文层的膨胀

正文层最常见的毛病是膨胀：把整套流程的每个细节都写进去，命中一次就吃掉几 KB。

判断标准：正文应该让模型能开始工作并知道何时算完成，不必把每个分支都穷举。分支细节可以放到资源层，或者留给模型按情况判断。

一个具体的量化：如果一个 Skill 正文有 8 KB，一次任务里被加载两次，就是 16 KB。这个成本相当于四十个工具定义。

## 4. 发现与优先级

Skill 从哪来、重名怎么办，决定了「同一个名字在不同项目里是不是同一件事」。

<iframe src="/diagrams/skill-discovery.html" title="Skill 发现的三层来源与优先级" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/340;border:0;display:block;margin:24px 0;"></iframe>

三类来源：项目根（随仓库版本走）、自定义根（部署级）、用户根（个人级）。

发现规则通常是扫描这些根目录的顶层，支持两种形态：目录 bundle（含 `SKILL.md`）与平铺文件（`<name>.md`）。刻意不支持嵌套的 `**/SKILL.md`——嵌套会让扫描成本随目录深度上升，而且同名冲突的概率大增。

重名的裁决有一条固定顺序：

1. 最近的 scope 层直接胜出（项目层盖过全局层）；
2. 同层内先比 rank（提权字段）；
3. 再比提供方注册顺序；
4. 最后比本地目录顺序。

顺序固定是好事：同名覆盖可预测，不需要读代码就知道谁赢。它也有代价：用户根的同名 Skill 永远盖不过项目根，即使它是更新版本。所以升级一个 Skill 时，改内容要改在对应的层，光在用户根改没用。

### 元数据的作用

三个字段控制「谁能看到这个 Skill」：

| 字段 | 作用 |
| --- | --- |
| `whenToUse` | 目录里额外的一行，说明何时使用 |
| `disable-model-invocation` | 从模型目录与加载器中排除，只留给人调用 |
| `user-invocable` | 从用户命令中排除，只留给模型调用 |

第二个字段的用途容易被忽略：有些 Skill 只适合人显式调用（例如「重置环境」），让模型自己决定加载它很危险。

第三个字段的用途相反：有些 Skill 只适合模型按需加载，不希望出现在用户的命令菜单里（例如内部的重试策略）。

## 5. 版本与覆盖

部署时常见两种需求：内置一份默认 Skill，同时允许团队覆盖。

可行设计是「内置默认 + 团队覆盖 + 记录基线」：

- 覆盖记录基于哪个内置版本；
- 升级时保留团队的文本；
- 默认变更时在界面上标出「默认已更新」并显示差异；
- 团队可以保持自己的版本、采用新默认、或编辑后再保存；
- 没有覆盖的部分自动跟随新默认。

这套机制解决了一个具体问题：升级时团队的自定义内容被悄悄覆盖。有了基线记录，系统知道哪部分是团队的、哪部分是默认的。

保存规则里还有两条实用约束：未知字段直接拒绝（不静默忽略），模板占位符缺失也拒绝。两者都是为了避免「保存成功了但行为不对」。

## 6. 写作方法

一份可用的 Skill 正文包含四段。

**触发条件。** 什么任务下用，什么任务下不用。排除条件同样重要——只写「处理文档」会导致它在所有文档任务里都被加载。

**流程。** 可执行的步骤。每一步是一个动作加一个判断，不要写「仔细分析需求」这类无法执行的话。

**完成标准。** 可判定。写成「输出包含三节、每节有结论」，「输出质量好」不构成标准。

**示例。** 只示范格式，不示范事实。这一点最容易被写错：示例里的具体数字、具体结论会被模型当成事实引用。所以示例要么用占位符（`<项目名>`），要么显式标注「以下仅为格式示例」。

## 7. 失败模式

**Skill 膨胀。** 症状：目录层涨到十几 KB，模型开始漏选。成因：什么都想放进 Skill。修法：把只在特定分支用到的内容移到资源层，或拆成两个 Skill。

**触发条件过宽。** 症状：某个 Skill 几乎每个任务都被加载，但多数时候无关。成因：描述写得太泛（「处理文档」「辅助开发」）。修法：描述里加排除条件。

**正文与脚本不一致。** 症状：Skill 说「运行 `scripts/check.py` 并确保通过」，但脚本已经改了行为。成因：脚本与正文分开维护。修法：把脚本的输出格式写进正文的完成标准，让不一致能被发现。

**被压缩挤掉后不再加载。** 症状：长任务里 Skill 的正文被压缩掉了，后续步骤不再遵守它。成因：Skill 加载后被当作普通消息，压缩时一起被摘要。修法：加载机制要在压缩后重新注入，或者把 Skill 的关键约束提升到系统提示。

第四条在多 Agent 与长会话场景里最常见，而且最难发现——因为任务表面还在推进，只是不再遵守某些约定。

## 8. 判断顺序小结

写一份内容之前，按顺序问四个问题：

1. 需要模型执行动作吗？需要 → 工具。
2. 对所有任务都生效吗？是 → 系统提示。
3. 只在某类任务里生效吗？是 → Skill。
4. 只有分支细节吗？是 → 资源层，正文里只写路径。

四问之后如果仍然不确定，把它放进 Skill 的正文，别放进系统提示——放错到系统提示的代价是每轮都付，放错到 Skill 的代价只是偶尔多加载一次。
