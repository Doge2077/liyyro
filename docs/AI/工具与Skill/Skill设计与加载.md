# Skill 设计与加载

## 1. 按需要时机的分类

模型能拿到的知识，按「什么时候需要」可以分成三类。这个分法与「内容属于什么类型」不同，因为它直接对应成本结构。

| 类别 | 需要时机 | 成本特征 | 典型内容 |
| --- | --- | --- | --- |
| 恒定类 | 每一轮 | 每轮固定支付 | 身份、不可违反的约束、输出格式 |
| 匹配类 | 某类任务命中时 | 命中时一次支付 | 某类任务的流程、判定原则、完成标准 |
| 执行类 | 具体动作要用时 | 用到时按需读取 | 脚本、模板、示例数据 |

三类内容的成本量级差一个数量级：恒定类每轮都付，匹配类一次几 KB，执行类只在真的跑脚本时才产生读取。

把内容按这个轴分类，再决定放在哪，比按「这是提示词还是文档」分类更接近实际。一条「不许提交密钥」属于恒定类；一段「生成发布说明要先跑某个脚本」属于匹配类；脚本本身属于执行类。

下面的讨论集中在匹配类，也就是 Skill。

## 2. 三类内容之间的流动

三类的划分可以移动，而移动方向决定了成本。

**从匹配类移到恒定类。** 把一条只在发布任务里用的约定写进全局提示词。后果是每轮都付，且它与几十条其他约定竞争注意力。第 1 节那个「约定被埋在一万两千字中段」的例子即属此类。

**从恒定类移到匹配类。** 把「改完代码要跑测试」从全局提示词移到一个 Skill 里。这一步看似省了每轮成本，但引入一个新风险：如果这个 Skill 在该任务里没被加载，模型就不会跑测试。

所以移动有前提：**被移动的内容必须是「不加载也不会造成错误」的**。「改完代码要跑测试」不满足这个前提，因为不跑就出错。它可以留在恒定类，或者同时用程序约束（提交前强制跑测试）来保证。

**从匹配类移到执行类。** 把 Skill 正文里的脚本内容移出去，正文只留「运行 `scripts/check.py`」。这一步几乎总是划算的：正文从几 KB 降到一行，脚本在执行时才被读取。

判断标准是：这段内容是否需要模型逐字阅读。脚本需要执行，不需要逐字读；流程需要逐字读。

## 3. 三层披露的体积预算

Skill 本身也按需要时机分三层。

**目录层**常驻：名称、一句描述、何时使用。每条 100 到 200 字节。
**正文层**命中后加载：流程、判定条件、完成标准、注意事项。通常 2 到 8 KB。
**资源层**执行时读：脚本、模板、示例。正文里只需给路径。

设目录有 $n$ 条、每条描述 $d$ 字节，则常驻成本是：

$$
c = n \cdot d
$$

二十个 Skill、每条 200 字节是 4 KB；每条 500 字节就是 10 KB，且每轮都付。这个数字与「二十个 Skill 的正文总量」（假设平均 4 KB，共 80 KB）形成对照：常驻部分只占正文总量的 5%，这正是分层披露的价值。

三层的预算约束不同，写法要求也不同。

| 层 | 预算 | 写法要求 |
| --- | --- | --- |
| 目录 | 每条 100–200 字节 | 只回答「什么任务下该选我」 |
| 正文 | 2–8 KB | 能让模型开始工作并知道何时算完成 |
| 资源 | 无硬上限 | 可执行即可，不必可读 |

## 4. 目录层的写法

目录描述要回答一个问题：什么任务下该选我。不需要说怎么实现，不需要列全部能力。

对比两种写法：

```text
弱：处理文档相关工作。
强：把 Markdown 转成正式的 Word 文档，包含目录、页眉、样式模板。
```

弱写法在「把这份文档转成 Word」这个任务里不会命中，因为它没说 Word。强写法命中，因为它把动作与产物都写出来了。

三个具体的写法要求。

**写产物名，不写领域名。** 「Word 文档」是产物，「文档相关工作」是领域。产物名能被任务描述里的词直接匹配。

**写排除条件。** 一条 Skill 如果只写「处理文档」，会在所有文档任务里被加载。写上「不用于纯文本转换」，就能把一部分任务挡在外面。

**控制长度上限。** 这条不是建议，是硬约束：目录长度直接等于每轮成本。有实现给描述设了长度上限并在超限时截断，这是必要的防护。

## 5. 正文层该写多少

正文层最常见的毛病是膨胀：把整套流程的每个细节都写进去，命中一次就吃掉几 KB。

判断标准：正文应该让模型能开始工作并知道何时算完成。它不需要穷举每个分支。

一个具体的量化：如果一个 Skill 正文有 8 KB，一次任务里被加载两次，就是 16 KB。这个成本相当于四十个工具定义。

正文该写四段。

**触发条件。** 什么任务下用，什么任务下不用。排除条件同样重要——只写「处理文档」会导致它在所有文档任务里都被加载。

**流程。** 可执行的步骤。每一步是一个动作加一个判断，不写「仔细分析需求」这类无法执行的话。

**完成标准。** 可判定。写成「输出包含三节、每节有结论」，「输出质量好」不构成标准。

**示例。** 只示范格式，不示范事实。这一点最容易被写错：示例里的具体数字、具体结论会被模型当成事实引用。所以示例要么用占位符，要么显式标注「以下仅为格式示例」。

## 6. 元数据与控制字段

除了名称与描述，三个字段控制「谁能看到这个 Skill」。

| 字段 | 作用 | 典型用途 |
| --- | --- | --- |
| 何时使用 | 目录里额外一行，说明适用场景 | 补充主描述的匹配信号 |
| 禁止模型调用 | 从模型目录与加载器中排除 | 只适合人显式调用的危险操作 |
| 禁止用户调用 | 从用户命令中排除 | 只适合模型按需加载的内部策略 |

第二个字段的用途容易被忽略：有些 Skill 只适合人显式调用（例如「重置环境」），让模型自己决定加载它很危险。

第三个字段的用途相反：有些 Skill 只适合模型按需加载，不希望出现在用户的命令菜单里（例如内部的重试策略）。

除这两个布尔字段，有的实现把可见性做成逐条覆盖，按 Skill 名设置：

| 档位 | 模型可见 | 用户可见 | 描述是否渲染 | 适用 |
| --- | --- | --- | --- | --- |
| 开 | 是 | 是 | 是 | 常规 Skill |
| 仅名称 | 是 | 是 | 否 | 描述很长但用得频繁 |
| 仅用户调用 | 否 | 是 | 不适用 | 危险操作、需人确认 |
| 关 | 否 | 否 | 不适用 | 临时停用，保留内容 |

第二档是最细的一档：Skill 仍然对模型可见、可以被调用，但目录里只列名字，不渲染描述。它省下的是目录体积，代价是模型只能凭名字判断该不该用。

这一档的存在说明可见性是一个「模型看到多少」的刻度，不只有开关两态。目录体积与选择准确率之间的取舍可以按单个 Skill 调，不必全局一刀切。

### 跨运行时的一致性要求

同一个 Skill 常常要同时供给两个运行时，而两个运行时的元数据格式不同：

| 运行时 | 文件 | 字段 | 语义 |
| --- | --- | --- | --- |
| 一种 | `SKILL.md` 的 frontmatter | `disable-model-invocation` | 是否禁止模型调用 |
| 另一种 | `agents/openai.yaml` | `policy.allow_implicit_invocation` | 是否允许隐式调用 |

两者的语义相反。这带来一个必然会发生的漂移：改了一个忘了改另一个，于是同一个 Skill 在一个运行时里是手动专用、在另一个运行时里可以被自动加载。

对付这种漂移，光靠文档要求不够，需要一条可执行的校验。一条可行的规则是三项：

第一，两个字段必须都出现且都是布尔值。

第二，两者推出的结论必须一致：前者的真等价于后者的假。不一致即报错，并指出两侧各自的值——这种错误靠人肉对照很难看出来。

第三，一个手动专用的 Skill 必须仍然可由用户调用。否则它谁都调不到：模型不许调，人也不能调。这条最容易漏，因为两个标志分别看都合理。

校验的作用不只是防错，它还固定了一件事：手动专用这个概念在两侧必须同时成立。有了这条，新增一个运行时就必须补一份等价映射，不能只实现一半。

## 7. 发现与裁决顺序

Skill 从哪来、重名怎么办，决定「同一个名字在不同项目里是不是同一件事」。

<iframe src="/diagrams/skill-discovery.html" title="Skill 发现的三层来源与优先级" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/340;border:0;display:block;margin:24px 0;"></iframe>

三类来源：项目根（随仓库版本走）、自定义根（部署级）、用户根（个人级）。

发现规则是扫描这些根目录的顶层，支持两种形态：目录 bundle（含 `SKILL.md`）与平铺文件（`<name>.md`）。刻意不支持嵌套的 `**/SKILL.md`——嵌套会让扫描成本随目录深度上升，而且同名冲突的概率大增。

重名的裁决有一条固定顺序：

1. 最近的 scope 层直接胜出（项目层盖过全局层）；
2. 同层内先比 rank（提权字段）；
3. 再比提供方注册顺序；
4. 最后比本地目录顺序。

顺序固定的好处是可预测：同名覆盖不需要读代码就知道谁赢。代价是用户根的同名 Skill 永远盖不过项目根，即使它是更新版本。所以升级一个 Skill 时，改内容要改在对应的层，光在用户根改没用。

## 8. 失效与变更传导

目录是快照还是实时，决定了「新加一个 Skill 要不要重启」。

主流做法是监视这些根目录，新增、改名、删除无需重启即可到达。但监视带来一个新问题：变更如何传导到已加载的 Skill。

三种传导方式。

**立即失效重取。** 变更事件到达后，目录与已加载内容一起失效，下次读取时重取。优点是简单不会漏，代价是每次变更都要全量重取。

**增量更新。** 只更新受影响的那条。优点是便宜，代价是需要正确处理改名与删除——改名在文件系统层面是「删除加新增」，增量更新很容易漏掉删除那一半。

**不传导。** 只在会话开始时读一次。优点是稳定可预测，代价是会话中途改 Skill 不生效。

第二种的坑值得单独说。一个 Skill 从 `old-name` 改名为 `new-name`，如果是增量更新且只处理了新增，目录里会同时出现两个名字——旧名字还指向已经不存在的文件，或者读到缓存里的一份旧内容。表现出来是「我改了 Skill 但没生效，还多了个重复的」。

第一种方式没有这个问题，因为它是全量重取。代价可以接受：目录本身不大。

### 变更的来源

变更不只来自人改文件。三个来源各自的传导方式不同。

| 来源 | 例子 | 传导方式 |
| --- | --- | --- |
| 文件变更 | 新增、改名、删除 | 监视目录，失效缓存 |
| scope 变更 | 切换工作目录、重组会话 | 缓存键变化 |
| 提供方变更 | 插件加载、注册表更新 | 注册表失效事件 |

第二个来源容易被漏。会话中途切换工作目录后，适用哪些 Skill 会变——因为项目层的那一批换了。如果发现缓存只按「上次扫描时间」做键，切换后读到的仍是旧结果。

第三个来源在代码注册的 Skill 里才有。它的失效粒度通常是全量的：一个提供方变更就让整个注册表失效。这个粗粒度在数量少时可以接受，数量多时需要按提供方分片。

### 缓存键的选择

三种键，各自的正确性不同。

| 键 | 正确性 | 命中率 |
| --- | --- | --- |
| 空（不缓存） | 最高 | 最低 |
| 扫描时间 | 依赖文件系统时间戳的精度 | 高 |
| 解析后的 scope 链 | 高 | 高 |

第三种是唯一能在「正确」与「命中」之间取得平衡的。它的思路是：缓存的内容只取决于「哪些根被扫描」，而根由 scope 链决定，所以用 scope 链做键就能保证正确。

第一种在数量少时是合理选择——不缓存也就没有正确性问题。数量多时必须缓存，此时键的选择就变成关键。

## 9. 版本与覆盖

部署时常见两种需求：内置一份默认 Skill，同时允许团队覆盖。

可行设计是「内置默认 + 团队覆盖 + 记录基线」：

- 覆盖记录基于哪个内置版本；
- 升级时保留团队的文本；
- 默认变更时在界面上标出「默认已更新」并显示差异；
- 团队可以保持自己的版本、采用新默认、或编辑后再保存；
- 没有覆盖的部分自动跟随新默认。

这套机制解决一个具体问题：升级时团队的自定义内容被悄悄覆盖。有了基线记录，系统知道哪部分是团队的、哪部分是默认的。

保存规则里还有两条实用约束：未知字段直接拒绝（不静默忽略），模板占位符缺失也拒绝。两者都是为了不出现「保存成功了但行为不对」。

### 覆盖的三种状态

一份 Skill 在「内置」与「团队自建」之间有第三种状态：基于内置修改过。

三种状态的处理不同：

| 状态 | 升级时 | 界面标识 |
| --- | --- | --- |
| 纯内置 | 直接跟随新默认 | 无 |
| 基于内置修改 | 保留团队文本，标出默认已更新 | 显示差异 |
| 团队自建 | 不受升级影响 | 标为自建 |

第二种是唯一需要人决策的状态。系统知道哪部分是团队的，因此能给出准确的差异；团队可以选择保持、采用新默认、或编辑后保存。

如果系统不记录基线，第二种会退化成第一种或第三种——要么升级时覆盖掉团队的修改，要么把团队修改过的当成自建而永远不更新。两种退化都在实践中出现过。

### 占位符替换的约束

有的实现支持在 Skill 正文里写占位符，加载时替换成实际值（例如项目名、当前分支）。

这个机制省去了为每个项目写一份 Skill 的成本，但引入一类新错误：占位符拼错或缺失变量时，替换结果是一段奇怪的空洞。

拒绝是唯一合理的处理，不能忽略。忽略会让 Skill 带着「当前分支是 」这种残缺内容被加载，模型会尝试理解这段残缺，而理解结果不可控。

## 10. 与记忆注入的对照

Skill 与记忆都会进入上下文，但两者的时效与失效方式不同。

| 维度 | Skill | 记忆 |
| --- | --- | --- |
| 内容来源 | 人写的流程与原则 | 从轨迹中抽取的事实与偏好 |
| 命中方式 | 按任务类型匹配 | 按相似度检索 |
| 失效方式 | 人改文件或换版本 | 过期、被替代、冲突 |
| 冲突处理 | 重名裁决（优先级固定） | 判并列或互斥 |
| 体积控制 | 三层披露 | 索引加正文 |

两者最大的差别在冲突处理。Skill 的重名有确定的裁决顺序，因为它是文件系统，层级清晰；记忆的冲突没有这种结构，只能靠主体与属性字段判断并列还是互斥。

这个差别解释了为什么 Skill 的加载可以做得比记忆的检索更简单：它不需要判断「这条内容是否适用于当前情况」，只需要判断「当前任务是否属于这个类型」。

## 11. 失败模式

| 失败模式 | 症状 | 成因 | 修的位置 |
| --- | --- | --- | --- |
| Skill 膨胀 | 目录涨到十几 KB，模型漏选 | 什么都想放进 Skill | 把分支细节移到资源层，或拆分 |
| 触发条件过宽 | 几乎每个任务都被加载 | 描述写得太泛 | 描述里加排除条件 |
| 正文与脚本不一致 | 说「运行某脚本并确保通过」，脚本已改行为 | 脚本与正文分开维护 | 把脚本输出格式写进完成标准 |
| 压缩后不再加载 | 长任务里正文被摘要掉，后续不再遵守 | 加载后当作普通消息 | 压缩后重新注入，或把关键约束提升到恒定类 |
| 改名残留 | 改名后目录出现两个名字 | 增量更新只处理新增 | 改为全量重取 |

第四条在多 Agent 与长会话场景里最常见，而且最难发现——任务表面还在推进，只是不再遵守某些约定。

一个检测方式：在长任务的中后期问一句「你现在遵守哪些约定」，看它能否说出那条被压缩掉的。说不出来说明已经被摘要掉了。

## 12. 一份完整的 SKILL.md

前面各节分开讲写法，这里给一份完整的文件，看各部分的相对体量。

```markdown
---
name: release-notes
description: 把一批合并提交整理成对外发布说明，输出含分类与致谢的 Markdown。
whenToUse: 需要为某个版本生成对外公告时；不用于内部技术变更记录。
---

# 生成发布说明

## 13. 何时使用

版本号确定、待发布提交已合并到主分支时。不要用于：
- 内部技术变更记录（那是另一份文件）
- 尚未合并的提交（会让公告与代码不一致）

## 14. 流程

1. 取两个标签之间的提交列表，排除合并提交本身。
2. 按面向用户的类别分组：新增、改进、修复、不兼容变更。
3. 每条写成一句话，说清「变了什么」与「对谁有影响」。
4. 不兼容变更置顶，并写明迁移方式。
5. 致谢外部贡献者，用其提交里的署名。

## 15. 完成标准

- 包含四个分类标题，没有内容的分类省略；
- 每条不超过一句话，不含提交哈希与内部代号；
- 不兼容变更在文首，且每条都写了迁移方式；
- 贡献者署名与提交记录一致。

## 16. 格式示例

以下仅为格式，不含真实内容：

    ## 新增
    - <功能名>：<对用户的影响>
    ## 不兼容变更
    - <变更名>：<迁移方式>

## 17. 资源

- 分类规则细化：`references/categories.md`
- 生成脚本：`scripts/collect.py`
```

五个部分里，正文约 500 字，资源只给了两个路径。

三处值得注意。

**何时使用部分重复了 frontmatter。** 这是有意的：目录层的那一句用于「要不要加载」，正文里的这一段用于「加载后要不要继续」。两处的作用不同，重复不算冗余。

**完成标准四条都是可判定的。** 「每条不超过一句话」能数，「不含哈希」能查，「置顶」能看位置。换成「语言简练」就无法判定。

**格式示例用了占位符。** 如果写成「新增：支持批量导出，处理速度提升 3 倍」，模型会把「3 倍」当成真实数据引用。占位符与「仅为格式」的声明共同防这件事。

## 18. 一份 Skill 的生命周期

写完之后，一份 Skill 会经历几个阶段，每个阶段有不同的维护动作。

| 阶段 | 判定 | 动作 |
| --- | --- | --- |
| 草稿 | 内容未定 | 加禁用字段，避免被误加载 |
| 试用 | 已能命中，完成标准有待验证 | 保持目录描述保守，观察命中率 |
| 稳定 | 命中与完成都正常 | 定期检查正文是否与实现脱节 |
| 待修订 | 出现「按描述做但结果不对」 | 对比正文与当前实现 |
| 废弃 | 对应流程已下线 | 移出目录，保留内容供查 |

第一阶段用控制字段控制可见性，不删文件，理由是草稿还需要被自己看到。

第四阶段最容易被忽略。判据是「按 Skill 做完之后有没有返工」，不靠有没有人抱怨。返工率高说明正文与实际流程已经不一致。

第五阶段的关键是「移出目录但保留内容」。直接删掉会让历史任务失去引用；留在目录里又会让模型继续加载。控制字段里的「禁止模型调用」正好对应这个需求。

## 19. 判定顺序

写一份内容之前，按顺序问四个问题：

1. 需要模型执行动作吗？需要，做成工具。
2. 对所有任务都生效，且不加载就会出错吗？是，放进恒定类。
3. 只在某类任务里生效吗？是，做成 Skill。
4. 只有分支细节吗？是，放进资源层，正文里只写路径。

四问之后如果仍然不确定，把它放进 Skill 正文，别放进恒定类。放错到恒定类的代价是每轮都付，放错到 Skill 的代价只是偶尔多加载一次。

第四问的反面也常见：把本该给路径的内容内联进正文。判断标准是「模型是否需要逐字阅读」，与这段内容是否重要无关。
