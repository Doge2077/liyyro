# 工具与 Skill 工程实践

## 1. 六项对照

四家 Coding Agent 的工具与 Skill 系统，差别不在「有没有」，而在六项取舍上。

| 维度 | 问题 |
| --- | --- |
| 注册表形态 | 怎么登记、怎么查、怎么裁决重名 |
| 作用域分层 | 有没有全局层与局部层 |
| 发现优先级 | 重名时谁赢，顺序是否固定 |
| 延迟加载 | 不常驻的工具怎么被发现 |
| 权限模型 | 权限声明在哪个粒度 |
| 结果截断 | 单次输出多大，超限怎么办 |

## 2. 注册表形态

### DeepSeek Harness

工具定义是一个完整对象，包含面向模型的 schema、规范输出声明、执行函数、宿主使用的调度元数据、可选的 UI 展示函数。

几个字段的设计意图值得看：

| 字段 | 作用 |
| --- | --- |
| `schema` | 面向模型的字段，是唯一进入模型请求的部分 |
| `output` | 规范输出声明，含 schema 与渲染函数 |
| `execute` | 执行函数，返回规范 JSON 值 |
| `timeoutMs` | 工具级超时 |
| `isConcurrencySafe` | 是否可与其他调用并发 |
| `presentCall` / `presentResult` | UI 展示投影 |

文档里有一条硬约束：`output`、`execute`、`projectContent`、`finalizeContent`、`timeoutMs`、`isConcurrencySafe`、`presentCall`、`presentResult` 绝不能泄漏到模型请求中。

这条约束的意义在于分清「模型看到什么」与「宿主知道什么」。工具的实现细节、超时、并发安全，都是宿主的调度信息，模型不需要知道，知道了反而占空间。

`output` 用独立的 schema，没有复用入参 schema，因为输出结构通常比输入复杂（分页、错误、部分成功），而且需要被校验。

### Codex

工具注册与「可加载工具」分开。可加载工具进入搜索索引，常驻工具直接进模型请求。搜索索引的条目保存搜索文本与工具规格，并支持只迭代工具名而不实例化 schema 的操作——这个优化避免了大批工具的 schema 在搜索时被全部构造出来。

命名空间参与搜索。这在工具数量大时是必要的：同名的 `search` 在不同命名空间下是不同工具。

### OpenCode

叶子工具各自是一个插件单元，声明自己需要什么权限动作，输出有 schema。装配时按位置组合。

这个形态的收益是「工具即插件」，加一个工具不需要改动中心化的列表。代价是没有全局视图：要回答「当前有哪些工具」需要遍历装配结果。

### Claude Code

内置工具在源码目录里，每个工具有自己的提示词文件。工具描述可以是静态常量，也可以是运行时计算的函数（例如读取当前配置后生成描述）。

后者带来一个隐患，也就是《渐进式披露与按需注入》里提到的缓存问题：描述的运行时变化会让 schema 缓存失效。修法是把会变的内容移到附件。

## 3. 作用域分层

只有 DeepSeek Harness 有完整的分层注册表。

注册落入调用方 scope 对应的层：宿主行与 repository 插件落全局层，由 agent preset 常驻组合挂载的插件落该 preset 的层。提供方名称在每层内唯一。

读取时把全局层与观察 scope 的链合并：最近层的条目直接赢得重名。

这个设计的价值在两处。第一，它让「不同的 agent preset 看到不同的工具集」成为注册表的能力，不再依赖装配时的特例。第二，它让重名裁决有明确的层级依据，不必靠注册顺序。

另外三家没有等价机制。Claude Code 用工具白名单（核心集合）+ 延迟集合来分层；Codex 用「常驻 / 可加载」二分；OpenCode 用装配配置。

三者的共同点是「分层发生在装配时」，注册表本身不带分层。这个差别在工具数量不大时不明显，在需要多套配置共存时（例如同一进程里跑不同 preset）会显现出来。

### 文件系统来源的优先级

DeepSeek Harness 的 Skill 注册表：宿主层 + 按 scope 的分层；单层内按 rank、提供方顺序、本地顺序裁决；摘要按名称排序。

发现缓存以解析后的 scope 链为键，所以重设 scope 父级（空会话重组）无需注册表变更即可被下一次读取看到。

这条细节解决一个具体问题：会话中途切换工作目录后，哪些 Skill 适用会变。如果缓存不按 scope 链做键，切换后可能读到旧结果。

本地发现侧的特性：

- 扫描项目、自定义、用户三个根；
- 支持目录 bundle（含 `SKILL.md`）与平铺文件（`<name>.md`）两种形态；
- 刻意不支持发现嵌套的 `**/SKILL.md`；
- 解析 YAML frontmatter，必填 `name` 与 `description`；
- 监视这些根，新增、改名、删除无需重启即可到达。

不支持嵌套的理由是成本：嵌套扫描的耗时随目录深度上升，而收益（更细的组织）远小于同名冲突带来的麻烦。

### 一致性与失效

注册表在以下情况发失效事件：提供方变更、运行时变更。事件不带 diff，消费方用自身的查找选项重新取快照。

这个设计是「失效即重取」，没有做增量更新。好处是简单且不会漏；代价是每次失效都要全量重取，工具多时开销不小。

另一处细节：提供方的 `list()` 被拒绝时，系统记录日志并从不完整观测中省略该提供方的结果；显式的不完整观测提供可用候选项，但不使结果可缓存；格式错误的候选项快速失败。

三档处理分别对应三种情况：提供方挂了（省略）、提供方部分可用（标记不完整，不缓存）、数据格式坏了（快速失败）。把这三者分开，避免了「一个提供方挂掉导致全部缓存不更新」这类连锁问题。

## 5. 延迟加载

机制细节已在《渐进式披露与按需注入》展开。这里只补一段实现层面的对照。

| 家 | 延迟的触发 | 加载后的可见性 |
| --- | --- | --- |
| Claude Code | 不在核心白名单即为延迟 | 需显式搜索并执行 |
| Codex | 进可加载集合 | 加载后进入工具集 |
| OpenCode | 无统一机制 | 由装配决定 |
| DeepSeek Harness | 无统一机制 | 由装配决定 |

前两家有统一机制，后两家没有。这个分布不是巧合：前两家的工具数量大（内置 + 全部 MCP），后两家的工具来源相对可控。

一个判断标准：当工具来源是「用户随时可能接入任意 MCP 服务」时，统一延迟机制是必需品；当工具来源是「部署时确定」时，装配即可。

## 6. 权限模型

三种粒度。

**工具名级。** Claude Code 的按角色禁用工具。简单，但不能表达「这个工具只能读某些路径」。

**权限动作级。** OpenCode 的每个工具声明需要什么权限动作，检查时按声明匹配。可以表达「能用 shell，但 shell 内的写操作要单独授权」。

**工具策略级。** Codex 的工具策略与命名空间过滤。粒度接近工具名级，但支持命名空间。

三种粒度各有盲区。工具名级挡不住参数越界；权限动作级需要每个工具正确声明（声明错了就等于没限制）；工具策略级需要维护策略表。

一个共同点：三家都做不到「参数级白名单」（例如「只能对 `src/` 下的路径调用写入」）。这类限制通常靠沙箱或文件系统权限实现，不在工具层的职责内。

## 7. 结果截断

| 家 | 阈值 | 超限动作 |
| --- | --- | --- |
| Claude Code | 20,000 字符（内容搜索） | 触发持久化，完整内容写文件 |
| Codex | 按内容类型选择策略 | 截断 + 大结果外置 |
| OpenCode | 2,000 行 / 50 KiB | 原文落盘，返回预览与路径 |
| DeepSeek Harness | 20 MB 原始输出 / 250 条匹配 / 2,000 字节单行 | 溢出则失败；超内联上限写外置并给定位 |

四处值得注意的差别。

第一，阈值的量纲不同：字符、行加字节、原始输出大小。这反映了各家对「什么会爆」的判断不同。

第二，超限动作分两类：截断并继续（Claude Code、Codex、OpenCode），与直接失败（DeepSeek Harness 的原始输出溢出）。后者的理由是「不解析不完整的流」——截断后解析出来的结果是不完整的，而模型无法知道它不完整。

第三，只有部分实现区分「内联上限」与「原始输出上限」。区分开的好处是：内联可以小（省窗口），原始输出可以大（不丢数据），中间用外置存储衔接。

第四，单行长度限制只有部分实现有。这条在处理压缩过的代码（minified JS）时必需——那种文件可能只有三行，每行几万字符。

## 8. 三条判断

### 注册表分层决定谁能覆盖谁

如果系统需要「同一进程里跑不同配置的 agent」，注册表分层是必需品。否则重名只能靠注册顺序，而顺序是隐式的、不易审计的。

判断标准：是否有两个以上的配置需要在同一进程内共存。没有，装配即可；有，需要分层。

### 延迟加载的触发信号

统一延迟机制的触发信号有两种：白名单（不在名单里就延迟）与数量阈值（超过 N 个才延迟）。

白名单更可预测，但要维护名单；数量阈值更自动，但行为会随工具数变化而突变——昨天还能直接调的工具，今天要搜索了。这个突变在生产环境里会造成困惑。

### Skill 与工具的取舍

同一个能力可以用 Skill 描述（告诉模型怎么做）或工具实现（让模型直接调）。

用工具：定义占固定空间，但每次调用只有参数与结果。
用 Skill：目录占少量空间，但加载正文占几 KB，且模型要自己按步骤执行，容易偏。

判断标准：这个能力是否需要模型在中间做判断。需要，用 Skill（模型能变通）；不需要，用工具（执行稳定且省 Token）。

如果一个能力既需要判断又步骤固定，拆开：Skill 写判断原则与流程，工具写可执行步骤。
