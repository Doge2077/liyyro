# 工具与 Skill 工程实践

## 1. 从声明到模型可见的六环

一个工具或 Skill 从写下来到被模型看到，要经过六个环节。每一环都可能失效，而失效的表现各不相同。

| 环节 | 做什么 | 典型失效 |
| --- | --- | --- |
| 声明 | 定义结构、描述、执行体 | 结构与实现不一致 |
| 注册 | 进入注册表，按层归位 | 重名覆盖 |
| 发现 | 从来源扫描出来 | 缓存未失效 |
| 过滤 | 按 scope 与开关裁剪 | 漏挂或错挂 |
| 渲染 | 转成面向模型的形式 | 超预算被截断 |
| 失效 | 变更传导 | 缓存不更新 |

按这个顺序看，四家的差异落在哪一环变得清楚：它们在前两环设计不同，中间两环差别最大，后两环都有但成熟度不同。

## 2. 声明层：结构与执行体分开

DeepSeek Harness 的工具定义是一个完整对象，包含面向模型的结构、规范输出声明、执行函数、宿主使用的调度元数据、可选的界面展示投影。

几个字段的分工值得看。

| 字段 | 作用 | 是否进入模型请求 |
| --- | --- | --- |
| 结构（schema） | 面向模型的字段 | 是 |
| 输出声明 | 规范输出结构与渲染函数 | 否 |
| 执行函数 | 返回规范值 | 否 |
| 超时 | 工具级超时 | 否 |
| 并发安全 | 是否可与其他调用并发 | 否 |
| 展示投影 | 界面如何显示 | 否 |

文档里有一条硬约束：输出声明、执行函数、内容投影、超时、并发安全、展示投影，绝不能泄漏到模型请求中。

这条约束的意义在于分清「模型看到什么」与「宿主知道什么」。工具的实现细节、超时、并发安全都是宿主的调度信息，模型不需要知道，知道了反而占空间。

输出声明用独立结构，不复用入参结构，原因是输出通常比输入复杂（分页、错误、部分成功），而且需要被校验。

其余三家的声明层更简单：Codex 的可加载工具与常驻工具分开，搜索索引的条目保存搜索文本与工具规格，并支持只迭代工具名而不实例化结构的操作——这个优化避免了大批工具的结构在搜索时被全部构造出来。OpenCode 的叶子工具各自是一个插件单元，声明所需权限动作。Claude Code 的工具定义在源码里，描述可以是静态常量，也可以是运行时计算的函数。

最后一项有个隐患：描述的运行时变化会让结构缓存失效。修法是把会变的内容移到附件，第 5 节展开。

## 3. 注册层：分层解决谁覆盖谁

只有 DeepSeek Harness 有完整的分层注册表。

注册落入调用方 scope 对应的层：宿主行与仓库插件落全局层，由预设常驻组合挂载的插件落该预设的层。提供方名称在每层内唯一。

读取时把全局层与观察 scope 的链合并，最近层的条目赢得重名。

这个设计的价值在两处。第一，它让「不同的预设看到不同的工具集」成为注册表的能力，不再依赖装配时的特例。第二，它让重名裁决有明确的层级依据，不必靠注册顺序。

另外三家没有等价机制。Claude Code 用白名单加延迟集合分层，Codex 用「常驻与可加载」二分，OpenCode 用装配配置。

三者的共同点是分层发生在装配时，注册表本身不带分层。这个差别在工具数量不大时不明显，在需要多套配置共存时（例如同一进程里跑不同预设）会显现。

单层内的裁决顺序是 rank、提供方顺序、本地顺序，摘要按名称排序。顺序固定意味着同名覆盖可预测。

## 4. 发现层：扫描与缓存

<iframe src="/diagrams/skill-discovery.html" title="Skill 发现的三层来源与优先级" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/340;border:0;display:block;margin:24px 0;"></iframe>

DeepSeek Harness 的 Skill 发现规则：扫描项目、自定义、用户三个根；支持目录 bundle（含 `SKILL.md`）与平铺文件（`<name>.md`）两种形态；刻意不支持发现嵌套的 `**/SKILL.md`；解析 YAML frontmatter，必填 `name` 与 `description`；监视这些根，新增、改名、删除无需重启即可到达。

不支持嵌套的理由是成本：嵌套扫描的耗时随目录深度上升，而收益（更细的组织）远小于同名冲突带来的麻烦。

缓存有一个细节：发现缓存以解析后的 scope 链为键。所以重设 scope 父级（空会话重组）无需注册表变更即可被下一次读取看到。

这个细节解决一个具体问题：会话中途切换工作目录后，哪些 Skill 适用会变。如果缓存不按 scope 链做键，切换后可能读到旧结果。

## 5. 过滤与渲染层

**过滤**决定哪些条目对当前 scope 可见。Skill 侧有三个控制字段，覆盖四种可见性：

| 组合 | 模型可见 | 用户可见 | 适用 |
| --- | --- | --- | --- |
| 默认 | 是 | 是 | 常规 Skill |
| 禁模型调用 | 否 | 是 | 危险操作、需人确认 |
| 禁用户调用 | 是 | 否 | 内部策略 |
| 都禁 | 否 | 否 | 临时停用，保留内容 |

**渲染**把条目转成面向模型的形式。这一环的核心约束是预算：目录渲染有描述长度上限，超限截断。

Claude Code 在渲染层做过两处改动，都有量化。

第一处，延迟工具只渲染名称，搜索提示不渲染。文档说明这是对照实验的结论：搜索提示没有带来收益。

第二处，代理列表从工具描述搬进附件消息。原因是列表随外部服务异步连接、插件重载、权限模式变化而变，进而使全部工具结构的缓存失效。文档给出的量化是约占全集群缓存重建的 10.2%。

两处改动的共同逻辑：渲染层决定「什么内容出现在哪个位置」，而位置决定了它变化时会波及多少缓存。

## 6. 失效层：变更如何传导

前面五环都假设「读到的是最新内容」。这一环处理读到旧内容的情况。

注册表在以下情况发失效事件：提供方变更、运行时变更。事件不带差异内容，消费方用自身的查找选项重新取快照。

这是「失效即重取」，没有做增量更新。好处是简单且不会漏；代价是每次失效都要全量重取，工具多时开销不小。

另一处细节：提供方的列举被拒绝时，系统记录日志并从不完整观测中省略该提供方的结果；显式的不完整观测提供可用候选项，但不使结果可缓存；格式错误的候选项快速失败。

三档处理分别对应三种情况：提供方挂了（省略）、提供方部分可用（标记不完整，不缓存）、数据格式坏了（快速失败）。把三者分开，避免了「一个提供方挂掉导致全部缓存不更新」这类连锁问题。

Skill 侧的失效以 scope 链为键，第 4 节已说明。

## 7. 延迟加载的机制对照

机制细节在上一篇展开。这里补实现层面的对照。

| 实现 | 延迟的触发条件 | 加载后的可见性 |
| --- | --- | --- |
| Claude Code | 不在核心白名单即为延迟 | 需显式搜索并执行 |
| Codex | 进可加载集合 | 加载后进入工具集 |
| OpenCode | 无统一机制 | 由装配决定 |
| DeepSeek Harness | 无统一机制 | 由装配决定 |

前两家有统一机制，后两家没有。这个分布与工具来源有关：当工具来源是「用户随时可能接入任意服务」时，统一延迟是必需品；当来源在部署时确定时，装配即可。

延迟机制有两种触发信号：白名单（不在名单里就延迟）与数量阈值（超过 N 个才延迟）。

白名单更可预测，但要维护名单，且名单会腐化——只增不减。数量阈值更自动，但行为会随工具数变化而突变：昨天还能直接调的工具，今天要搜索了。这个突变在生产环境里会造成困惑。

## 8. 逐层失效的具体形态

六环各有失效形态，且表现不同。把它们列齐，排障时才能从症状反推到环节。

| 环节 | 失效形态 | 症状 | 排查入口 |
| --- | --- | --- | --- |
| 声明 | 结构与实现不一致 | 接受了一个做不到的调用 | 对照结构与执行体 |
| 声明 | 该隐藏的字段泄漏 | 模型请求里出现超时、并发标记 | 检查请求体 |
| 注册 | 重名覆盖 | 调到了另一个同名的 | 打印该层全部条目 |
| 注册 | 层归属错 | 某个预设看不到本该有的工具 | 检查注册时的 scope |
| 发现 | 缓存未失效 | 新增的 Skill 不出现 | 清缓存后重试 |
| 发现 | 改名残留 | 目录里出现新旧两个名字 | 查增量更新是否处理删除 |
| 过滤 | 漏挂 | 该可见的对某些 scope 不可见 | 检查控制字段组合 |
| 渲染 | 超预算截断 | 描述被砍半，匹配信号丢失 | 统计目录总长度 |
| 渲染 | 会变内容在稳定位置 | 重连后缓存命中率骤降 | 对比前缀哈希 |
| 失效 | 增量更新漏删除 | 删掉的内容仍在生效 | 对比全量与增量结果 |

第五行与第十行同源：增量更新在「新增」上总是正确的，在「删除」上容易漏。原因是文件系统层面「改名」是删除加新增，而多数实现只处理了新增那一半。

一个便宜的防护是定期做一次全量重取并与增量结果对比。差异不为零就说明增量有问题。

## 9. 完整的读取实现

截断阈值的抽象说明不如看一个具体实现。一个文件读取工具有五个阈值协同工作。

| 常量 | 值 | 作用 |
| --- | --- | --- |
| 最大行数 | 2,000 | 单次返回的行数上限 |
| 最大字节 | 50 KiB | 单次返回的字节上限 |
| 单行最大长度 | 2,000 字符 | 单行超长时截断并加后缀 |
| 首块读取 | 256 KiB | 判定编码与是否二进制 |
| 媒体文件上限 | 20 MiB | 图片与 PDF 的内联上限 |

### 双阈值谁先到算谁

行数与字节两个上限同时生效，先到者截断。这个设计处理了一类具体情况：代码文件通常行短，2,000 行可能只有几十 KB，先撞行数；但压缩过的代码或数据文件可能三行就有几百 KB，先撞字节。

只设一个上限会出现两种失效：只设行数，遇到长行文件时会一次返回几兆；只设字节，遇到空行很多的文件时会返回几万行。

### 分页是返回结构的一部分

截断不是「截掉就完了」，它把「下一页从哪里开始」写进返回里。

返回里有一个可选字段记录下一条的行号，被截断时才有该字段。这与前文讲过的「只在真截断时报上限」是同一条原则：不截断时不给分页信息，避免模型误以为还有更多而去翻页。

分页的另外两个细节。

第一，偏移超出范围时报错，不返回空。理由是空结果会被模型理解成「文件是空的」，而实际情况是「你翻过头了」。

第二，目录列表与文本读取用同一套分页结构。这省掉了一组重复的参数定义。

### 单行截断要带可见标记

一行超过 2,000 字符时，截断并在末尾加一段说明，说明被截到多少字符。

这个标记的作用不是提示模型，是保证「内容被改过」这件事在文本里可见。没有标记的话，模型会看到一段看似完整的内容，而它实际被截断了——这比截断本身更危险。

### 二进制要先判定

读取前先读首块判断类型。判定为二进制直接报错，不返回内容。

这条的理由是二进制内容的截断没有意义：任何一段字节片段都不是「部分可见的内容」，它只是一堆乱码。返回乱码会让模型尝试从中解读，而解读结果完全是编造的。

图片与 PDF 走另一条路径，有独立的上限（20 MiB）。它们不是「读成文本」，是作为附件交给模型。

### 行定位的实现代价

这套实现里有一处值得注意的工程细节：为了在不解码全文的前提下定位第 N 行，它用一个按子树记录字节数与换行数的结构维护已读块。查找某一行变成一次顺序统计查询。

这个优化不是必需的——多数文件不大，直接解码再切分也能用。它只在两种情况有价值：文件极大（几十 MB）且需要随机偏移读取；同一文件在一个会话里被多次按行读取。

记录它是因为它说明一件事：**读工具的分页不是简单的数组切片**，当文件大到不能整读时，行号定位本身需要数据结构支持。

## 10. 结果侧的截断阈值

四个实现的阈值与量纲对比：

| 实现 | 阈值 | 超限动作 |
| --- | --- | --- |
| Claude Code | 20,000 字符（内容搜索） | 触发持久化，完整内容写文件 |
| Codex | 按内容类型选择策略 | 截断加外置 |
| OpenCode | 2,000 行 / 50 KiB | 原文落盘，返回预览与路径 |
| DeepSeek Harness | 20 MB 原始输出 / 250 条匹配 / 2,000 字节单行 | 溢出则失败；超内联上限写外置并给定位 |

四处差别值得注意。

**量纲不同。** 字符、行加字节、原始输出大小。这反映各家对「什么会爆」的判断不同：Claude Code 认为字符数最直接，OpenCode 认为行数与字节都要管，DeepSeek Harness 认为原始输出与内联展示要分开管。

**超限动作分两类。** 截断并继续（前三家），与直接失败（DeepSeek Harness 的原始输出溢出）。后者的理由是不解析不完整的流——截断后解析出来的结果是不完整的，而模型无法知道它不完整。

**只有部分实现区分内联上限与原始输出上限。** 区分开的好处是内联可以小（省窗口），原始输出可以大（不丢数据），中间用外置存储衔接。

**单行长度限制只有部分实现有。** 这条处理压缩过的代码（minified JS）时必需——那种文件可能只有三行，每行几万字符。

## 11. 权限模型的三种粒度

| 粒度 | 表达能力 | 盲区 |
| --- | --- | --- |
| 工具名级 | 「这个角色不能写文件」 | 不能表达「只能写某些路径」 |
| 权限动作级 | 「能用 shell，shell 内写操作单独授权」 | 依赖每个工具正确声明 |
| 策略与命名空间级 | 按命名空间整体开关 | 粒度仍在工具层 |

三家都做不到参数级白名单。这类限制通常靠沙箱或文件系统权限实现，不在工具层的职责内。

## 12. 三条判断

### 注册表分层何时必需

判据是是否有两个以上的配置需要在同一进程内共存。没有，装配即可；有，需要分层。

这条判断的实际意义在于：分层是成本，它要求每个提供方想清楚自己属于哪一层。只有一套配置时，分层的收益为零。

### 延迟加载的触发信号

白名单与数量阈值的选择，取决于工具集的变化频率。工具集稳定（部署时确定），用数量阈值；工具集频繁变化（用户随时接入），用白名单加显式标记。

### 三条判断的共同前提

三条判断都假设一件事：工具与 Skill 的数量会增长。如果数量固定（例如一个专用 Agent 只有五个工具），所有判断都不重要——五个工具全量注入即可，不需要分层、不需要延迟、不需要取舍。

数量增长带来的不只是成本，还有排序问题：新增的条目该放在哪一层、该不该常驻、与已有条目是否冲突。第 11 节的清单与第 3 节的分层，都是为了在增长时保持可预测。

### Skill 与工具的取舍

同一个能力可以用 Skill 描述（告诉模型怎么做）或工具实现（让模型直接调）。

| 方式 | 占用 | 稳定性 | 适用 |
| --- | --- | --- | --- |
| 工具 | 固定定义空间 | 执行稳定 | 无需中间判断的动作 |
| Skill | 目录少量加正文几 KB | 模型按步骤执行，可能偏 | 需要中间判断的流程 |

判断标准是这个能力是否需要模型在中间做判断。需要，用 Skill（模型能变通）；不需要，用工具（执行稳定且省 Token）。

如果一个能力既需要判断又步骤固定，拆开：Skill 写判断原则与流程，工具写可执行步骤。

## 13. 配置分层与工具可见性

工具的运行时行为常受配置影响，而配置的层数决定了「同一份代码在不同部署里行为不同」的范围。

一个完整的配置分层通常有四到五层，优先级从高到低：命令行参数、环境变量、项目配置、用户配置、内置默认。

对工具系统来说，有两类配置需要单独考虑。

**影响工具可见性的配置。** 例如「哪些外部服务被信任」「哪些工具被禁用」。这类配置的改动会让工具集变化，进而让缓存失效。它们应当被当作装配期配置，改动后要求重启或显式刷新。

**影响单次调用行为的配置。** 例如超时、结果上限、是否沙箱。这类配置可以运行期改，但必须不进入模型请求——一旦进入，每次改动都会破坏前缀缓存。

区分两类的判据是：改动它会不会改变「模型看到什么」。会，属于装配期；不会，属于运行期。

一个常见错误是把运行期配置写进工具描述（例如把当前超时值渲染进描述）。后果是每次调超时都要重建全部工具结构，而超时本来与模型无关。这与代理列表从描述搬到附件是同一类问题：会变的内容不该待在稳定位置。

## 14. 完整接入的记录

清单是抽象的，一次真实接入的记录更能说明每一项要落到什么程度。

假设要给一个已有的 Agent 加一个「查询工单状态」的工具。

**声明。** 结构里只有两个字段：工单号（字符串，必填）与是否包含历史（布尔，默认否）。输出声明三段：状态（枚举：待处理、处理中、已完成、已关闭）、摘要（一句话）、历史（可选数组）。

这里有两个决定：工单号不设格式校验（各团队格式不同，校验过严会拒绝合法输入）；历史做成可选（多数查询不需要历史，默认返回会让结果体积翻倍）。

**注册。** 归属全局层——它不依赖任何特定项目。提供方名称用「工单」这个领域词，不与已有条目重名。

**发现。** 它不是文件系统条目，是代码注册，所以不涉及扫描路径。

**过滤。** 需要决定它对哪些 scope 可见。一个考虑：它需要访问外部系统，而某些 scope 可能不允许外部访问。这种情况下应当按 scope 分层注册，不放全局层。

**渲染。** 描述长度控制在 200 字节内：说清「查工单状态」、排除「不用于创建或修改工单」、说明返回什么。不写实现细节。

**失效。** 代码注册的变更随版本发布生效，不涉及运行期失效。但要注意：如果描述里嵌了「当前支持的状态值」这类会随外部系统变化的内容，它就成了会变内容待在稳定位置。

六项过完之后还有一件事：用一个明显该选它的任务与一个明显不该选它的任务各测一次。前者验证能被选中，后者验证不会被误选。

两个测试都通过，才算接入完成。只测前者是常见的疏漏——它能被选中，但不该被选中的时候也被选中，代价是每次误选一次无效调用。

## 15. 新工具的接入清单

按六环逐项过。

**声明。** 结构与执行体分开；输出声明独立于入参结构；实现细节不进模型请求。

**注册。** 确定归属层；提供方名称在该层内唯一；rank 只在需要覆盖时使用。

**发现。** 确认扫描路径包含它的位置；不支持嵌套时不要放在子目录。

**过滤。** 确认它对哪些 scope 可见；是否需要「禁模型调用」或「禁用户调用」。

**渲染。** 描述长度是否在预算内；有没有会随运行时变化的内容，如果有，考虑放到附件。

**失效。** 变更能否被感知；如果是增量更新，改名与删除是否都处理了。

六项之后再做一件事：用「故意写错的描述」测一次，看模型是否会误选。这个测试能暴露描述层的缺口，成本只有一次调用。
