# 渐进式披露与按需注入

## 1. 六十个 MCP 工具之后

一个团队接了六个 MCP 服务：GitHub、Jira、Confluence、数据库、监控、文档检索。每个服务暴露 10 到 25 个工具，合计上百个。

接入后的第一个现象是模型开始选错工具：让它查 Jira 工单，它调了 GitHub 的 issue 查询。第二个现象更隐蔽——即使选对了工具，参数也经常填错，因为同一批工具里有三个都叫 `search`，参数结构各不相同。

第三个现象最贵：上下文占用从 30 KB 涨到 120 KB，每一轮都要付，缓存命中率明显下降。

这不是某一家的特殊问题。任何接入多个 MCP 服务的 Agent 都会遇到。四家 Coding Agent 各自给了答案，但答案的形式差别很大。

## 2. 规模账

先把账算清。窗口里被五类内容占据：系统提示、内置工具定义、MCP 工具定义、Skill 目录、历史消息。

| 内容 | 量级 | 是否随服务数增长 |
| --- | --- | --- |
| 系统提示 | 8–20 KB | 否 |
| 内置工具定义 | 10–40 KB | 否 |
| MCP 工具定义 | 每个服务 5–25 KB | 是，无上限 |
| Skill 目录 | 每条 0.1–0.2 KB | 是，增长慢 |
| 历史消息 | 可变 | 由压缩控制 |

前三项之和是「工具与 Skill 规模账」的主体。它们不随任务推进变化，却每轮都要付。

设第 $j$ 个服务暴露 $m_j$ 个工具，每个定义平均 $a$ 字节，共 $k$ 个服务，则 MCP 工具定义的总量是：

$$
c = a \sum_{j=1}^{k} m_j
$$

取 $k = 6$、$m_j = 20$、$a = 450$ 字节：$c \approx 54000$ 字节，约 54 KB。这是六个服务、每个 20 个工具的规模。如果接到十个服务，就是 90 KB。

关键在于这个数字与「当前任务需不需要这些工具」无关。一个只要求「改这一行代码」的任务，也要付这 90 KB。

## 3. 五种注入方式

按常驻成本从高到低：

<iframe src="/diagrams/toolskill-injection-modes.html" title="五种注入方式的成本与风险" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/400;border:0;display:block;margin:24px 0;"></iframe>

### 全量注入

所有工具定义常驻。零延迟，占窗口最大，且随服务数线性增长。

适用条件只有一个：工具总数很少（例如十个以内）且每个都可能被用到。超过这个规模，全量注入的边际成本会超过它带来的便利。

### 核心常驻加其余按需

把最常用的几个工具常驻，其余进「待加载」集合。模型平时看到的是这些工具的名字，需要时按名加载定义。

这是 Claude Code 的做法，后面详述。

### 名称目录加正文按需

常驻所有工具的名称（不含参数结构），正文按需加载。

与上一种的差别在于：它常驻的是**全部名称**，不是「常用的几个定义」。常驻成本低得多（每个名称几十字节），但模型要在上百个名称里找到对的那个。

### 检索式发现

零常驻，模型必须先搜索工具再调用。两段式：搜索、执行。

常驻成本最低，但首次调用多一次往返，且漏选风险最高——如果搜索没找到，模型会认为「没有这个能力」。

### 命名空间分组

按服务分组，组内仍需枚举。粒度介于前几种之间。

分组解决的是「同名冲突」，对总量帮助有限：`github.search` 与 `jira.search` 不会混，但两者仍然都占空间。

### 五种方式的定量对照

用第 2 节的规模（6 个服务、120 个工具、平均 450 字节）估算：

| 方式 | 常驻成本 | 首次调用延迟 | 漏选风险 | 缓存影响 |
| --- | --- | --- | --- | --- |
| 全量注入 | 54 KB | 0 | 低 | 稳定前缀，命中高 |
| 核心常驻 | 约 6 KB + 名称表 | 一次加载 | 中 | 名称表稳定 |
| 名称目录 | 约 5 KB（120 个名字） | 一次加载 | 中 | 名称表稳定 |
| 检索式发现 | 约 0.5 KB | 两段式 | 高 | 目录变化破坏前缀 |
| 命名空间分组 | 约 8 KB | 一次加载 | 中 | 分组稳定 |

这张表里有一个反直觉的结论：**检索式发现的常驻成本最低，但它对缓存最不友好**。原因是目录内容随查询变化，每轮的前缀都不同，缓存无法复用。

而全量注入虽然常驻 54 KB，但它是稳定的前缀，按缓存折扣计价后实际开销远低于表面数字。设缓存命中价格为正常价格的十分之一：

$$
c' = \alpha f + v
$$

全量注入的 54 KB 全在 $f$ 里，实际约 5.4 KB；检索式发现的目录在 $v$ 里，每轮全价，虽然只有 0.5 KB，但加上两段式往返的开销，总量未必更低。

这条算式解释了为什么四家的选择不完全一致：它们对缓存折扣的假设不同，对延迟的容忍度也不同。

## 4. 四家的解决方案

### Claude Code：核心白名单加延迟集合

机制上有三层。

**第一层，核心工具白名单常驻。** 读文件、编辑、写文件、执行命令、文件匹配、内容搜索、子代理、网页抓取、网页搜索、技能。这十个左右永远在，不在延迟集合里。

**第二层，其余全部延迟。** 判定逻辑很直接：不在核心白名单里、且没有显式标记「总是加载」的工具，一律进入延迟集合。这包括全部非核心内置工具与全部 MCP 工具。

**第三层，两段式调用。** 延迟工具不能直接调用，必须先搜索再执行：

```text
第一步：SearchExtraTools({"query": "select:CronCreate"})
        → 返回：找到 CronCreate，用 ExecuteExtraTool 调用
第二步：ExecuteExtraTool({"tool_name": "CronCreate", "params": {...}})
        → 返回：实际工具结果
```

搜索支持四种查询形态：

| 形态 | 写法 | 用途 |
| --- | --- | --- |
| 精确名 | `select:CronCreate` | 已知名字时最快 |
| 多选 | `select:CronCreate,CronList` | 一次拿多个 |
| 取详情 | `discover:schedule cron job` | 返回名称、描述、schema 但不加载 |
| 关键词 | `cron schedule` | 不知道确切名字时 |
| 必含词 | `+slack send` | 要求名字含某词，其余词参与排序 |

四种形态的设计意图很清楚：已知名字时省一次检索（精确名），不知道名字时给模糊匹配（关键词），需要先看再决定时给「取详情」这一档。

**一个值得注意的约束。** 提示词里明确写：如果执行失败，不要重复搜索同一个工具，会陷入循环，应当停下并告知用户。这条约束针对的是一个具体故障：搜索成功但执行失败时，模型倾向于「再搜一次确认」，而这只是重复同样的失败。

**延迟工具的呈现方式。** 只有工具名出现在附件里，`searchHint` 不渲染。文档里说明这是做过 A/B 的结论：搜索提示没有带来收益。这条结论值得记，因为它违背直觉——直觉上多给一点提示应该有帮助。

**另一处缓存优化。** 代理列表原本嵌在 AgentTool 的描述里，导致描述随 MCP 异步连接、插件重载、权限模式变化而变，进而使全部工具 schema 的缓存失效。文档给出的量化是：约占全集群缓存重建的 10.2%。修法是把列表挪进附件消息，让工具描述保持静态。

这条改动是「缓存视角」的典型例子：它不减少任何内容，只是把会变的内容从不该变的位置挪走。

**Skill 侧的按需。** 目录常驻，另有发现工具用 TF-IDF 在全部已注册 Skill 上排序返回。这解决的是「目录里没有明显匹配时」的情况。

### Codex：独立搜索工具

把搜索做成一个独立工具，与「可加载工具」分开。搜索结果默认返回 8 条，来源描述的总预算 512 KB。

与 Claude Code 的差别在于：Codex 的搜索是一个独立的、模型可正常调用的工具，不需要「先搜再执行」的两段式协议——搜到的工具直接出现在工具集里。

这个设计简化了调用流程（少一次协议往返），代价是工具集的动态变化需要被正确处理：加载一个工具后，模型下一轮才看到它。

### OpenCode：按位置装配

没有统一的延迟工具池。工具按位置装配：每个叶子工具自己声明需要什么权限动作，能力由所在的组合决定。

这个设计的收益是权限粒度细（可以表达「能用 shell，但 shell 里的写操作要单独授权」）。代价是没有「全局的工具预算」概念：要减少常驻得改装配配置，没有统一的延迟机制可用。

工具输出侧的默认限制是 2,000 行、50 KiB，超限落盘。这个限制与注入侧无关，但同样影响窗口。

### DeepSeek Harness：注册表分层

工具注册表与 Skill 注册表都采用「宿主层 + scope 层」的分层结构。注册落入调用方 scope 对应的层，读取时把全局层与观察 scope 的链合并，最近层的条目直接赢得重名。

单层内的裁决顺序是 rank、提供方顺序、本地顺序。摘要按名称排序。

这个设计解决的是「谁覆盖谁」，对注入只有间接影响：分层让「某个 scope 只需要某几个工具」成为可能，从而减少该 scope 的常驻量。

Skill 侧的特性：目录渲染有描述长度上限；`disable-model-invocation` 可以把 Skill 从模型目录与加载器中排除；发现只扫根目录一层，刻意不支持嵌套。

## 5. 判断顺序

五种方式怎么选，按四步走。

**第一步，工具是否每轮都要用。** 是，全量注入或核心常驻。多数任务的工具使用集中在少数几个上，全量注入的收益率很低。

**第二步，首次调用延迟能否接受。** 交互式对话里，多一次往返是可感知的；批处理任务里，几乎无感。

**第三步，漏选代价有多高。** 漏选一个只在特定场景用的工具，代价是那次任务失败重试；漏选一个关键工具，代价是模型绕路或用错方式完成。后者严重得多。

**第四步，缓存是否命中。** 稳定的常驻内容按折扣计价，变化的目录按全价。这一项常被忽略，但它在长任务里的影响超过前两项。

四步之后的选择通常落在「核心常驻 + 其余延迟」——它在延迟、漏选、缓存三项上都没有明显短板。

## 6. 失败模式

**延迟工具直接调用。** 症状：模型调用了一个不在当前工具集里的工具，协议层报错。成因：模型看到了延迟工具的名称（在附件或目录里），以为可以直接调。修法：在延迟工具的名称附近明确写「不能直接调用，需先搜索加载」。

**两段式之间的状态漂移。** 症状：搜索返回了工具 A，执行时用了工具 B 的参数。成因：两段式需要模型自己记住搜索结果与参数的对应。修法：搜索返回时把 schema 一起给出，减少模型凭记忆重建参数。

**目录过长导致选择困难。** 症状：常驻的名称表太长，模型在表里找不到对的那个。成因：名称不含足够语义（`svc1_search`、`svc2_search`）。修法：名称里带领域词，或改用分组。

**MCP 连接变化引发前缀失效。** 症状：每次 MCP 服务重连，整个工具 schema 的缓存失效。成因：工具定义嵌在稳定的系统提示位置，内容一变前缀全废。修法：把会变的部分移到附件，保持主前缀静态。

第四条是 Claude Code 那段 10.2% 的直接来源，也是最容易被忽略的一类成本——它不在任何一次调用的账单上，而在整体吞吐上。

## 7. 小结与交接

工具与 Skill 的注入问题，本质是把「有限窗口」分配给「可能有用」与「确定要用」两类内容。五种方式是这个分配的五个刻度。

四家的答案不同，但有个共同点：没有一家把所有工具一次性常驻。这说明这个上限在实践中很早就会撞到。
