# 工具设计

## 1. 工具在上下文里承担三条通道

一个工具在模型看来是三类信息，不是一个函数签名。

**定义通道**：工具名、描述、参数结构。它决定模型是否选中这个工具。
**调用通道**：模型填写的参数。它决定调用是否成功。
**结果通道**：工具返回的内容。它决定模型能否据以做下一步决策。

三条通道各有独立的失真方式，也各有独立的成本。

分开看能解释一个常见现象：一个工具「看起来写得挺好，但就是用不对」。多数时候是三条通道里有一条坏了，而修的人只盯着另一条。例如模型选对了工具但参数填错，问题在调用通道，改描述解决不了。

## 2. 定义通道的固定成本

定义通道的成本固定且每轮支付。设第 $i$ 个工具的名字与参数结构占 $s_i$ 字节、描述占 $d_i$ 字节，$n$ 个工具的总占用是：

$$
c = \sum_{i=1}^{n}\left(s_i + d_i\right)
$$

$s_i$ 通常在 80 到 150 字节（工具名、参数名、类型、必填项），$d_i$ 通常 200 到 650 字节。描述占七成以上。

实际体量比直觉大。Claude Code 全部工具提示词文件合计约 135 KB，其中几个单项：

| 工具 | 提示词体量 | 说明 |
| --- | --- | --- |
| 命令执行 | 20.8 KB | 含后台运行、超时、沙箱、提交规范等多段 |
| 子代理 | 11.9 KB | 含角色列表、分叉语义、并行要求 |
| PowerShell | 9.8 KB | 与命令执行对齐的 Windows 版 |
| 待办列表 | 9.5 KB | 使用时机与格式约束 |
| 技能调用 | 8.3 KB | 加载规则与调用形式 |
| 延迟工具搜索 | 4.3 KB | 两段式协议与失败策略 |

单轮请求的工具部分就要几十 KB。代入 $n = 200$、平均 450 字节，得到 90 KB，在 200K Token 窗口里约占 11%——而这 11% 与当前任务是否相关无关。

成本随 $n$ 线性增长，但**判断负担不是线性的**。工具越多，模型越可能选错或漏选，因为相似工具之间需要更精细的区分。这解释了为什么单纯缩短描述解决不了问题：$d_i$ 减半，$c$ 减半，$n$ 不变，选择困难照旧。

正确的优化顺序是先减少常驻数量（延迟加载），再考虑缩短长度。

## 3. 定义通道的区分度

描述写对了，模型仍然选错，最常见的原因是区分度不足。

三份递进的定义，同一件事。

```json
{
  "name": "search",
  "description": "搜索内容",
  "parameters": {"type": "object"}
}
```

第一份几乎无法使用：参数结构为空，模型不知道传什么；描述没有说明搜索什么、返回什么。

```json
{
  "name": "search_web",
  "description": "搜索公开网页",
  "parameters": {
    "type": "object",
    "properties": {"query": {"type": "string"}}
  }
}
```

第二份能跑了，但仍有缺口：多长的查询合适？返回几条？能不能搜内部文档？

```json
{
  "name": "search_web",
  "description": "搜索公开网页。适合查找当前行业资料和竞品信息；不用于读取团队内部文档。返回标题、摘要、发布日期和 URL。query 必须是具体问题，不要传入整段任务描述。",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "要搜索的具体主题"},
      "max_results": {"type": "integer", "minimum": 1, "maximum": 10}
    },
    "required": ["query"]
  }
}
```

第三份写清四件事：使用场景、排除场景、返回内容、输入粒度。

四件事里最容易被省略的是排除场景。写「不用于什么」看起来浪费字节，但它解决最常见的一类误选——模型知道这个工具能搜，就什么都搜。

另外两类信息值得写进描述。

**工具之间的先后关系。** 例如「先读取文件，再编辑文件」「发送消息前先展示草稿」。这类约束写在任何一个单独的工具描述里都不完整，但写在主流程相关的工具上能起作用。

**已知陷阱。** Claude Code 的搜索工具描述里写了三条：正则里的字面大括号要转义、跨行匹配要显式开启、结果被截断时考虑更精确的模式。这三条把常见错误前置到了错误可能发生的地方。

### 命名也是区分度

工具数量超过几十个时，命名的信息量开始决定选择质量。

`svc1_search`、`svc2_search` 这类名字没有领域词，模型只能靠描述区分，而描述在长列表里容易被跳过。`search_issues`、`search_docs`、`search_web` 把范围写进名字，选择就变成模式匹配，不必逐字读描述。

这条与延迟加载的分组策略相关：分组解决同名冲突，命名解决同名共存时的可读性。两者都需要。

## 4. 调用通道：合法性与语义正确性

定义通道决定「选不选」，调用通道决定「填得对不对」。两者之间有一条容易混淆的分界：schema 只能检查形状，检查不了意图。

参数错误分两类，schema 只管第一类。

参数错误分两类，schema 只管第一类。

| 类型 | 例子 | 谁能发现 |
| --- | --- | --- |
| 语法不合法 | 必填项缺失、类型错、枚举值超范围 | schema |
| 语义不正确 | 路径存在但指错了文件、查询词太宽泛、时间范围反了 | 工具实现或模型自己 |

第二类无法在 schema 层面拦截，只能靠三件事降低概率。

**枚举优于自由文本。** 一个参数如果只有几种合法取值，用枚举声明。模型从枚举里选比从零生成稳得多，而且 schema 层面就能拒绝非法值。

**必填最小化。** 只把真正必须的参数设为必填。必填项越多，模型越可能在信息不足时编造。其余参数给合理默认值。

**一次调用完成一件事。** 如果完成一个语义动作需要三次调用（创建、配置、启动），考虑提供合并工具。每次调用都是一次往返，往返多了中途出错的概率上升。

第三个原则有个例外：合并工具会让单个工具的语义变复杂、描述变长。判断标准是能否用一句话说清「它做什么」。能，就合并；不能，就保持分开。

## 5. 结果通道：四段式结构

工具返回一段长字符串是最常见的设计缺陷。模型要自己从中提取状态、结论、后续动作，而它可能读错，尤其在内容被截断时。

四段式把这件事拆开。

```json
{
  "status": "success",
  "summary": "找到 5 个结果，其中 3 个与会议纪要相关。",
  "items": [
    {"title": "企业协作趋势报告", "url": "https://example.com/report", "date": "2027-02-11"}
  ],
  "artifact": "artifacts/search/call_01.json",
  "truncated": false
}
```

四段的分工：

| 字段 | 作用 | 谁用 |
| --- | --- | --- |
| `status` | 决定下一步动作 | 模型判断继续、重试、改参、报告 |
| `summary` | 一两句话给结论 | 模型默认读这段 |
| `items` | 结构化数据 | 需要精确判断时 |
| `artifact` | 原始产物路径 | 出错后追溯 |

`truncated` 这个布尔值看起来多余，但它解决一个具体问题：模型无法从内容判断「是不是全部」。显式声明截断，模型才知道该不该继续取。

### 失败分类决定恢复动作

失败不能只回一个错误字符串，因为不同的失败需要不同的恢复动作。

| 分类 | 含义 | 恢复动作 | 典型错误 |
| --- | --- | --- | --- |
| 可重试 | 临时故障 | 稍后重试，通常带退避 | 限流、锁冲突、网络 |
| 需改参 | 参数非法或模式错误 | 改参数再调 | 正则语法、枚举越界 |
| 环境问题 | 依赖缺失、路径不可达、权限拒绝 | 换路径或报告环境 | 文件不存在、权限不足 |
| 中止 | 超时、调用方取消 | 可重试，也可放弃 | 超时、取消信号 |

四类混在一起时，模型的默认行为是重试，而「需改参」这一类重试多少次都不会成功。DeepSeek Harness 的搜索工具给出了一个正面例子：四类错误码各自对应一种恢复动作，并且明确区分「成功且有结果」（退出码 0）与「成功的空搜索」（退出码 1）。把空结果与失败分开，模型才不会把「查无此项」当成「工具坏了」。

## 6. 三条通道的相互牵制

设计一条通道的改动，常常在另一条通道上产生成本。

**延迟加载。** 省了定义通道的每轮成本，但增加了调用通道的一次往返：延迟工具不能直接调用，必须先搜索再执行。这个往返在「确实需要这个工具」时值得付，在「其实用常驻工具也能做」时是浪费。

**结果截断。** 省了结果通道的体积，但增加了模型误判的风险：它可能把不完整当完整。缓解办法是显式标注截断并给出「还有多少」的估计。

**合并工具。** 省了调用通道的往返次数，但增长了定义通道的描述，也压缩了模型在中间的判断空间。

三条通道的相互牵制意味着优化不能只盯一处。一个常见错误是在定义通道上狂删描述来省 Token，结果选择准确率下降、调用通道的失败往返增加，总量反而上升。

## 7. 权限与副作用检查

schema 只能检查类型、必填项、枚举值。运行时要另做检查：

```text
模型生成参数
    ↓
schema：类型、必填、范围
    ↓
业务检查：权限、路径范围、重复动作、风险等级
    ↓
执行
    ↓
结果：状态、摘要、结构化数据、产物路径
```

第二层的检查项里，「重复动作」最容易被忽略。同一个删除请求被执行两次，结果通常比执行一次更糟，而且模型不知道为什么失败。

第三类是「不可逆动作」：删除、覆盖、对外发送。这类动作建议独立授权：把「不可逆」作为工具的一个属性，由外层策略决定是否需要额外确认，不必每次调用都问人。

有一处分界要划清：工具层能做的是「拒绝执行」，做不到「保证内容安全」。一个写入工具可以限制只能写某个目录，但不能判断写进去的内容是否恰当。后者属于提示词与审核的职责。

## 8. 完整样例：代码搜索工具

三条通道都做到位的工具不多，代码搜索工具是最完整的一个。把它的设计拆开看，能看清三条通道如何配合。

### 定义通道

参数结构里有九个可调项，其中三项直接服务于「减少结果体积」：

| 参数 | 取值 | 默认 | 作用 |
| --- | --- | --- | --- |
| 输出模式 | 内容、文件路径、计数 | 文件路径 | 决定返回什么形状 |
| 结果上限 | 整数，0 表示不限 | 250 | 决定返回多少条 |
| 偏移 | 整数 | 0 | 从第 N 条开始 |

默认输出模式选「文件路径」，不选「内容」，这个选择很关键：多数搜索的真实目的是「找到是哪些文件」，内容可以在确定文件之后按行读取。默认给路径，把「读内容」变成一次显式选择。

描述里还有两条效率提示：按文件类型过滤比按通配符更高效（前者用语言类型索引，后者要遍历路径）；多行模式默认关闭，需要跨行匹配时显式开启。

另有一条隐含的过滤：版本控制目录（`.git`、`.svn`、`.hg`、`.bzr`、`.jj`、`.sl`）自动排除。这类目录里的内容几乎总是噪声，排除它们相当于给结果做了一次免费的去重。

### 调用通道

三个参数之间的相互作用写得很细：上下文行数（前、后、前后）只在内容模式下有效，其他模式忽略；行号默认开启；偏移与上限的语义是「先跳过 N 条，再取 M 条」，等价于命令行的 `tail -n +N | head -N`。

这种「参数只在某模式下有效」的设计是有代价的：模型可能填了无效组合。但它比重载三个不同的工具更省定义空间——一个工具加九个参数，比三个工具各带三个参数占得少。

### 结果通道

截断的表达方式值得单独看。设计里有两条规则：

第一，只有在真的发生截断时才报告上限值。没有截断时不报告，避免模型误以为「有更多结果」而去翻页。

第二，上限为 0 表示不限，但描述里明确写「谨慎使用——大结果集浪费上下文」。

第一条是四段式结构里 `truncated` 字段的更精细版本：不只告诉「是否截断」，还告诉「当前限的是多少」。这让模型能判断该不该用偏移继续取。

结果体积还有一个上限：内容超过约 20 KB 时落盘，模型拿到的是预览加路径。在没有这个上限的会话里，密集使用搜索会让工具结果占到几万 Token。

### 三条通道在这个工具上的配合

定义通道用默认值压低体积（默认只给路径、默认 250 条上限）。
调用通道用枚举把选择收窄（三种输出模式，不是自由文本）。
结果通道在真的截断时才报告上限，避免误导。

三处配合的结果是：同一个工具在「只想看看有哪些文件」和「要读具体匹配行」两种场景下都能用，而不需要两个工具。

代价是参数多、交互复杂。一个只有三个参数的工具更容易被正确使用，但它无法同时服务两种场景。这个取舍与第 6 节讲的「合并工具」是同一条判断：合并后能否用一句话说清它做什么。这个工具能——「按模式搜索代码并返回匹配」。

## 9. 四家的实现对照

| 维度 | Claude Code | Codex | OpenCode | DeepSeek Harness |
| --- | --- | --- | --- | --- |
| 定义体量 | 最大（单工具 20 KB 级） | 中等 | 较小 | 中等 |
| 输出声明 | 最大结果字符数 | 按内容类型选策略 | schema | 强制规范输出声明 |
| 失败表达 | 错误文本 | 错误码 | 错误类型 | 四类错误码 |
| 权限粒度 | 工具名级 | 策略与命名空间 | 权限动作级 | 执行守卫 |
| 结果截断 | 20,000 字符触发持久化 | 截断加外置 | 2,000 行 / 50 KiB | 超内联上限写外置 |

一处值得单独说：DeepSeek Harness 的 `output` 字段是强制的，且出现在「不得泄漏到模型请求中」的字段清单里。这个设计把「工具返回什么」定为强制约定：调用方不必猜返回结构，宿主可以按 schema 校验。

Claude Code 走的是另一条路：把大量约束写进描述（例如搜索工具的三条陷阱），正确使用靠提示词保证，不靠 schema。代价是描述很长，收益是模型在失败前就知道该避开什么。

## 10. 通道的度量

三条通道各自有可观测的指标。这些指标的价值在于它们能提前发现问题，而不必等到效果变差。

| 通道 | 指标 | 怎么测 | 异常信号 |
| --- | --- | --- | --- |
| 定义 | 单次任务选错工具的次数 | 对比选中的工具与期望工具 | 持续大于零 |
| 定义 | 常驻体积 | 统计全部定义字节数 | 随接入服务线性上升 |
| 调用 | 参数错误率 | 四类失败里「需改参」的占比 | 高于 10% |
| 调用 | 一次成功率 | 首次调用即成功的比例 | 低于 70% |
| 结果 | 截断率 | 触发截断的调用占比 | 高于 15% |
| 结果 | 模型追问率 | 拿到结果后又问「还有吗」的比例 | 高于 5% |

第三行与第四行要一起看。参数错误率高而一次成功率低，说明 schema 写得太松；参数错误率低而一次成功率仍低，说明错误发生在执行阶段（环境问题、超时），不在参数。

第五行与第六行的关系同第三第四行。截断率高是正常的（大结果本来就该截），但截断后模型追问率高说明截断方式有问题——它没让模型知道还能取多少。

### 诊断顺序

拿到「工具用不对」的反馈之后，按这个顺序查：

1. 看选错还是填错。选错归定义通道，填错归调用通道。
2. 选错的话，看是不是同名或描述过泛。用「明显该选它」与「明显不该选它」各测一次。
3. 填错的话，看是 schema 拒绝还是执行失败。前者改 schema，后者看错误分类。
4. 都不是的话，看结果。模型是不是把部分成功读成了成功，或把截断当完整。

四步走完基本能定位。跳过第一步直接改描述是最常见的误修——填错参数时改描述不会有用。

## 11. 工具调用的完整往返

把三条通道串起来，看一次调用从决策到结果的完整路径，能看清每一环的时间与成本。

```text
模型读到全部工具定义（定义通道，每轮固定成本）
    ↓
模型输出工具名与参数（一次生成，参数越多越长）
    ↓
schema 校验（本地，微秒级；失败即返回「需改参」）
    ↓
权限与业务检查（本地或远程；失败即返回「环境问题」）
    ↓
执行（可能几毫秒到几分钟）
    ↓
结果整形（截断、四段式、落盘）
    ↓
模型读到结果，决定下一步（结果通道）
```

七步里，只有第三步与第六步是纯粹的工具层责任，其余各步都有别的层参与。

**第二步的成本与参数数量成正比。** 一个九参数的工具，模型要生成九个键值对；一个三参数的工具只需三个。这是合并工具的隐含成本：它省了往返，增加了每次生成的 Token。

**第三步失败是最便宜的失败。** 本地校验在微秒级完成，不产生任何外部副作用。所以 schema 应当尽量严格——严格在这里没有代价。

**第四步失败次便宜。** 它可能要访问外部系统，但通常不产生副作用。

**第五步失败最贵。** 一次执行到一半失败，可能留下了部分状态：写了半个文件、创建了资源但没配置完。这类失败需要清理，而清理本身可能失败。

**第六步是唯一可以「花小钱省大钱」的一步。** 结果整形多花几十字节（摘要、计数、截断标记），能避免模型误判后的整轮返工。

这条路径解释了一个设计优先级：先保证第三、四步的失败是干净且分类明确的，再优化第六步的信息量，最后才考虑合并工具减少第二步。

顺序反过来（先合并工具）会让失败变得更难处理——一次调用做了三件事，第二件失败时前两件已经生效。

## 12. 失败模式按通道归类

| 通道 | 失败模式 | 症状 | 修的位置 |
| --- | --- | --- | --- |
| 定义 | 同名不同义 | 模型反复试不同工具 | 名字里加范围词 |
| 定义 | 描述与实现漂移 | 按描述使用却得到意外结果 | 描述随实现同步改 |
| 定义 | 工具过多 | 选择困难 | 分层：核心常驻、其余延迟 |
| 调用 | 自由文本参数 | 参数宽泛导致结果无用 | 改枚举、加范围限制 |
| 调用 | 必填过多 | 信息不足时编造 | 必填最小化 |
| 结果 | 长字符串 | 模型提取错状态 | 四段式结构 |
| 结果 | 隐式截断 | 把不完整当完整 | 显式标注与计数 |
| 结果 | 失败未分类 | 一律重试 | 四分类加对应恢复动作 |

第二行最难发现，因为它不报错，只是效果慢慢变差。一个具体的检查方式：拿工具描述与最近一次真实调用的参数对照，看描述里承诺的返回字段是否真的存在。这个检查很便宜，但很少有团队做。

## 12. 工具设计的检查清单

按三条通道逐项过。

**定义通道。**

- 名字里带范围词，不用 `search` 这类通名；
- 描述写清使用场景、排除场景、返回内容、输入粒度；
- 与其他工具的先后关系写在其中一方；
- 已知陷阱写在描述里；
- 参数有枚举时用枚举。

**调用通道。**

- 必填项只有真正必需的那些；
- 每个参数有默认值或范围说明；
- 一次调用能完成一件事。

**结果通道。**

- 返回四段式；
- 截断显式标注并给计数；
- 失败按四类区分并各给恢复动作；
- 空结果与失败分开表达。

三条通道都过一遍之后，再考虑是否延迟加载。顺序不能反：一个设计有问题的工具，延迟加载只会让它更难被发现。
