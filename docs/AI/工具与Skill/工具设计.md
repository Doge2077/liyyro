# 工具设计

## 1. 模型选错了工具

一个 Agent 有三个搜索类工具：`search`、`find`、`lookup`。描述分别是「搜索内容」「查找文件」「查询信息」。任务要求找出一个函数定义，模型调了 `search`，返回一堆网页结果；它又调了 `find`，返回文件路径列表；最后才试 `lookup`，拿到了代码。

三次调用里两次无效。问题不在模型能力——三个描述都在说「找东西」，没有任何一个说明自己处理的是代码、网页还是文件路径。

工具设计的核心问题就在这里：**工具是上下文里的动作说明，它的目标是让模型做对选择**。不是给人看的功能目录，也不是 API 文档的转述。

## 2. 定义的成本

每个工具的定义都进入每一轮请求。设第 $i$ 个工具的名字与参数结构占 $s_i$ 字节、描述占 $d_i$ 字节，$n$ 个工具的总占用是：

$$
c = \sum_{i=1}^{n}\left(s_i + d_i\right)
$$

量级上，$s_i$ 通常 80 到 150 字节（工具名、参数名、类型、必填项），$d_i$ 通常 200 到 650 字节（描述、使用场景、返回形态、注意事项）。描述占七成以上。

代入一个实际规模：十个 MCP 服务，每个暴露 20 个工具，$n = 200$，平均每个 450 字节：

$$
c \approx 200 \times 450 = 90000 \text{ 字节} \approx 90 \text{ KB}
$$

90 KB 在 200K Token 的窗口里约占 11%，而这 11% 每一轮都要付，且与当前任务是否相关无关。

成本随 $n$ 线性增长，但**判断负担不是线性的**。工具越多，模型越可能选错或漏选，因为相似的工具之间需要更精细的区分。这就是为什么单纯缩短描述解决不了问题：$d_i$ 减半，$c$ 减半，但 $n$ 不变，选择困难照旧。

正确的优化顺序是：先减少常驻定义的数量（延迟加载），再考虑缩短描述。

## 3. 描述写作

三份递进的定义，同一件事。

```json
{
  "name": "search",
  "description": "搜索内容",
  "parameters": {"type": "object"}
}
```

第一份几乎无法使用：参数结构为空，模型不知道传什么；描述没有说明搜索什么、返回什么。

```json
{
  "name": "search_web",
  "description": "搜索公开网页",
  "parameters": {
    "type": "object",
    "properties": {"query": {"type": "string"}}
  }
}
```

第二份能跑了，但仍有缺口：多长的查询合适？返回几条？能不能搜内部文档？

```json
{
  "name": "search_web",
  "description": "搜索公开网页。适合查找当前行业资料和竞品信息；不用于读取团队内部文档。返回标题、摘要、发布日期和 URL。query 必须是具体问题，不要传入整段任务描述。",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "要搜索的具体主题"},
      "max_results": {"type": "integer", "minimum": 1, "maximum": 10}
    },
    "required": ["query"]
  }
}
```

第三份写清了四件事：使用场景（公开网页、行业资料、竞品信息）、排除场景（内部文档）、返回内容（标题、摘要、发布日期、URL）、输入粒度（具体问题，不是整段任务描述）。

四件事里最容易被省略的是排除场景。写「不用于什么」看起来浪费字节，但它解决的是最常见的一类误选——模型知道这个工具能搜，就什么都搜。

还有两类信息值得写进描述：

**工具之间的先后关系。** 例如「先读取文件，再编辑文件」「发送消息前先展示草稿」。这类约束写在任何一个单独的工具描述里都不完整，但写在主流程相关的工具上能起作用。

**已知陷阱。** Claude Code 的搜索工具描述里就写了三条：正则里的字面大括号要转义、跨行匹配要显式开启、结果被截断时考虑更精确的模式。这三条把常见错误前置到了错误可能发生的地方。

## 4. 参数设计

三个原则。

**枚举优于自由文本。** 一个参数如果只有几种合法取值，用枚举声明。模型从枚举里选比从零生成稳得多，而且 schema 层面就能拒绝非法值。

**必填最小化。** 只把真正必须的参数设为必填。必填项越多，模型越可能在信息不足时编造。其余参数给合理默认值。

**一次调用完成一件事。** 如果完成一个语义动作需要三次调用（创建、配置、启动），考虑提供一个合并工具。每次调用都是一次往返，往返多了，中途出错的概率上升。

第三个原则有个例外：合并工具会让单个工具的语义变复杂，描述变长。判断标准是——合并后能否用一句话说清「它做什么」。能，就合并；不能，就保持分开。

## 5. 结果的形态

工具返回一段长字符串是最常见的设计缺陷。模型要自己从中提取状态、结论、后续动作，而它可能读错，尤其在内容被截断时。

四段式结构把这件事拆开：

<iframe src="/diagrams/tool-result-shape.html" title="工具结果的四段式结构" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/360;border:0;display:block;margin:24px 0;"></iframe>

```json
{
  "status": "success",
  "summary": "找到 5 个结果，其中 3 个与会议纪要相关。",
  "items": [
    {"title": "企业协作趋势报告", "url": "https://example.com/report", "date": "2027-02-11"}
  ],
  "artifact": "artifacts/search/call_01.json",
  "truncated": false
}
```

四段的分工：

- `status` 决定下一步动作（继续、重试、改参数、报告失败）；
- `summary` 是模型默认读的那段，用一两句话给结论；
- `items` 是需要精确判断时读的结构化数据；
- `artifact` 是出错后追溯用的原始产物路径。

`truncated` 这个布尔值看起来多余，但它解决一个具体问题：模型无法从内容判断「是不是全部」。返回里显式声明截断，模型才知道该不该继续取。

### 失败的四分类

失败不能只回一个错误字符串，因为不同的失败需要不同的恢复动作：

| 分类 | 含义 | 恢复动作 |
| --- | --- | --- |
| 可重试 | 临时故障（网络、限流、锁） | 稍后重试，通常带退避 |
| 需改参 | 参数非法、模式错误 | 改参数再调 |
| 环境问题 | 依赖缺失、路径不可达、权限拒绝 | 换路径或报告环境问题 |
| 中止 | 超时、调用方取消 | 可以重试，也可以放弃 |

四类混在一起时，模型的默认行为是重试——而「需改参」这一类重试多少次都不会成功。

有一个实现细节值得注意：退出码 0 表示成功且有结果，退出码 1 表示成功的空结果。把「空结果」与「失败」分开，模型才不会把「查无此项」当成「工具坏了」。

## 6. 权限与副作用

schema 只能检查类型、必填项、枚举值。运行时要另做检查：

```text
模型生成参数
    ↓
schema：类型、必填、范围
    ↓
业务检查：权限、路径范围、重复动作、风险等级
    ↓
执行
```

第二层的检查项里，「重复动作」最容易被忽略。同一个删除请求被执行两次，结果通常比执行一次更糟，而且模型不知道为什么失败。

第三类是「不可逆动作」：删除、覆盖、对外发送。这类动作建议独立授权：把「不可逆」作为工具的一个属性，由外层策略决定是否需要额外确认，不必每次调用都问人。

有一处分界要划清：工具层能做的是「拒绝执行」，做不到「保证内容安全」。一个写入工具可以限制只能写某个目录，但不能判断写进去的内容是否恰当。后者属于提示词与审核的职责。

## 7. 延迟加载

当工具数量超过几十个时，全量常驻的成本无法接受。延迟加载把「定义」与「能力」分开：模型平时只看到工具名，需要时按名加载定义。

这个机制的成本结构在《渐进式披露与按需注入》里展开。这里只记一个判断标准：**改用延迟加载的收益，等于常驻定义节省的字节数乘以轮数**。如果任务只有三五轮，收益有限；如果是几十轮的长任务，收益显著。

延迟加载的代价是首次调用多一次往返。这个代价在「确实需要这个工具」时值得付，在「其实用常驻工具也能做」时是浪费。所以延迟工具的描述里通常会写一句「优先使用核心工具」。

## 8. 失败模式

**同名不同义。** 两个工具都叫 `search`，一个搜代码一个搜网页。模型只能靠描述区分，而描述如果都写「搜索」，区分不了。修法：名字里带范围（`search_code`、`search_web`）。

**描述与实现漂移。** 工具的实现改了行为，描述没改。症状是模型按描述使用却得到意外结果。修法：把描述当作实现约定的一部分，改实现时同步改描述；有条件时用测试校验描述里的关键断言。

**工具过多导致选择困难。** 症状是模型反复试不同工具，或选一个明显不合适的。修法：分层（核心常驻、其余延迟），继续优化描述解决不了选择困难。

**结果不可复现。** 同一个输入两次调用返回不同结果，且没有说明为什么。修法：结果里带上时间戳与数据来源的时间点；对可能变化的查询，返回「截至某时」的限定。

四条里，第二条最难发现，因为它不报错——只是效果慢慢变差。
