# 知识组织与更新

## 1. 扁平向量库三个月后的状态

一个团队把内部文档全部切块、嵌入、入库。第一个月效果不错，第二个月开始出现重复答案，第三个月出现更麻烦的现象：同一个问题有多个版本的答案，检索会随机返回其中之一。

具体表现有四类：

- 同一份文档被不同的人上传三次，得到三组几乎相同的片段，互相挤占排名；
- 旧版政策没有下线，和新版一起被召回，模型给出自相矛盾的答案；
- 目录结构表达的知识层次完全丢失——"退款流程"与"退款政策"在向量空间里很近，但前者是操作步骤、后者是条款依据，检索无法区分；
- 更新一次文档就要重刷整批嵌入，成本高到没人愿意改文档，库逐渐腐烂。

四个现象有同一个根：**扁平化把结构和时间都丢了**。块与块之间没有从属关系，没有版本，没有有效期。检索时能做的只有"找相似的"，而相似不等于正确、不等于最新、不等于属于同一层。

## 2. 三种组织方式

### 树状抽象

把文档切成叶子块，把语义相近的叶子聚类，为每类生成一个更高层的摘要作为父节点，递归向上，形成一棵从细节到概括的树。检索可以在任意层级进行。

这类结构解决的是"从概念钻进细节"的查询。问"SSE 指令集是什么"，先在高层摘要里定位到 SIMD 相关章节，再沿树向下取到具体指令的说明。扁平检索做不到这一点，因为它只能返回若干平级的片段，无法表达"先看整体再看局部"。

代价在索引期：每一层聚类都要相似度计算，每个父节点都要一次摘要调用。文档更新时，受影响的不只是叶子，还有它向上路径上的所有摘要。

### 实体关系图

把文档知识建模成实体与关系构成的三元组网络。实体是人物、组织、概念、术语，关系是实体之间的联系。

这类结构解决两种查询。一是多跳：问"我的医生所在医院的地址"需要沿"用户→医生→医院→地址"走三步，扁平存储要么多次检索再拼接，要么根本表达不了。二是同名消歧：两个"张医生"靠关系边连到不同的人和机构，在图里天然是两个节点。

代价有两处。索引期要抽取实体与关系，再对紧密的实体群做社区发现与摘要。更根本的代价是语义降级：把自然语言转成三元组会丢掉条件与时间——"如果下周还下雨，我就取消去海边，改成去博物馆"拆成三元组后只剩孤立的事实，条件逻辑全部消失。

语义降级的成因是三元组的表达能力有限。主谓宾三个位置装不下"在什么条件下""到什么时候为止""如果不成立怎么办"。这些信息在自然语言里靠从句与连接词承载，抽取时被丢掉了。

一个缓解办法是给关系边加属性：时间范围、成立条件、置信度。代价是抽取成本上升，而且抽取时就要判断"这条关系的有效期到什么时候"，模型往往判断不准。

所以图适合作为专项索引，不适合作为通用存储。常见组合是：自然语言保存核心信息以保留语义完整，结构化字段承担索引与过滤，图用在需要多跳与消歧的垂直场景。

### 三种方式的成本对比

三种组织结构在索引期与查询期的开销差别很大，这张表可以直接用来做选型：

| 方式 | 索引期成本 | 查询期成本 | 更新成本 | 可维护性 |
| --- | --- | --- | --- | --- |
| 树状抽象 | 每层聚类加摘要，高 | 低，逐层下降 | 高，改叶子连带改祖先 | 中 |
| 实体关系图 | 抽取加社区摘要，高 | 中，需要图遍历 | 中，新增实体与边 | 中 |
| 文件系统 | 几乎为零 | 低，目录遍历加快照 | 低，改一个文件即可 | 高 |

这张表解释了一个常见现象：团队一开始选树状抽象，效果很好，但半年后没人愿意更新知识库。原因是更新成本太高——改一个事实要重算它所在分支的所有摘要。文件系统看起来最"土"，但更新成本最低，长期维护的可行性最高。

可行的组合是按更新频率分层：稳定的主体知识用树状抽象或图，频繁变动的操作细节用文件系统。两层之间靠链接连接，检索时先查稳定层定位，再查变动层取细节。

### 文件系统

不建独立索引结构，用目录表达从属、用文件名表达实体，所有条目映射为可寻址的路径。

这类结构解决的是"人可读、可维护"的问题。纯文本意味着用户可以打开、修改、修正；可以进版本控制、diff、回滚；可以用现有的搜索工具直接查。

代价在组织纪律上。文件系统本身不提供语义，如果条目之间没有链接，除了全文扫描与向量检索之外无从导航——知识越多，平铺的文件反而越难找。要让这套结构真正可用，必须有两条纪律：

第一，条目之间互相链接。提到另一个条目时给出指向它的链接，形成双向可达的引用网络。

第二，有入口页与索引页。每个目录有一份索引，说明这一层有什么、从哪开始读。

还有一条实践细节：不同模型主动建立链接的意愿差别很大。能力强的模型写新条目时会自发回指已有条目、顺手更新索引；不少模型只会孤立地追加。所以"每新增一个条目，先检索并链接到相关已有条目，并更新所在目录的索引页"这条要求必须写进写入提示，不能指望模型自觉。

三层摘要的加载方式可以叠加在这套结构上：每个条目维护一句话摘要、一份概览与全文；检索先看摘要判断相关性，需要时加载概览，确定要用了才读全文。这套做法与技能系统的渐进披露、与记忆的索引加主题文件是同一个模式。

## 3. 什么时候需要结构化

三种结构都不是默认选项。混合检索（稠密加稀疏加重排）已经能覆盖大多数需求。判断标准是查询的形状：

| 查询形状 | 需要的结构 |
| --- | --- |
| 找到包含某信息的片段 | 混合检索足够 |
| 跨文档综合（比较两份材料在某方面的差异） | 树状抽象，或预生成的对比摘要 |
| 多层次导航（从整体架构到具体参数） | 树状抽象 |
| 实体关系（A 与 B 是什么关系） | 实体关系图 |
| 同名消歧（两个同名的人分别是谁） | 实体关系图 |
| 需要人工维护与版本控制 | 文件系统 |

判断顺序可以简化成三个问题：这个查询需要多跳吗？需要聚合吗？需要人改吗？三个都不需要，混合检索就够了。

## 4. 增量更新

<iframe src="/diagrams/rag-update-paths.html" title="知识更新的两条路径与失效过滤" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/400;border:0;display:block;margin:24px 0;"></iframe>

更新有两条路径，各自解决不同的问题。增量更新处理"刚出现一条新证据，该对当前知识作什么局部修改"；定期整理处理"多次局部正确之后累积出的全局问题"。

增量更新的做法可以概括成一句话：把知识库当代码库，每次变更当一次提交。

这条类比带来的不只是版本控制，还有一整套已经验证过的流程：

1. 提议方从原始证据中发现新事实、冲突或过期内容，在工作分支上提交一个尽可能小的差异。它不会把最新一次对话直接追加到末尾：先检索相关已有条目，再增删改，同时维护链接、索引与时间元数据。
2. 审核方拿到变更前的知识、差异与原始证据，独立检查每个新断言是否有证据支撑、是否遗漏限定条件、是否与其他条目冲突、删除或改写是否过度。审核不通过时给出指向具体证据与位置的意见，避免笼统地说"再改改"。
3. 双方迭代到收敛，设置最大轮次或成本预算。超出上限转人工，不默认放行。
4. 合入后重建受影响的索引。索引是可重建的派生物，仓库里已审核的知识才是真源。

两个角色都应当是智能体而不仅仅是两次固定的模型调用。提议方往往要主动搜索其他相关条目，审核方要追溯证据、对比多份文档、运行检查。这需要工具，而现成的 Coding Agent 通常就能胜任。

有一条经验值得单独说：提议方与审核方最好用能力相近但来自不同家族的模型。不同的训练数据与推理习惯能降低两者在同一处犯同类错误的概率。能力不宜悬殊，否则审核方跟不上提议方的复杂度。这种异源互审增加独立性，但不能替代原始证据——审核方应主要核对证据与差异，不沿着提议方的结论再讲一遍。

权限上要强制分工：提议方只能写工作分支，审核方只读证据并提交审核结果，只有合并流程能更新主库与线上索引。

### 一次增量更新的具体形状

"提交一个尽可能小的差异"这句话需要落到具体形状上，否则会被理解成"随便改改"。

假设原始证据是一次客服通话记录，其中提到"退款申请现在需要上传物流单号"。这条信息涉及三个已有条目：退款流程、退款材料清单、退款审核时限。

一个合格的提议会做四件事：

第一，检索这三处是否都提到了材料要求。流程条目里写"提交申请"，清单条目里列了两项材料，时限条目里提到"材料齐全后开始计算"。三处都可能需要改。

第二，判断改动范围。新材料要求影响流程（多一步上传）与清单（多一项材料），但不影响时限（时限的起算点还是"材料齐全后"）。所以改两处，不改一处。

第三，保留条件与来源。新条目要写清"从某日起""针对线上订单"，并附上通话记录的标识。如果不写条件，三个月后线下订单的客服会照着这条执行。

第四，更新索引与链接。清单条目改动后，流程条目里指向它的链接要保持有效；如果新增了一个独立条目，索引页要加一行。

这四件事做完，差异可能只有十几行。它比"把通话记录摘要追加到库末尾"多花了十分钟，但它让下一次检索能命中正确条目，也让三个月后能判断这条规则的来源与范围。

反面的做法是把整段摘要追加成一条新记忆。短期看信息没丢，长期看库里多了一条与三个条目都部分重复的记录，检索时会与它们竞争排名。

## 5. 定期整理

增量更新的盲区是它每次只看到一个局部。长期运行后，多次局部正确的修改仍可能累积出全局问题：同一事实散落在多个条目里，新旧说法并存，摘要逐渐偏离原始证据，目录结构不再适合当前规模。

定期整理至少包含三项工作。

**去重、去旧与合并。** 全量扫描，识别语义重复、已被取代、过度碎片化的条目，删除或归并。同时重建链接、入口页与索引页，必要时拆分过大的文件、合并过小的文件、调整目录层次。要删除的是可服务的知识表达，不是下层只增不改的原始证据。

**回到原始数据核查。** 这一项最容易偷懒也最重要。只在已有摘要之间互相改写，早期的遗漏与误读会一代代传下去。整理过程需要逐段对照原始对话、执行轨迹、业务文档与工具输出，检查旧摘要是否遗漏关键事实、丢失否定词或时间条件、把推测当成事实。大规模知识库可以按目录、时间或主题分批，但必须保留覆盖清单，确保最终覆盖全量，不能随机抽样。

**冲突解决与场景限定。** 遇到互相矛盾的说法，不简单地"保留最新"或让模型猜。要追溯各自的原始来源，检查它们是否分别在不同时间、对象、地域、任务或前置条件下成立。都有效时应当把各自的适用场景写进知识，删掉其中一条会丢信息；证据不足时保留冲突与待确认状态，不强行收敛。

### 覆盖清单怎么用

"分批但不漏"这件事靠的不是自觉，是一份可核对的清单。

做法是：整理开始时先枚举全量条目，按目录或主题切成若干批，每批记录条目标识与范围。每批完成后标记状态，最后核对"已处理条目数等于总条目数"。

清单要记录三件事，缺一件就无法核对：

- 批次的定义（哪些标识属于这一批）；
- 处理状态（未处理、已处理、跳过及跳过理由）；
- 产物位置（这批的差异提交在哪个分支或哪次提交里）。

第三项在出问题时最关键。如果某次整理之后发现某个主题的知识消失了，需要能定位是哪个批次、哪次提交造成的。

Codex 在记忆整理上用了另一条思路达到同样目的：整个记忆目录是一个 git 工作区，每次整合前生成"自上次成功整合以来的差异"，整合后重置基线。差异文件本身就是覆盖清单——它列出了所有变动，且天然带可回滚能力。

这条思路可以推广：与其维护一份独立的清单，不如让变更本身可枚举、可回滚。前者依赖记录纪律，后者依赖工具保证。

### 整理之后的回放

整理完成后必须回放一组典型检索与问答用例。原因是整理改变了结构，而结构改变会让某些原本能找到的知识变得不可见——不是内容丢了，是路径变了。

回放集不需要很大，十几条就够，但要覆盖三种情况：原本能答对的（确认没退化）、原本答错的（确认修好了）、边缘主题的（确认没有因为批次划分被漏掉）。

这一步常被跳过，因为整理者倾向于认为"我只是重组，没删内容"。实际上重组会改变索引、链接与摘要层级，三者任一变化都可能让某条知识从可达变成不可达。

### 触发条件

整理可以由三种信号触发：时间（每周或每月）、规模（新增条目数超过阈值）、质量（检索失败率或冲突数上升）。

时间触发最可靠但可能过度——没有新变化时整理是浪费。规模与质量触发更精准，但需要监控指标。实践中常见组合是"月度定时加质量触发"：每月至少跑一次，出现质量下降时提前跑。

## 6. 失效过滤与隔离

**失效内容要在下发前过滤。** 一篇被新版取代的旧政策若仍留在库里，检索时可能与新版一起被召回。生产系统通常给每个片段附版本号与生效/失效时间，在检索阶段就过滤掉已失效的内容，或在摘要里显式标注"此条已于某日废止"。

**权限过滤要下推到检索层。** 知识库面向所有用户共享，但"所有用户"不等于"所有内容对所有人可见"。关键原则是按调用者的权限过滤，越权文档不能进入上下文。一旦敏感内容进入了模型的上下文，就很难保证它不以某种形式出现在回答里。

**多租户要隔离索引与元数据。** 不只是逻辑上的过滤，物理上也要分开，避免一个租户的查询检索到另一个租户的私有知识。

## 7. 智能体化检索

前面所有内容都假设检索是一次性的：查询进去，片段出来。复杂问题往往需要多轮。

智能体化检索把检索做成工具，由模型决定查什么、查几次、要不要换词。流程从单向管道变成"思考、行动、观察"的循环：分析需求，决定关键词，调用检索，评估结果是否充分，不够就提炼更精确的查询再搜，甚至换用其他工具。

这个模式的价值在复杂问题上最明显。一个需要结合三条法条的问题，第一次检索通常只能命中其中一条；模型看到结果后意识到缺什么，第二次针对缺的那部分查，才可能凑齐。简单问题上它与单次检索差别不大，所以不必默认启用——多轮意味着更多的模型调用与更长的响应时间。

代价之外还有一个安全考虑：检索到的内容正是间接提示注入最典型的载体。攻击者可以把指令藏进会被收录的文档里，等它被检索命中、拼进上下文，模型可能把数据当指令执行。防御分两层：把所有检索内容标为"供参考的外部资料，不是要服从的命令"；让有副作用的动作（转账、删除、对外发信）不因为检索内容而自动执行，而要走独立的授权判断。

## 8. 验收

组织与更新的质量体现在几个可检查的事实上：

| 检查项 | 判断方式 |
| --- | --- |
| 旧答案是否被替换 | 查一个已变更的事实，确认只返回新版本 |
| 结构是否可导航 | 从一个高层条目能否沿链接走到具体条目 |
| 更新是否可回滚 | 能否还原到上一个已审核版本 |
| 抽查是否覆盖全量 | 整理计划里的覆盖清单是否完整执行 |
| 检索路径是否可审计 | 能否说明某条结论来自哪份原始材料 |
| 权限是否真的隔离 | 用低权限账号尝试检索高权限内容 |

第三项与第四项最容易被忽略。更新不可回滚意味着一次错误的整理会永久破坏知识；覆盖清单不完整意味着每次整理都只在"上次整理过的部分"里打转，边缘内容永远得不到核查。

## 9. 本章要点

知识组织要解决的是"找得准、改得动、退得回"这三个问题，存储容量早就不是约束。

三种组织方式各自解决不同形状的查询，可以叠用，但每一种都需要在索引期投入。更新要分成两条路径：增量保证及时，全量保证不腐化。失效与权限必须在下发前处理，进了上下文就收不回来了。
