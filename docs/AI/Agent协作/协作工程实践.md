# 协作工程实践

## 1. 六项对照的由来

上一篇给了判断框架，这一篇把它落成可比较的维度。四家 Coding Agent 的协作机制设计差异很大，但都在回答同样六个问题：

| 维度 | 问题 |
| --- | --- |
| 派生方式 | 子 Agent 怎么创建，能否继续、能否分叉 |
| 隔离粒度 | 隔离到什么层级：会话、进程、还是工作目录 |
| 上下文继承 | 子 Agent 看到父级多少历史 |
| 权限收窄 | 子级的工具集比父级少什么 |
| 回报结构 | 结果以什么形式回到父级 |
| 并发与配额 | 同时能跑几个，与人的请求怎么抢资源 |

这六项不设统一的假想任务，因为四家的设计目标不同：有的为探索优化，有的为并行任务优化，有的为跨运行时复用优化。用同一个场景硬套，只会得到「都不错」或「都不行」这类没有信息量的结论。

## 2. Claude Code

### 派生方式

两条路径。一条是角色化的内置子代理：Explore、Plan、GeneralPurpose、Verification，各有固定的系统提示与工具集。另一条是进程内分叉（fork），它复制父级的上下文前缀，得到一个「看得到父级全部历史」的子会话。

两条路径解决不同问题。角色化的子代理适合「我知道要干什么，需要隔离」；分叉适合「我需要它理解我刚才说的那些细节」，例如审查一次刚完成的实现。

分叉有一个隐含代价：它继承了父级的全部上下文，包括父级的错误假设。如果父级误判了问题，分叉会带着同样的误判去执行，而且因为前缀相同，它的第一反应很可能与父级一致。

### 隔离粒度

会话级。每个子代理有自己的消息列表、自己的工具调用记录。工具调用的结果不回传给父级，只有最终消息回传。

探索类子代理（Explore）有一个额外约束：它不加载项目规则文件。这个选择有明确理由——探索只需要理解代码，不需要理解「提交前要跑 lint」这类与执行相关的约定。把项目规则塞进探索上下文，会让它把时间花在无关的规则上。

### 上下文继承

角色化子代理：全新上下文，只有调用方给的任务描述。分叉：继承父级完整前缀。

这个二元设计简单，但有一个缺口：中间档（「继承摘要但不继承全文」）没有直接支持。实践中要靠调用方在任务描述里手工写摘要。

### 权限收窄

按角色禁用工具。Explore 禁用了编辑、写文件、Agent 工具，只留只读检索类。Verification 同样不复用执行者的自检结论，它的价值来自「独立」。

收窄的粒度是工具名级，不是参数级。一个角色有读取工具，就能读所有它能访问的路径；没有「只能读 `src/`」这种约束。

### 回报结构

最终消息回父级，内容由子代理自己组织。这带来一个不稳定因素：同一个子代理两次运行，可能一次给结论加来源，一次只给结论。父级拿到的信息量因此波动。

Claude Code 在这点上依赖提示词约束（例如要求探索子代理返回绝对路径），没走结构化 schema 这条路。灵活，但不可强校验。

### 并发与配额

子代理与主会话共用同一套工具执行通道，并发受工具层的并发安全声明约束。主会话在等待子代理时是阻塞的——它发出 Agent 调用后，本轮就等这个结果。

这个设计让编排简单，但意味着「并行三个探索」必须由主会话在一次消息里同时发出三个 Agent 调用，分三轮发就串行了。

## 3. Codex

### 派生方式

任务式派生：父会话 spawn 出一个子级，子级有独立的会话与工作目录。子级可以被继续（follow-up）、被中断、被列举。

六个面向模型的操作构成完整接口：spawn、send_message、wait、list_agents、interrupt_agent、followup_task。这个接口集合比「只能派生」的设计多出两项能力——中断与列举。

列举的价值常被低估。多个子级并行时，父级需要知道「还有谁在跑、跑到哪了」，否则它只能在「等全部」和「放弃等待」之间二选一。

### 隔离粒度

会话级，且带协作模式（collaboration mode）。协作模式决定子级的行为约束——它不自由执行，按模式行事。

### 上下文继承

默认全新上下文。父级要传什么，必须显式写在 spawn 的指令里。

这个默认值与 Claude Code 的分叉形成对比：Codex 的默认是「不继承」，要继承得自己传；Claude Code 的分叉是「全继承」，要隔离得选角色化子代理。

两种默认各有代价：不继承的默认迫使调用方把任务写清楚（好），但也容易漏关键背景（坏）；全继承省了交代（好），但子级容易被父级的噪声带偏（坏）。

### 权限收窄

由协作模式限定。子级能用的工具集是父级工具集的子集，具体范围由模式定义。

### 回报结构

消息传递加等待。父级用 wait 取回结果，结果是一条消息，不是结构化对象。

这个设计让「非阻塞」成为可能：父级可以先干别的，稍后 wait。代价是父级需要自己管理「哪个子级对应哪个任务」的映射。

### 并发与配额

多子级并行是这套设计的重点。父级可以同时跑多个，用 list_agents 查看状态，用 interrupt 中止不需要的。

这带来一个资源问题：并行子级各自消耗模型调用，配额需要在父子之间分配。Codex 的做法是把配额做成配置项，不硬编码每会话上限。

## 4. OpenCode

### 派生方式

配置化的子代理类型。配置文件里声明一个 agent，标记 `mode: subagent`，它就从主菜单隐藏，只能被 subagent 工具按名字调用。

这个设计把「有哪些子代理」放进配置：加一个角色不需要改实现，只需要加一段配置。

### 隔离粒度

会话级。子代理有自己的会话，结果通过 subagent-job 回到调用方。

### 上下文继承

由类型定义。不同子代理类型可以有不同提示词与工具集，继承策略随之而变。

内置的两个内部角色值得看：一个文件搜索专家（只读、要求并行、禁止创建任何文件包括临时文件）、一个标题生成器（极短输出、只输出一行）。后者的存在说明子代理不一定承担「任务」，也可以承担「格式化动作」。

### 权限收窄

权限动作声明式。每个工具声明自己需要什么权限动作（读、写、执行等），子代理的工具集由配置决定，权限检查在执行时按声明匹配。

这个设计的粒度比「按角色禁用工具」更细：它可以表达「这个角色能用 shell，但 shell 里的写操作要单独授权」。

### 回报结构

任务输出。子代理跑完返回一段结果，调用方拿到的是文本。

### 并发与配额

子代理任务作为独立 job 管理，可以被列举与等待。并发受 provider 的速率限制约束，没有额外的每会话硬上限。

## 5. DeepSeek Harness

### 派生方式

注册表化的委派后端。委派服务（`ctx.subagents`）本身只定义接口，具体后端按需挂载：

- 进程内新会话：隔离最彻底；
- 进程内分叉：带父级已完成历史；
- 跨 ACP：通过 Agent Client Protocol 跑外部 Agent；
- 跨 Codex / Claude Code / 另一 Harness：把别的运行时当作子级后端。

最后两项是这套设计最特别的地方：子级可以不是同一个运行时。代价是跨运行时的能力差异——外部后端的工具集、权限模型、回报格式都由它自己决定，父级只能按最低共同标准使用。

### 隔离粒度

按后端而定。进程内是会话级，跨运行时是进程级。

### 上下文继承

由后端决定：新会话不继承，分叉继承父级已完成历史（注意是「已完成」，不含当前进行中的回合，避免子级看到半成品状态）。

这个细节值得指出：分叉只取已完成历史，是为了让子级看到一个自洽的过去。如果包含进行中的回合，子级会看到「父级刚说了一半」的状态，难以判断哪些已经确定。

### 权限收窄

工具集与权限按后端配置。进程内后端继承父级权限并可由配置收窄；跨运行时后端的权限由对方决定，父级只能拒绝挂载过宽权限的后端。

### 回报结构

工具回报。子级的运行结果通过 subagent-report 类工具回到父级，另有 subagent-control 用于中止与列举。

### 并发与配额

由后端决定。进程内后端与父级共享进程资源，跨运行时后端各有自己的配额。

另有一套并行的团队机制（agent-team），提供身份、邮箱、任务与共享检出。它与 subagent 是两套东西：subagent 是「临时派活」，team 是「长期共事」。并存带来一个选择成本——什么时候用哪套，需要团队自己定规则。

### 六项横向对比

| 维度 | Claude Code | Codex | OpenCode | DeepSeek Harness |
| --- | --- | --- | --- | --- |
| 派生方式 | 角色化子代理 + 进程内分叉 | 任务式派生 + 六操作接口 | 配置化子代理类型 | 注册表化委派后端 |
| 隔离粒度 | 会话 | 会话 + 协作模式 | 会话 | 按后端：会话或进程 |
| 上下文继承 | 全新或全前缀 | 默认全新 | 按类型定义 | 按后端：全新或已完成历史 |
| 权限收窄 | 按角色禁用工具 | 按协作模式 | 权限动作声明 | 按后端配置 |
| 回报结构 | 自由文本 | 消息 + 等待 | 任务输出 | 工具回报 |
| 并发与配额 | 单调阻塞，一次多调 | 多子级并行 + 列举 | job 管理 | 按后端 |

## 6. 三条判断

### 隔离与继承的取舍点

两家的默认值相反：Codex 默认不继承，Claude Code 的分叉默认全继承。哪个更好取决于任务类型。

探索类任务适合不继承——它需要的是「许可与范围」，给了上下文只会增加噪声。审查类任务适合继承——它需要理解「刚才那个改动为什么这样做」，而这些信息往往没被写进任务描述。

判断标准可以落到一句话：子任务需要的信息能否用一段任务描述写完。能，就用不继承；不能，就用继承或手工摘要。

### 工具集收窄的实际范围

四家都做工具名级的收窄，没有一家做到参数级。这意味着「只读角色」能读全部路径，「只写某目录的角色」实际上不存在。

参数级收窄需要工具层支持「带参数的权限规则」，成本高且在多数场景下收益不明显。但它确实是一个缺口：当工作目录里混有不该被读的敏感文件时，工具名级的收窄挡不住。

替代方案是环境级隔离——把子 Agent 放进只有一个目录可见的沙箱。这属于运行时能力，不在协作机制里。

### 回报结构决定主上下文体积

回报越自由，主上下文体积越不可控。四家里只有部分实现要求结构化回报（带状态、结论、来源），其余依赖提示词。

一个具体的量化：如果子代理自由返回 2000 字，父级要读全部；如果返回结构化的「结论、证据、未决问题」三段各 200 字，父级只读 600 字。三次子任务就差 4 KB 上下文。

这个差距在单次任务里不明显，在长任务里会累积成窗口压力与缓存失效。

## 7. 并发槽位与人机争用

一个容易被忽略的设计点：并发配额怎么在「Agent 之间」和「Agent 与人的请求之间」分配。

多数系统把并发做成一个池子，先到先得。这带来一个具体问题：当所有槽位被自动任务占满时，人的请求要排队。对一个交互式工具，这直接表现为「我打字没反应」。

有系统显式解决了这一点：并发上限之外留一个额外槽位，专供人的消息与状态查询使用，并且人的唤醒优先于新任务启动。这条规则的效果是「新工作不能阻止人继续已有工作」。

这个设计值得抄走的原因在于它把一个隐含假设写成了显式规则：自动化任务的紧急程度永远低于人的直接请求。
