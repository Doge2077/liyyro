# 协作模式设计

## 1. 三个 Agent 互相等

一次运维任务里，主 Agent 把「查日志」「改配置」「跑验证」分给三个子 Agent。查日志的把结果交给改配置的，改配置的等验证的确认，验证的等主 Agent 汇总。结果改配置的认为验证的会给信号，验证的认为改配置的会通知它，主 Agent 在等三方都完成。三方互相等待，任务停住，最后靠人工发现。

问题不在提示词，在于控制流没有明确的归属。三个子 Agent 都有「等对方」的逻辑，而没有一方被指定为「判断何时结束」的持有者。

多 Agent 系统出问题，多数出在这一层：控制流、状态、权限三件事的归属没有定清。

## 2. 多 Agent 的收益在哪里

多 Agent 常被描述成「多个模型一起想，答案更好」。这个说法在工程上不成立：把同一个模型跑三遍再投票，只能降低采样方差，不能提升能力上限。真正带来收益的是三处分离。

**上下文分离。** 一次代码库探索可能读几十个文件、几万行内容，这些内容对「改一个函数」这个动作没有用，但只要进了主上下文，就永久占用窗口、破坏缓存。把探索放进子上下文，主上下文只收结论，是实打实的节省。

**权限分离。** 一个只做代码审查的 Agent 不需要写文件权限。把它限制成只读，即使它被诱导，也改不了代码。效果不止是「更安全一点」，而是把一类事故变成不可能。

**失败归因。** 单 Agent 出错时，你只能看到一段长轨迹和错误结果，很难定位是检索错了、工具选错了还是判断错了。职责分开后，每个子任务的输入输出都被显式传递，出错的那一段可以被单独回放。

三处收益各有代价，且代价常常被低估：

| 收益 | 直接代价 |
| --- | --- |
| 上下文分离 | 子 Agent 看不到主历史，任务必须自包含 |
| 权限分离 | 需要为每个角色定义工具集，配置成本上升 |
| 失败归因 | 需要跨 Agent 的轨迹关联，观测成本上升 |

如果这三样收益都用不上，多 Agent 只会增加开销。这也是为什么实践中的经验是「先单 Agent，压不住了再拆」。

## 3. 四种协作形态

按控制流归谁持有，协作分为四种。这个划分比「有几个 Agent」更有用，因为控制流归属决定了谁判断完成、谁承担失败、谁有权终止。

### 中心编排

调度者持有控制流：它拆任务、派任务、收结果、判断是否继续。子任务之间不直接通信，一切经过调度者。

优点是终止条件明确——调度者说结束就结束。缺点是调度者成为单点：它的判断错了，错误会被放大到所有子任务，而且它必须理解每个子任务的输出才能正确决策。

Codex 的 multi-agent 机制偏这一侧：父会话 spawn 子级，通过 send_message 传递、wait 等待、interrupt_agent 中断、list_agents 查看状态。控制流在父会话手里，子级之间没有通道。

### 对等移交

当前执行者把控制流整个交给下一个执行者，自己退场。接收方成为新的持有者，直到它再交出去。

优点是链路短、每次只有一方在工作，不需要协调。缺点是「踢球」——A 交给 B，B 认为该 A 处理，交回去，形成循环。必须有明确规则约束「什么情况下不许交回」。

Claude Code 的 Handoff 偏这一侧：当前会话把任务交给另一个角色，接收方接手全部上下文与责任。

### 共享黑板

没有单一持有者。所有参与者读写同一块共享状态，靠写入竞争推进。协调发生在状态上，不在消息上。

优点是参与者可以并行，不需要两两通信。缺点是写入冲突与活锁：两个参与者反复改写同一字段，或者都在等对方写入某个值。

这种形态在长流程编排里更常见（图结构的工作流把共享状态作为协调介质），在 Agent 对话式协作里较少见，因为它要求状态结构极其明确。

### 独立复核

执行方与判定方分离。判定方不参与执行，只负责否决或放行。

优点是它能把「自己检查自己」的偏差消掉——执行者倾向于认为自己的结果是对的。缺点是判定方的信息可能不足：只看到结果，看不到执行过程中的权衡。

Claude Code 的 Verification 角色偏这一侧：独立对抗式复核，不复用执行者的自检结论。

### 四种形态的对照

| 形态 | 控制流持有者 | 状态归属 | 终止条件 | 主要风险 |
| --- | --- | --- | --- | --- |
| 中心编排 | 调度者 | 调度者 | 调度者判定完成 | 单点判断错误放大 |
| 对等移交 | 当前执行者 | 随控制流转移 | 无人可移交或目标达成 | 来回踢球 |
| 共享黑板 | 无（竞争写入） | 黑板 | 黑板进入收敛态 | 写入冲突与活锁 |
| 独立复核 | 复核者（仅否决权） | 执行者 | 判定给出结论 | 判定方信息不足 |

## 4. 三维归属

控制流只是第一维。完整的设计要回答三个问题：谁的上下文、谁的状态、谁的权限。

<iframe src="/diagrams/collab-ownership.html" title="上下文、状态与权限的三维归属" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/340;border:0;display:block;margin:24px 0;"></iframe>

**上下文归执行者。** 会话历史、工具结果、当前观察都属于正在干活的那一方。执行者换人，这些就断了——这是设计上应有的行为，不是缺陷。

**状态归任务。** 阶段、已完成项、待办、授权范围属于任务本身，不属于任何执行者。只有把状态从会话里抽出来，执行者才能被替换。

这两条的区分是多数多 Agent 设计的成败点。把状态塞进上下文，等于宣布「这个任务只能由这个会话完成」；一旦会话因为超时、崩溃、压缩而更换，状态就丢了。

**权限归来源。** 谁在哪个渠道、以什么身份发起，决定了这次任务能做什么。权限不随上下文传播：子 Agent 读到了父 Agent 的对话，不代表它继承了父 Agent 的权限。

第三条最容易被违反，因为「父 Agent 有权限，所以子 Agent 也应该有」在直觉上很自然。但这条直觉会带来一个具体后果：父 Agent 被诱导执行了越权动作，子 Agent 会继承这个越权。

正确的做法是权限随任务走、不随上下文走：任务声明「允许写 `src/` 下的文件」，执行者无论是谁、无论看到了什么，都受这条约束。

## 5. 通信成本的模型

每次 Agent 间传递都有成本。设一次交接的总成本为 $h$，它可以拆成三项：

$$
h = s + r + l
$$

其中 $s$ 是序列化成本（把要传的东西写成子 Agent 能读的形式），$r$ 是恢复成本（接收方读到这些内容并重建理解），$l$ 是损耗（传递过程中丢失的信息造成的返工）。

三项里 $l$ 最难察觉也最贵。一个典型例子：主 Agent 把「修复登录失败」交给子 Agent，省略了「上次试过改 session 超时，没用」。子 Agent 重新试了一遍改超时，浪费一轮。

要降低 $l$，可以引入一个自包含度的度量。设子任务实际需要的外部状态为 $e$（它必须知道才能正确做事的信息量），已传递的状态为 $p$：

$$
\rho = \frac{e}{p}
$$

$\rho \le 1$ 时交接是自包含的，子 Agent 不需要回头问。$\rho > 1$ 时信息不足，子 Agent 要么猜，要么返工。

举两个算例。

**算例一，探索子任务。** 任务是「找出支付回调的处理函数，列出定义与调用点」。它需要的外部状态是仓库本身（$e$ 约等于「代码库的可读性」，用探索次数近似：预计需要 5 次检索），已经传递的是「目标、范围、输出格式」（$p$ 约等于 1 次明确的检索指令）。$\rho = 5$，远大于 1。但这里 $\rho > 1$ 是可接受的，因为探索子任务有工具可以自己获取信息——它需要的是「许可与范围」，不是「答案」。

**算例二，修改子任务。** 任务是「按这份方案改三个文件」。如果只传「改这三个文件」，子 Agent 不知道为什么要改、哪些不能动、改完怎么验证，$e$ 包含方案意图、改动范围、验收方式，$p$ 只传了文件列表，$\rho$ 明显大于 1，返工概率很高。加上方案与验收标准之后，$\rho$ 降到 1 附近。

这两个算例说明一个判断：$\rho$ 的大小要看子 Agent 能否自己获取缺失的信息。能自己查的（代码、文档、日志），$\rho$ 大可以接受；不能自己查的（决策意图、历史教训、用户偏好），$\rho$ 必须压到 1 以下。

## 6. 终止条件与死锁

多 Agent 最常见的故障是不结束，很少是答错。三种形态。

**互相等待。** A 等 B 的信号，B 等 A 的通知。这是第 1 节那个案例的成因。判据是：任何等待关系里，是否存在至少一方有超时或轮次上限。

**重复委派。** A 把任务交给 B，B 认为该 A 处理，交回 A，A 再交给 B。判据是：交接路径上是否有「同一任务不得两次经过同一 Agent」的约束。

**无限复核。** 复核者不断发现问题，执行者不断修改，没有收敛判据。判据是：复核轮次是否有上限，以及超出上限后由谁裁决。

三种死锁的共同点是「没有指定终止权的持有者」。修复方式都是显式指定：

| 死锁形态 | 修法 |
| --- | --- |
| 互相等待 | 指定一方为持有者，其余为被通知方；持有者设轮次上限 |
| 重复委派 | 交接链上记录已访问的 Agent，重复即拒绝 |
| 无限复核 | 复核轮次上限，超限转人工或按执行者版本放行 |

第三条的「按执行者版本放行」值得解释：当复核无法收敛时，与其无限循环，不如放行并记录「这是第 N 版，复核未通过但已放行」。这比卡住更诚实，也让后续可以追查。

## 7. 失败模式

四类，各自对应一个归属没定清。

**责任稀释。** 症状：出了错，每个 Agent 都能说「这不是我负责的」。成因：控制流持有者不明确，或者持有者没有权限约束下游。修的位置在协作形态选型——中心编排把责任放在调度者，对等移交放在最后的持有者。

**权限漂移。** 症状：子 Agent 做了父 Agent 不该做或不会做的事。成因：权限随上下文传播，没有随任务声明。修的位置在权限模型——把权限做成任务的属性，不继承。

**汇总失真。** 症状：多个子任务的结果都正确，合并后结论错误。成因：汇总时丢掉了限定条件（「在测试环境」「只对某类订单」）。修的位置在回报结构——要求回报必须带条件与来源，不只是结论。

**终止缺失。** 症状：任务长时间不结束，或反复在两个 Agent 之间往返。成因：没有指定终止权持有者。修的位置在终止条件，见上一节。

四类里，前两类是设计问题，后两类是实现问题。但它们的共同点是：都表现为「系统在动，但没人知道该停下来或该改哪里」。

## 8. 什么时候退回单 Agent

三条判据，任何一条成立就该考虑退回。

**第一，子任务之间需要频繁共享上下文。** 如果三个子任务每做一步都要看另外两个的中间结果，拆开只会增加传递成本。共享黑板形态能缓解，但它的协调复杂度通常不低于单 Agent 的长上下文。

**第二，任务短于交接开销。** 一个子任务如果本身只需要两次工具调用，而交接需要一次上下文重建，拆开就是负收益。粗算：交接成本约等于一次完整的短任务，子任务本身短于这个量级就不值得拆。

**第三，权限没有实质差别。** 如果所有子角色都需要同一套工具、同一份权限，那权限分离的收益为零，剩下的只有上下文分离——而上下文分离用单 Agent 加子任务摘要也能做到，不必引入多 Agent 的编排复杂度。

第三条常被忽略。很多多 Agent 设计里，所有角色的工具集完全一样，只是提示词不同——这种设计等价于用多个提示词跑同一个 Agent，收益仅来自上下文隔离，却要付出全部编排成本。
