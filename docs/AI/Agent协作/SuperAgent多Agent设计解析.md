# SuperAgent 多 Agent 设计解析

## 1. 它解决的不是「派生子 Agent」

多数多 Agent 框架把重点放在「父 Agent 如何派生子 Agent 并收拢结果」。`deepseek-ai/dsh-superagent-prototype` 走的是另一条路：它把 Agent 会话放进一组领域对象之间，长驻主会话只做路由，每个工单配一个执行会话，中间隔一层完整的领域模型。

这个选择的直接后果是：会话可以被随时替换，而任务状态不会丢。会话崩了、超时了、被压缩了，重新起一个就好——因为「这个任务进行到哪一步、被授权做什么、属于谁」都记在领域对象里，不在会话历史里。

我认为这是整份设计里最值得学的部分，下面逐层看它怎么做，以及我认为哪里有问题。

## 2. 领域模型与流转

八个概念构成主干：来源、触发、线程、评估、决定、授权、工单、派工。加上两个支撑概念：订阅与渠道。

流程是：来源产生触发；触发归属到一个或多个线程；触发按线程汇成批次进入评估；评估产出决定；接受时创建工单并附带授权；派工把工单交给一个执行器实例；执行器的报告经渠道写回来源。

### 两条状态线

工单有独立于执行器的状态线：open → ended，以及在某些条件下回到 open。

派工有独立于工单的状态线：pending → running → ended。

两条线独立的理由在文档里写得很明确：一个工单在生命周期内可以有多次派工。执行器崩了，工单不结束，换一次派工继续；执行器完成了，工单可能还在等后续的审查意见。

这个分离解决了单 Agent 设计里一个常见问题：会话结束就等于任务结束。实际上任务的生命周期通常长于任何一个会话。

### 恢复与重新校验

已结束的工单保留授权。人在它自己的线程上发一条消息，可以恢复同一份工作，不需要新的评估或决定。

这条规则有一个前提：恢复前要重新校验授权。校验项包括：

- 来源是否仍在监听原线程；
- 若授权来自推断，接受模式是否仍为自动、匹配规则是否仍启用；
- 若授权来自准入表，按今天的表与名单是否仍能给出原本的强度；
- 若是机器人授权，该机器人是否仍在名单上；
- 其余情况，发送人是否仍在允许名单上。

校验失败时，工单保持结束状态，等待中的消息按「未到达任何工单」处理，进入评估。主会话不会被告知它曾到达过工单。

这段设计我认为是对的：授权不是一次授予永久有效，它绑定当时的策略版本，恢复时按当前策略重算。代价是恢复可能失败，而且失败的原因对用户不透明——他只知道「我说了话，但没有反应」。

## 3. 授权与上下文的分离

这是整个设计最值得学的一处。

**授权（Mandate）决定能做什么。** 它记录策略版本、范围、强度、匹配的规则、发送人在该来源上的身份、以及来源如何收到这个触发。

**订阅（Subscription）决定能看到什么。** 每个活着的已订阅工单会收到线程上的每条消息，作为上下文扇出。

关键规则：扇出绕过准入检查，也不授予任何新权限。工单始终受限于它的授权范围。

这个分离带来的好处很直接：讨论可以自由流入执行器，不需要每次重新判断「这个人有没有资格说话」。资格在授权时已经判断过，后续消息只是补充信息。

它也带来一个我认为需要正视的风险。文档里明写订阅扇出「不检查是谁发的」——包括机器人消息与 CI 消息。这意味着一条来自任何来源的消息都会进入执行器上下文，而执行器可能据此行动。

设计者对此的防护是：扇出只给上下文，不给权限，执行范围仍受授权约束。这个防护在「执行范围写得很窄」时成立；如果授权范围很宽（例如「可以修改本仓库任意文件」），扇出就成了一个软通道——外部内容可以影响一次被授权的大范围修改。

我的判断是：这个风险没有被消解，只是被推迟到了授权范围的定义上。更稳妥的做法是让扇出也带来源标记，并在提示词层明确「来自非允许名单的内容仅作参考」，避免完全不做检查。

## 4. 三档强度与准入表

授权强度分三档：显式请求、推断候选、不准入。

- 显式请求：允许名单上的人点名智能体，或在线程已有工单时跟进。
- 推断候选：名单外的人跟进、准入表某格设为推断、来源机器人名单上的机器人消息。
- 不准入：其余机器人消息、被准入表忽略的、以及关闭模式下的一切推断。

准入表是「接收范围 × 三格」的结构。三格分别是：在名单上但未点名、不在名单上但点名、不在名单上且未点名。每格可选推断、忽略或显式。

接受模式是三态的：关闭、观察、自动。观察模式下，正向研判会被记录为「本会接受」但不实际接受。

从观察到自动的迁移路径是这份设计里很实用的一条：先让系统跑一段时间，看它会接受什么，确认无误后再开自动。

### 我对准入表的意见

准入表在表达力上没问题，但在可理解性上有问题。它是接收范围乘三格的笛卡尔积，加上机器人名单、接受模式、策略版本，共同决定一条消息能不能变成工作。

一个非工程角色的团队负责人，要回答「我的团队里谁知道这个机器人能替他开工」这个问题，需要把上述五个概念一起读懂。这在实际部署里很难。

我认为更可用的形式是「默认拒绝 + 显式列出允许的交集」：与其让每一格可选三态，不如让团队直接列出「谁在哪个范围可以请求什么」，其余一律不准入。表达力下降，但审计成本大幅下降。

## 5. 注意力预算作为第一原则

这份设计的开篇原则是：用最少的人类注意力，给出最大的价值。它被落实成了一组具体约束。

对智能体：

- 只在被请求时行动，或按团队写下的规则行动；
- 只在有人必须行动或能用上结果时说话；
- 一次只问一个具体问题，用结构化形式；
- 按影响停止，不按投入停止；
- 诚实报告：草稿标注未完成，失败报告为失败。

对设计：

- 概念要少，业务需求变成已有概念的属性，或一段提示词；
- 设置要少，一个默认值能适用几乎所有团队时就取代设置；
- 面板只显示需要人处理的事；
- 文档按顺序写，每篇只依赖前面引入的概念。

这些原则被落成了硬约束，其中几条我认为很有说服力：

| 约束 | 数值 | 我的理解 |
| --- | --- | --- |
| 路由笔记长度 | 不超过 30 词 | 迫使路由只传事实，不做解释 |
| 发给人消息长度 | 不超过 100 词 | 强制删掉寒暄与铺垫 |
| 主会话禁止等待 | shell 超时超 30 秒拒绝，job 等待超 5 秒拒绝 | 等一秒，就晚一秒处理新候选 |
| 后台预算 | 回合结束后最多 30 分钟 | 防止一个卡死的任务永远占着槽位 |

前两条的作用不是「省 Token」，是「强迫表达」。写 30 词的路由笔记时，你没法写铺垫，只能写「哪个工单、什么决定、为什么」。

第三条尤其值得说。多数系统允许主 Agent 等一个长时间命令跑完，代价是这期间新的候选无法被处理。这份设计直接禁止等待，理由是「一个被阻塞的步骤会延迟新候选」。这是个很强的取舍：它把「主会话绝不阻塞」放在了「方便」之上。

## 6. 执行器与配额

每个工单获得一个名为 `worker-<工单 id>` 的执行会话，以及一个按工单短名命名的目录。目录在配置的执行根下创建。

几个具体机制：

**后台工作与槽位。** 一回合结束时若还有 shell 任务或子代理在跑，工单保留槽位并保持「工作中」，不会被报告为等待。任务完成会唤醒执行器。回合结束后后台最多 30 分钟，超时则杀掉 shell 任务、报告等待。

**交接给人即释放槽位。** 报告为就绪或提出问题后，除非之后又来了新输入，槽位立刻释放。

**并发上限加一个额外槽位。** 配置的并发上限之外留一个槽位，专供人的消息与状态查询。人的唤醒可以在正常槽位满时使用额外槽位，并且优先于新任务启动。

最后这条我认为是整个配额设计里最漂亮的一处。它把「自动化任务的紧急程度永远低于人的直接请求」这个隐含假设写成了显式规则。多数系统的并发池是先到先得，结果是自动任务占满槽位时，人打字没反应。

**准备命令。** 第一次派工前，如果工单目录不存在，用 `sh` 在执行根跑一次准备命令，限时十分钟。典型用法是 `git worktree` 创建检出。失败则工单失败并记录输出。

## 7. 我的批判

八条，按设计张力分三组。

### 张力一：注意力与完整性

**第一，路由不做技术决定，但要做范围判断，这两者矛盾。**

文档说主会话「只转发原始触发与路由事实，不做技术决定」。但同时它要判断「这条消息该接受、该附加到已有工单、还是该忽略」，这本身就是一个技术判断——判断它是新工作还是已有工作的延续。

文档给出的办法是「只在消息明确指向某工单的 PR、Issue、来源消息或致谢时才附加，主题相似不够」。这条规则是可靠的，但它把「明确指向」的识别责任交给了路由模型，而路由模型被要求不读代码。

**第二，领域事件齐全，但不记录判断理由。**

系统记录了每次决定（接受、停止、忽略、不可用），记录了授权与派工，但「为什么这样判断」没有结构化留存。面板显示状态，不显示推理。

对一个需要人审的系统，这是个实际缺口：人在复核一次「本会接受」的观察记录时，看不到判断依据，只能看到结论。

我的建议是把判断理由写进事件，但在面板上折叠——不占人的注意力，但在需要时可查。

**第三，30 分钟后台预算截断长任务连续性。**

这个约束的目的是防止卡死任务占用槽位，但代价是把「长任务的连续性」交还给人：跑测试超过 30 分钟，任务被杀，报告等待，人要么重新触发，要么手工继续。

我认为可以更细：按任务类型区分预算，例如测试类任务给更长预算，交互类任务给更短预算。

### 张力二：自动化与可控性

**第四，准入表表达力换可审计性。**

已在第 4 节说明。我的替代方案是默认拒绝加显式交集。

**第五，策略变更不撤销已发授权。**

文档明确说：策略变更会丢弃正在运行的评估、重新排队触发、给受影响工单发变更通知，但「不会立即撤销活工单的授权」。撤销只发生在下次恢复前的重新校验时。

这个设计的理由是「被取消的变更会留下半完成的工作」，所以选择记录并通知，不做取消。

我认为这个权衡在多数情况下成立，但有一个它没覆盖的场景：策略变更的原因是安全问题（例如发现某条规则会导致越权）。此时「推迟到下次重新校验」意味着风险继续存在。更稳妥的做法是给策略变更一个「紧急」标记，紧急变更走撤销路径。

**第六，扇出不检查发送人。**

已在第 3 节说明。

### 张力三：领域纯洁与实现重复

**第七，单工单单派工串行，并行只能靠子代理，而子代理不再收窄权限。**

一个工单同时只有一个派工，所以工单内部的并行只能靠执行器起子代理。文档说执行器的子代理使用宿主的「标准」预设，并保留执行器的允许工具，工单结束时失去这些工具。

缺口在这里：子代理继承了执行器的权限，没有进一步收窄。如果执行器有写仓库的权限，它的子代理也有。

对一个把「授权与上下文分离」做到极致的系统，这一处的粗糙显得不协调。

**第八，与宿主原生团队机制概念重叠。**

宿主的 subagent 家族已有进程内、分叉、跨运行时等后端，另有一套团队机制提供身份、邮箱、任务与共享检出。superagent 又实现了自己的执行器会话、邮箱式消息传递、身份（来源上的身份）。

三套东西并存，分工靠文档说明维持。这带来一个实际问题：部署者要判断什么场景用哪套，而这个判断没有明确依据。

## 8. 三条我认可的设计

批判之后要说清哪些成立。

**第一，授权与上下文分离。** 这是整份设计里最有价值的一条。它把一个常见混乱——「谁看到了什么」与「谁被允许做什么」——拆成两个独立的领域对象，各自有明确的创建与失效规则。第 3 节提到的风险不否定这条设计本身，只说明它在「扇出不检查来源」这一点上留了口子。

**第二，执行器可替换。** 因为状态在领域对象里，执行器只是一个可替换的端口。这带来的不只是容错，还有可测试性：你可以给同一个工单换不同的执行器，观察结果差异。

**第三，把注意力当一等预算。** 30 词的笔记、100 词的消息、禁止等待、额外槽位——这些看似零散，实际是同一条原则的多次落实。它迫使每个交互都回答「这次交互值得占用多少人的注意力」。

## 9. 从这份原型学到什么

如果把这份设计抽象成可迁移的三条经验：

第一，把「任务」与「执行它的会话」分开。任务有自己的状态与生命周期，会话是可替换的资源。这条经验能直接用在任何长流程 Agent 系统上。

第二，把「能不能做」与「能看到什么」分成两个独立的授权对象。混在一起时，你会发现在每次消息到达时都要重新判断资格，而这个判断本身就成了瓶颈。

第三，给人类的请求留一条不排队的通道。看起来是个小优化，实际上它决定了系统在高压下是否可用。

三条都不依赖这份原型的领域模型，可以直接用在别的架构里。
