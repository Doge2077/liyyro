# 观测回归与发布

## 1. 一个通过了所有检查的坏版本

一个版本在发布检查里全绿：回归集通过率 84%（基线 83%），安全用例全过，成本略降，时延持平。上线后当天收到投诉：它开始把用户的项目文件上传到公共存储。

查轨迹发现：这个任务在回归集里只有两个用例，且都是「上传成功即通过」。没有人检查「上传到哪里」。

这个案例说明发布检查的一个结构性缺陷：**检查项覆盖的是已知的失败模式，未知的那类不会被发现。** 所以检查之外还需要灰度与快速回滚。

## 2. 生产观测

<iframe src="/diagrams/eval-observability.html" title="必须记录的观测字段" loading="lazy" style="width:100%;height:auto;aspect-ratio:1000/340;border:0;display:block;margin:24px 0;"></iframe>

六类字段，缺任何一类就会有一类问题无法定位。

| 字段 | 回答什么 | 缺了会怎样 |
| --- | --- | --- |
| 任务标识与版本 | 这次运行属于哪个任务、哪个版本 | 无法按版本对比 |
| 工具与参数摘要 | 它做了什么 | 无法归因到具体动作 |
| 结果状态 | 成功、部分成功、失败 | 无法算通过率 |
| 失败类型 | 属于哪类问题 | 只能看总数，看不出趋势 |
| Token 与费用 | 成本是否退化 | 成本上升发现不了 |
| 时延 | 首词与总时长 | 体验退化发现不了 |

第二项写「摘要」，不存全文：工具参数可能含大段内容，全存会让日志成本失控。摘要保留关键字段（路径、查询词、目标 URL），足够归因。

### 失败类型的设计

八类足够，每类对应一个不同的修改方向：

| 类别 | 修改方向 |
| --- | --- |
| 工具选择错误 | 工具描述或名称 |
| 参数错误 | schema 或描述 |
| 检索未命中 | 索引或检索策略 |
| 过程违规 | 提示词或程序约束 |
| 能力不足 | 模型或工具能力 |
| 环境故障 | 基础设施 |
| 需求不清 | 澄清环节 |
| 超时或取消 | 性能或预算 |

类别太少（例如只有「成功/失败」）无法定位；太多（例如二十几类）没人维护，且标注一致性下降。

有一个实操建议：失败类型由规则或模型在运行时自动打标，不用人工填。人工填的字段在长期运行里一定会退化——先是填错，然后是不填。

### trace 的切分

一次任务是一个 trace，内部按工具调用切成 span。切分粒度影响两件事：查询成本与归因精度。

切得太细（每次函数调用一个 span），日志量爆炸；切得太粗（整个任务一个 span），无法定位是哪次工具调用出了问题。

一个可用的粒度是：每次模型请求一个 span，每次工具调用一个 span，压缩与记忆操作各一个 span。这个粒度覆盖了所有会改变行为的事件。

## 3. 离线回归

回归的目的不是「证明没变差」，是「发现变差了」。

### 按变更类型选子集

全量回归的成本随用例数线性上升。实践中按变更类型选子集：

| 变更类型 | 回归范围 |
| --- | --- |
| 提示词改动 | 全部用例 |
| 单一工具改动 | 用到该工具的用例 + 抽样 20% |
| 新增工具 | 全部用例（新工具可能被误选） |
| 依赖升级 | 全部用例 |
| 文档与注释 | 不跑 |

第二行的「抽样」是必要的：一个工具的改动可能通过「模型开始更多/更少选它」影响其他任务。只跑相关用例会漏掉这类间接影响。

### 判定标准

回归的判定不能只看平均数。三条规则：

**关键用例全过。** 安全、核心流程的用例，任一失败即阻塞。

**总体不退化。** 通过率下降超过 2 个百分点即阻塞（这个阈值要大于统计噪声）。

**单任务族不塌陷。** 任一任务族的通过率下降超过 10 个百分点即阻塞，即使总体没退化。这条规则防的正是第 1 节那类情况——某一族全崩但被其他族涨的分掩盖。

第三条的阈值高一些（10 个百分点），因为任务族的样本量小，噪声大。

## 4. 发布检查

四类检查，各自独立。

| 检查项 | 判据 | 阻塞性 |
| --- | --- | --- |
| 正确性 | 关键用例全过，总体不退化，单族不塌陷 | 阻塞 |
| 安全性 | 越权、注入、隐私用例全过 | 阻塞 |
| 成本 | 单任务平均 Token 不超过基线 1.2 倍 | 需说明理由 |
| 时延 | 首词与总时长不超过基线 1.3 倍 | 交互路径阻塞 |

成本与时延设成「需说明理由」，没有硬阻塞，因为它们的权衡有时合理——例如换一个更强的模型让准确率提升 5 个百分点、成本上升 15%。

但「需说明理由」有一个前提：有人会读这个理由。如果没人读，它实际上是自动放行。所以这一档需要指定审阅人，否则应当改成硬阻塞。

### 分级放行

不是所有改动都需要同样的检查。可以分三级：

| 级别 | 内容 | 检查 |
| --- | --- | --- |
| 一级 | 提示词、Skill 内容 | 全部四类 |
| 二级 | 工具描述、参数 schema | 正确性 + 安全性 |
| 三级 | 文档、注释、日志字段 | 构建通过即可 |

分级的意义在于让检查的成本与风险匹配。全部走一级会让流程变得冗长，团队开始想办法绕过。

## 5. 灰度与回滚

检查通过不代表没问题。第 1 节的案例就是全绿上线的。

灰度的两种切分方式：

**按流量比例。** 最简单，适合单一入口的服务。问题在于同一用户可能在不同请求里落到不同版本，体验不一致。

**按任务族。** 按任务类型分批放开。好处是能观察到「某一族变差」、不被整体数字盖住，坏处是需要能识别任务族。

回滚的触发条件要提前定，不要等到出事再讨论：

- 关键用例在线上出现失败；
- 失败率相对基线上升超过阈值；
- 出现新的失败类型（以前没见过的类别）；
- 用户投诉集中在某一类行为。

第三个条件最敏感也最有用。它不依赖绝对数值，只依赖「这是新东西」——而新出现的失败类型往往正是灰度要发现的东西。

回滚时限建议写进流程：确认要回滚后，多久之内必须完成。经验值是十分钟内——超过这个时间，损害通常已经发生。

## 6. 反馈闭环

线上失败到新用例的路径要短，否则同类问题会反复出现。

一条可用的流程：

1. 失败样本自动进候选池，带失败类型标签；
2. 按类型聚类，同一类型只保留最有代表性的若干条；
3. 人工确认后转成正式用例，进对应任务族；
4. 用例先进训练子集，不进保留集。

第 4 步的理由：新用例来自线上，它反映的正是当前版本的问题。如果直接进保留集，保留集就被当前版本「污染」了——它会变得容易通过。

去重与聚类这一步不能省。线上失败样本的分布高度偏斜，同一类问题可能有几千条。全部加进用例集会让评测集被单一问题主导。

## 7. 失败模式

**检查变成仪式。** 症状：所有改动都能通过，但上线后仍有问题。成因：检查项与真实风险脱节，或检查结果没人看。修法：定期用「已知有问题的版本」测试检查能否拦住。

这一条值得展开：如果一个检查项在过去半年里从未拦住任何改动，它要么是多余的，要么是失效的。两种都需要处理。

**观测字段过多导致成本失控。** 症状：日志成本超过模型调用成本。成因：记录了全量工具输出与完整对话。修法：只记摘要与关键字段，全文另存并按需读取。

**回滚不可用。** 症状：出问题后无法快速回到上一版本。成因：数据库 schema 变了、配置不兼容、依赖版本锁定。修法：把「可回滚」作为发布的硬性前提，每次发布前验证回滚路径。

第三条最致命，因为它在正常情况下完全看不出来。一个具体的检查方式：每次发布后，在一个测试环境里立刻执行一次回滚，确认能成功。这个操作只花几分钟，但它是「回滚可用」的唯一证据。

**门禁与灰度脱节。** 症状：检查全绿，灰度立刻全量。成因：灰度没有明确的观察指标与时长。修法：灰度必须定义「观察什么、看多久、什么情况下停」。
